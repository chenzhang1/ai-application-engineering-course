## 12.6 专题六：LangGraph

> 对应正文：part08（ch43~ch51，全书重点）与项目二（综合项目/项目二_日志排障助手）。这个专题的深水区是**恢复语义与幂等**——它是"写过演示"与"敢上生产"的分界线，也是本书验收标准（手写"带审批+恢复+持久化"的三节点图）的直接考察形式。

### 题 6-1 [模拟题] LangGraph 的状态更新为什么设计成"部分更新 + reducer"？

**1. 问题与考查点**：通道（channel）模型的机制理解——LangGraph 面试的第一分水岭；能否精确说出覆盖语义、追加语义、add_messages 三态。

**2. 常见错误回答**："每个节点返回整个新状态，后面的覆盖前面的。"——"覆盖"只是无 reducer 字段的默认语义；说不出并行写入怎么办、add_messages 的按 id upsert；更常见的错误是把所有字段都加上追加 reducer（过度设计）。

**3. 简洁合格回答**：每个状态字段是一个通道：不带 reducer 的通道是**覆盖语义**（后写顶掉先写），带 reducer 的通道按你声明的合并函数归并——`Annotated[list, merge]`。节点返回值是**部分更新**（只声明"我要改哪个字段"）。三个设计理由：① 节点解耦——只声明自己关心的字段；② 并行安全——同一超步多节点写入必须有确定的归并规则，否则 `InvalidUpdateError: Can receive only one value per step`；③ 恢复友好——快照+部分更新天然支持重放。`add_messages` 是最常用的消息通道 reducer：新 id 追加（自动把 str/tuple 包装成对应 Message 类型）、同 id **原位替换**（消息级 upsert）。

**4. 深入解释**：字段级类比——覆盖通道是白板（谁最后写是谁的），reducer 通道是签到表（只会变长或按规则归并），同一状态里两类可并存（EX-44-01 的 text 覆盖、findings 追加）。状态设计六条军规（ch44.3）：每个字段先问谁写/谁读/生命周期，答不出就删；追加型字段（日志/证据/轨迹）一律显式 reducer，裸 list 迟早吃掉审计记录；"当前值"字段（category/route）保持覆盖；可序列化优先——对象引用放闭包（工厂注入）不放状态；大对象不进状态（快照体积）；结论与过程分字段。工程坑：`from __future__ import annotations` + reducer 定义在函数内 → NameError（注解变字符串后按模块全局名解析），reducer 必须放模块顶层。

**5. 工程案例**：见 part08 ch44——EX-44-01（最小两节点）、EX-44-02（覆盖/追加/upsert/自定义去重四组实验）、EX-44-03（没有 checkpointer 时第二次 invoke 不记得第一次——"记忆"是 ch47 给的，不是 MessagesState 给的）；P2 的 TriageState 全部追加型字段用 `Annotated[list, merge_lists]`（README 第 4 节第 1 条），天然支持并行写入与恢复重放的幂等合并。

**6. 追问与回答边界**：
- 追问 1：为什么模型重答后消息列表不翻倍？——要点：add_messages 按 id 判重 upsert；适配层复用原消息的 id 就能原位替换。
- 追问 2：两个图报 `Channel 'xxx' already exists with a different type`？——要点：同名字段不同 reducer 在编译期注册冲突；复用同一个 reducer 对象（测试/test_ch47.py 的做法）。
- 边界：Pydantic/dataclass 状态 schema 的序列化细节、RemoveMessage 删除语义，以所用版本官方文档为准。

### 题 6-2 [模拟题] 条件路由和循环怎么写？recursion_limit 应该调多大？

**1. 问题与考查点**：控制流工程化——"判断放节点、分流放边"的职责划分与终止条件设计；recursion_limit 的语义定位是高频陷阱。

**2. 常见错误回答**："把 recursion_limit 调到 1000 就不会报错了。"——把保险丝当设计；或路由函数里直接查库做 IO（决策不可测、边不可审）。

**3. 简洁合格回答**：`add_conditional_edges(节点, 路由函数, path_map)`——路由函数**只读已归并进状态的字段、零副作用零 IO**（"判断"放节点里可测，"分流"放边上可改）；返回值必须在 path_map 全覆盖，缺失值直接 KeyError（fail-fast，配 pytest 锁住）。循环靠回边+终止条件：终止条件是独立可测的纯函数（如"评审通过→END，否则→draft"）。recursion_limit 默认 25，是**保险丝不是设计**——正经循环必须有业务终止条件（轮次/分数上限+达到上限的显式行为：返回部分结果并打标，而不是抛异常），调大它来容纳失控循环=把 bug 配置化。

**4. 深入解释**：四种常见路由模式（ch45.5）：分类路由（一进多出）、闸门路由（不通过出图或去人工）、升级路由（按严重程度分流）、Send 扇出（份数由数据决定）——识别口诀：需求里"根据 X 走不同流程"是①，"不满足不准往下"是②，"越严重越要贵通道"是③，"每个元素都要处理一遍"是④。循环图上线清单：业务上限+达限行为显式定义、每轮朝终止条件前进（零进展轮提前退出）、"0 次循环"与"打满上限"都有测试、**循环体内动作必须幂等**（循环×重试×恢复重跑是副作用重复的三重放大器）。模型分类的路由兜底三段式：schema 枚举约束→校验失败重试一次→回退默认通道并打标。

**5. 工程案例**：见 part08 ch45——EX-45-01（分类路由，Mock/Real 双模式）、EX-45-02（循环与 GraphRecursionError 熔断）、EX-45-03（Send 扇出）；P2 只有一条条件边（assess 后是否进人工审批）——刻意为之："每条条件边都该有测试，边越少越稳"；P2 扩展方向的"多轮取证循环"（缺口→回 extract_evidence）也明确要求 recursion_limit 保险丝（README 第 12 节）。

**6. 追问与回答边界**：
- 追问 1：GraphRecursionError 在"看起来没循环"的图里出现？——要点：两节点互相指或条件边震荡；修法是加尝试次数字段设上限，不是调大 recursion_limit。
- 追问 2：模型输出了 path_map 之外的分类值，生产怎么办？——要点：不能靠崩——schema 兜底+重试一次+回退通道打标（错分的代价是"走了通用通道"，可控可统计）。
- 边界：recursion_limit 的精确计数口径（按超步，每超步 1~2 次节点）以官方文档为准，本书未逐版本核对。

### 题 6-3 [模拟题] 讲清 interrupt 的恢复语义。为什么说"节点会从头重跑"？

**1. 问题与考查点**：本书重点的验收题——恢复语义的**精确**表述；"节点重跑"这个细节直接决定副作用设计，答错它等于没做过生产图。

**2. 常见错误回答**："interrupt 就是断点，恢复后从断点下一行继续。"——错。恢复后**节点从头重跑**，interrupt() 那一行"返回" resume 的值；"下一行继续"的想象会让 interrupt 之前的副作用执行两次。或者把 interrupt 说成异常处理机制（实现上像，语义是流程级暂停）。

**3. 简洁合格回答**：完整序列五步：① 节点执行到 `interrupt(payload)` → 本次 invoke 立即返回，结果带 `__interrupt__`，图**停在检查点上**（payload 成为检查点的一部分——人两天后才批，上下文还在）；② 外部做决定，`invoke(Command(resume=value), config)` 恢复；③ 该节点**从头重跑**，interrupt 之前的代码**再执行一遍**；④ 跑到 interrupt() 时直接"返回" resume 的值，代码继续；⑤ 图继续到下一节点。两条铁律：**interrupt 之前只能放只读操作**；副作用放 interrupt 之后（最好再下一个节点）+ 幂等账本。resume 的值是**一次性的**：被消费后对已完成 thread 重复 resume 不会重放节点。拒绝是一等结果：resume=False 时结论照常产出并留痕（P2 测试锁定）。

**4. 深入解释**：为什么"重跑"是语义内核不是实现瑕疵——它保证恢复路径与正常路径**共享同一段代码**（没有两套逻辑要维护）。三个区分：interrupt 与 sleep 等审批（sleep 占着线程、进程死了全丢；interrupt 把控制权交还，状态在检查点上，进程可释放重启换机器）；interrupt 与"向模型追问"（流程控制 vs 对话——判据：没人回应流程是否永远走不下去）；interrupt 与异常（返回值带 `__interrupt__` 结构，不是抛给调用方）。四种审批形态同一个原语：单票单审/会签（单节点顺序多次 interrupt，各自独立检查点）/或签（interrupt 前查已有批复——只读段，重跑安全）/升级审批（条件边分级）。超时升级 LangGraph 不管——外部定时任务查 `get_state().interrupts` 催办或自动拒绝。

**5. 工程案例**：见 part08 ch48——EX-48-01（人工审批）、EX-48-02（副作用幂等：实验 A 的"执行两次"翻车现场）；P2 的 approval 节点（只读段→interrupt→恢复后执行+账本）与 resume_demo 三段演示（进程内拒绝/跨进程批准/幂等重放）；审批平台字段映射表（thread_id=业务键、payload=申请单、resume 值=审批结果+操作者——resume 必须带操作者身份，审计才能回答"谁批的"）。

**6. 追问与回答边界**：
- 追问 1：恢复时报"没有匹配的 interrupt"？——要点：thread 已消费过该中断或 thread_id 写错；先 `get_state` 看 `next` 与 `interrupts` 再谈恢复。
- 追问 2：节点里有 HTTP 调用怎么办？——要点：读写拆开——重跑段只读（拼上下文），写动作放 interrupt 后过幂等键；不可幂等的（发短信）账本先行（先占 action_key 再发送）。
- 边界：`__interrupt__` 返回结构、多中断并存等细节以所用版本官方文档为准；本书实测基于 langgraph 1.2.16。

### 题 6-4 [模拟题] 恢复后副作用会不会执行两次？怎么保证"恰好一次"？

**1. 问题与考查点**：幂等设计的层次（纪律/账本/审计）——把分布式系统的老问题接到新框架上，考的是迁移能力而不是框架知识。

**2. 常见错误回答**："LangGraph 有事务保证。"——没有；或"我把执行放在 interrupt 后面就安全了"——只挡住了"重跑"，挡不住"执行成功但检查点未落"的崩溃窗口（进程在两者之间挂掉，恢复重放照样再执行一次）。

**3. 简洁合格回答**：三层防线：① **纪律层**——副作用只放在 interrupt 之后（重跑不触碰）；② **账本层**——副作用带唯一 action_key，执行前先查账本（命中即 `already_done` 跳过），执行后记账——进程崩溃在"已执行未提交检查点"窗口时，重放命中账本不重复执行；③ **审计层**——每次副作用对应一条人工决策（审计 `approval.*` 事件）+ 一条账本记录，可对账。语义上的诚实表述：这是 **at-most-once 生效**（at-least-once 执行+幂等去重），不是分布式意义的"恰好一次"。Java 对照：这就是幂等消费的唯一业务键+Saga 参与者去重表——经验直接平移。

**4. 深入解释**：账本的键设计：action_key 要含业务维度与轮次（P2 的 `restart_service:payment-service:incident-payment-outage`——动作:目标:事件单），唯一索引兜底并发。RetryPolicy 重试期间节点整体重入——重试也放大副作用，所以**重试原则上只给只读节点**（P2 的只读取证查询是天然候选）。恢复调用的输入语义：恢复 invoke 只传增量或 None——传"完整历史"会把旧消息再追加一遍（消息翻倍，ch47.9 的调试题）。

**5. 工程案例**：P2 的 actions_ledger.jsonl 与 `already_done` 状态；测试 `test_replayed_resume_does_not_repeat_side_effect`（重放命中账本不重复执行）与 `test_resume_state_consistent_with_prior_snapshot`（恢复不破坏事实）；ch48.7③ 的修复顺序（先把副作用挪到 interrupt 之后，再加账本——无法挪动的遗留副作用至少要有 action_key 去重）。

**6. 追问与回答边界**：
- 追问 1：不可幂等的副作用（发短信）怎么办？——要点：账本先行——先占 action_key 再发送；发送失败标记待补偿而不是盲目重发。
- 追问 2：账本和检查点要同一个存储吗？——要点：不必——账本是业务留痕（JSONL/表），检查点是执行机制；但对账要用同一个 action_key 字符串。
- 边界：多副本下账本去重键要进唯一索引；本书教学实现为单文件，未做并发压测（如实声明）。

### 题 6-5 [模拟题] checkpointer 和"把对话历史存数据库"有什么区别？thread_id 怎么设计？

**1. 问题与考查点**：持久化模型的本质（完整执行状态 vs 消息列表）+ thread_id 命名纪律——后者是生产事故高发区。

**2. 常见错误回答**："就是把 messages 存起来，下次拼上。"——那是历史管理的退化用法；checkpointer 存的是**图的完整执行状态**（中间字段、下一步是谁、待决中断信息），因此能精确恢复到任意超步——历史存库只是它的一种退化形态。thread_id 用随机 UUID 也是常见错误——出事时对不上业务。

**3. 简洁合格回答**：checkpointer 在**每个超步之后**自动快照整图状态，thread_id 是会话主键；查询接口 `get_state` 看四个字段——`next`（停在谁/完没完：`()`=完成、`('approval',)`=停在审批）、`values`（状态事实）、`interrupts`（待决事项）、`metadata`（步数与时间戳）；`get_state_history` 翻完整轨迹；历史快照支持重放（时间旅行）。thread_id 命名三选一并写进团队约定：业务单据号（对得上账，P2 的 incident-XXX）、`user_id:session_id`（客服隔离）、UUID（仅当流程与业务实体无对应）；反模式：用户级 ID 让多轮业务共享一个 thread——历史串台。存储选型：InMemorySaver（进程内）→ SqliteSaver（单机/演示，**单写者模型**不是多副本方案）→ PostgresSaver（多副本共享检查点库，任何副本可接手任意 thread）。

**4. 深入解释**：恢复前的健康检查"三看"（get_state 看 next/values/metadata 再动手——P2 resume_demo 进程 2 的标准动作）。检查点**不是审计日志**——它是执行机制不是合规记录，审计另建（P2 的 JSONL 审计）。快照含敏感业务状态→存储权限按敏感数据管理（Postgres 账号/SQLite 文件权限与业务主库同级）。schema 演进纪律：加字段可以、删字段慎（老 thread 恢复时报键缺失）、语义只追加式变更、schema_version 打标。性能账：成本大头是状态体积——先瘦身状态再谈优化（控制字段比关快照有效）。

**5. 工程案例**：见 part08 ch47——EX-47-01（InMemory+thread 隔离，两轮 6 个检查点）、EX-47-02（SqliteSaver 两个独立 with 块模拟两进程接力）、EX-47-03（时间旅行重放/分叉）；P2 用 incident_id 作 thread_id（README 第 4 节第 5 条）；SqliteSaver 依赖 langgraph-checkpoint-sqlite（本书实测 3.1.2）。

**6. 追问与回答边界**：
- 追问 1：每步都写快照，慢吗？——要点：内存微秒级/本地一次写；状态瘦身优先于关快照；序列化可自定义。
- 追问 2：时间旅行在生产有什么正经用途？——要点：修复类（答错那轮换输入重跑）、排障类（事故现场检查点重放定位）、测试类（从 interrupt 检查点重放验证账本幂等——P2 就这么测）。
- 边界：PostgresSaver 的部署形态、官方 saver 的 TTL/清理接口以官方文档为准；本书只实测了 InMemory 与 Sqlite。

### 题 6-6 [模拟题] LangGraph 里的工具调用循环怎么搭？模型"刷工具"怎么防？

**1. 问题与考查点**：双节点结构与三层防护——同时考"模型决定/程序执行"的分离意识与测试方法。

**2. 常见错误回答**："写个 while True 调模型直到它说完成。"——终止依赖模型**自我声明**，模型抽风就是死循环+账单失控（ch42 开头的真实事故叙事：同参数重复调用 20+ 次）；或者不给 ToolMessage 带 tool_call_id（模型读到错位上下文）。

**3. 简洁合格回答**：标准双节点：agent 节点（调模型，AIMessage 可能带 tool_calls）→ 条件边（有 tool_calls 去 tools、没有去 END）→ tools 节点（ToolNode 或白名单手工执行，ToolMessage 按 tool_call_id 配对）→ 回边到 agent。防刷三层：① **recursion_limit 硬保险丝**（默认 25）；② **业务层轮次计数**——tool_rounds 自增 reducer，达到上限提前收尾并返回"已查到的部分结果"+打标；③ **工具侧限流**（幂等键与退避同样适用于工具执行）。工具失败处理与题 5-4 同源：预期内失败转模型可读文案，或"错误即数据"（捕获写状态+条件边降级——异常也是证据）。

**4. 深入解释**：模型节点与工具节点分离的测试红利——脚本化 MockLLM（工厂闭包注入）驱动循环，`llm.calls` 断言"模型收到了什么"（调用次数与消息快照）；配合 `stream_mode="updates"` 看"图执行到哪"——**模型视角+图视角**双时间线，能回答工具循环排障三大问题：模型没调对工具？工具没返回对结果？循环没按预期收敛？ToolNode 的 `handle_tool_errors` 参数可把异常转文本回传，但生产更推荐错误即数据（P2 的 `tool_error` 证据项直接参与"证据不足"结论）。

**5. 工程案例**：见 part08 ch46——EX-46-01（两轮工具循环：消息序列 6 条、call_001/call_002 配对，Mock 脚本驱动）；ch42 的 create_agent 是同一循环的框架版；P2 **故意不用 ToolNode**——取证计划要"先落 plan、审查后执行"（README 第 4 节第 4 条），这是"控制流定制"的对照样本（与题 5-5 呼应）。

**6. 追问与回答边界**：
- 追问 1：ToolMessage 丢了 tool_call_id 会怎样？——要点：一轮可以并行多个工具调用，id 是模型把结果对回请求的唯一依据；错配让模型读到错位上下文——agent 输出错乱的经典来源。
- 追问 2：达到轮次上限时怎么向用户表达？——要点："已查到 X，Y 因轮次上限未完成"——把上限写进结论而不是静默截断；打满上限的 thread 进告警名单。
- 边界：并行工具调用的开关参数名随 SDK 版本与厂商而异，以所用 SDK 文档为准。

### 题 6-7 [模拟题] LangGraph 的并行是真并行吗？并行分支写同一字段会怎样？

**1. 问题与考查点**：超步（Pregel）模型与 reducer 的配合——区分"并发调度"与"并行执行"，以及归并冲突的机制与修法。

**2. 常见错误回答**："当然是多线程并行。"——图默认在同一事件循环里按超步调度；或"并行分支各自覆盖，最后写的赢"——这正是 `InvalidUpdateError` 的来源（无 reducer 字段一超步只能收一份更新）。

**3. 简洁合格回答**：图按 **Pregel 超步**推进：同一超步的分支**并发调度**（IO 密集型节点天然并发；CPU 密集的真并行要在节点内部用线程/进程做——题 1-1/2-1 的选型结论在这里继续生效），图的职责是编排与归并。并行分支写同一个**无 reducer** 字段 → `InvalidUpdateError: Can receive only one value per step`；解决：给字段声明追加/求和类 reducer（归并规则由你定义），或把写入错开超步。静态并行（多边同发）适合份数编译期已知；份数运行时才定用 **Send** 扇出（Map 节点收到的是单份 arg 而非整图状态；combine 必须只从 Map 有入边，靠超步屏障等到所有份到齐）。

**4. 深入解释**：一路失败怎么办——默认异常冒泡终止整图；要"部分成功"语义就在分支节点捕获**预期内**异常写错误标记（错误即数据），汇总节点按标记区分处理——P2 的 `tool_error` 证据即此模式。子图封装的判据：被多张图复用且有自己的内部状态才值得子图化（子图可独立测试/编译/加检查点）；"把节点函数抽成模块"只是代码组织不是子图。归并的确定性：超步内写入顺序无关紧要——带 reducer 的字段归并结果确定（求和/追加满足结合律）。

**5. 工程案例**：见 part08 ch49——EX-49-01（并行归并与 InvalidUpdateError 的修复现场）、EX-49-02（子图）；P2 扩展方向的三路并行取证（error_events/service_status/dependency_map 三路 Send + reducer 归并，README 第 12 节）。

**6. 追问与回答边界**：
- 追问 1：并行节点的写入顺序确定吗？——要点：对带 reducer 的字段，归并结果与到达顺序无关（结合律保证）；对覆盖字段才有"谁后谁赢"。
- 追问 2：怎么压测并行图的吞吐？——要点：瓶颈通常在模型 API（并发限制见题 2-4），图本身开销在快照与调度；先测下游再谈图。
- 边界：超步调度的线程模型细节以官方文档为准；本书未做并发基准测试（如实声明）。

### 题 6-8 [模拟题] LangGraph 应用怎么测试？"图没法测"你怎么反驳？

**1. 问题与考查点**：测试策略分层——"写过生产图"的照妖镜；能否给出四层地图与恢复语义的可信测法。

**2. 常见错误回答**："图是框架跑的，测不了。"——图的每层都可测；或只写一个"跑通就行"的冒烟——没有分层，失败定位靠猜；或测试间共享 InMemorySaver/审计文件（互相污染，时绿时红）。

**3. 简洁合格回答**：四层测试地图：① **节点直调**——节点是 `(state) -> dict` 纯函数，绕过图直接调，最快、覆盖业务分支；② **Mock 注入整图**——模型节点用工厂闭包创建（`make_agent_node(llm)`），测试注入脚本化 MockLLM：脚本逐条返回预置回答，**游标耗尽抛错绝不编造**（模型行为超出剧本会暴露而不是被洗白）；③ **快照断言**——`get_state` 断言 next/values/metadata/interrupts；含 interrupt 的图两段式：先断言 `__interrupt__` 暂停点，再 `Command(resume=...)` 断言终点；④ **失败路径**——`pytest.raises(GraphRecursionError/KeyError/RuntimeError 脚本耗尽)`。外加**框架契约测试**（锁 RetryPolicy 默认值、关键报错文案——升级版本先红）。恢复语义测试三步：断言暂停点（next+interrupts 载荷）→ 恢复后**逐字段对比**中断前后快照的事实字段（假设/告警不变）→ 时间旅行回到中断检查点重放，验证账本命中不重复执行。

**4. 深入解释**：Mock 脚本即"模型行为剧本"——测试读起来像剧本（第 1 轮要查订单→第 2 轮要查政策→第 3 轮总结），非模型同事也能 review；一个测试只回答一个问题（"正常路径+审批+幂等"分三个测试）；fixture 隔离（tmp_path+每测试新建 saver+审计目录）。"怎么测模型乱来"两问两答：控制流层用 Mock 模拟乱来剧本，验证防线真实生效（白名单拒绝/证据不足拒答）；模型层用评估集量化发生率——两层合起来回答"乱来了会怎样 + 多常发生"。CI 策略：节点+整图全量秒级；Prompt 回归与控制流回归分 job；真模型评估夜间跑（有成本）。

**5. 工程案例**：见 part08 ch51 EX-51-01（四种姿势全 PASS）与 测试/test_ch51.py；P2 的 14 个测试是四层地图的工程化样本（单节点白名单×2+只读+工具幂等 / 整图正常与三类失败 / 快照恢复一致与 thread 隔离 / recursion_limit+人工拒绝+重放幂等+审计完备）；`test_resume_state_consistent_with_prior_snapshot` 的逐字段对比是"恢复不破坏事实"的标准测法。

**6. 追问与回答边界**：
- 追问 1：快照断言锁多细？——要点：锁 next/values 关键字段与 metadata["step"] 量级，别锁完整轨迹的每一步（step 数随实现浮动）。
- 追问 2：真模型要不要进 CI？——要点：PR 只跑 Mock（秒级、零成本）；夜间跑评估集（golden set 断言规则化、不断言全文）。
- 边界：get_state_history 的轨迹断言粒度、契约测试覆盖哪些报错文案，按团队需要裁剪；本书给的是 1.2.16 实测样本。
