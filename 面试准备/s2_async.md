## 12.2 专题二：异步编程与服务性能

> 对应正文：part03（ch13~ch14、ch15、ch17、ch19、ch20）。这一专题的高频误区是"asyncio=更快"，合格回答的锚点永远是：**吞吐来自等待重叠，不是计算加速**。

### 题 2-1 [模拟题] asyncio 是单线程的，为什么能提高吞吐？

**1. 问题与考查点**：考你对并发模型的机制级理解——"单线程为什么快"是区分"用过 asyncio"与"理解 asyncio"的分水岭。

**2. 常见错误回答**："asyncio 是异步的，所以比同步快。"——没说清"快"的是吞吐还是延迟、快在哪个阶段；CPU 密集任务在 asyncio 下毫无收益这一点通常也答不出。

**3. 简洁合格回答**：吞吐提升来自**等待重叠**：一个协程在 `await` 处等 IO（网络/磁盘）时，事件循环调度其他协程运行，几十个"等模型 API 响应"的请求共享一个线程。它不加速计算——CPU 密集任务在 asyncio 下毫无收益（要进程池）。正确表述是"IO 密集、高并发、单机"场景的吞吐方案。

**4. 深入解释**：事件循环维护就绪回调队列，`await` 把控制权交回循环并挂起当前协程，IO 完成后回调恢复协程——本质是"用户态调度的状态机"，对比线程：省掉内核线程切换与每线程栈内存，也省掉大量锁（单线程内无抢占）。代价是"纪律"：任何同步阻塞（`time.sleep`、同步 HTTP、重计算）都会卡住**所有**协程（见题 2-2）。与 Java 对照：心智上接近虚拟线程/CompletableFuture 编排，但 asyncio 的"协作式调度"意味着阻塞点必须显式 `await`——好处是切换点可见，坏处是漏写 await 或混入阻塞库就是事故。

**5. 工程案例**：见 part03 ch13——EX-13-02（time.sleep vs asyncio.sleep 的耗时对照实验）、EX-13-08（并发抓取：N 个请求总耗时 ≈ 最慢一个而非 N 倍）。AI 服务的主路径全是"等模型 API"（秒级网络 IO），这正是 asyncio 的最佳场景——P1 的 SSE 问答与 P2 的图编排（异步模式）都建立在这个地基上（见 part03 第三部分小结的能力表）。

**6. 追问与回答边界**：
- 追问 1：CPU 密集怎么办？——要点：`to_thread`/进程池/拆独立服务，事件循环只做编排。
- 追问 2：事件循环底层是什么？——要点：selector/epoll 就绪通知；性能调优（uvloop 等）不在本书范围，答"知道分层即可"。
- 边界：TaskGroup 取消传播的细节顺序、uvloop 数据，本书未实测——答"以官方文档与实测为准"。

### 题 2-2 [模拟题] 在 async 函数里调用了 time.sleep(5) 会发生什么？怎么发现和避免？

**1. 问题与考查点**：考"sync 阻塞对事件循环的伤害"——asyncio 事故榜第一名，也是"知道语法"与"能上线"的差距。

**2. 常见错误回答**："会阻塞这个请求 5 秒。"——错在范围：阻塞的不是这一个请求，是**整个事件循环上的所有请求**；而且这种阻塞在单实例压测里常被误判为"下游慢"。

**3. 简洁合格回答**：`time.sleep(5)` 是同步阻塞，它把整个线程（事件循环）卡住 5 秒——期间所有协程都无法调度，服务表现为"全实例请求集体变慢"。避免：等待用 `asyncio.sleep`；阻塞调用（同步 SDK、重计算）用 `asyncio.to_thread` 或线程/进程池隔离；发现靠压测下的延迟尖刺 + 日志里的调度延迟。

**4. 深入解释**：协作式调度没有抢占——协程不 `await`，循环就没有交接点。判别清单：① 纯等待 → 换异步原语（`asyncio.sleep`/`asyncio.wait_for`）；② 只有同步实现的库（某向量库 SDK、某加密库）→ `to_thread` 包一层（它是线程池上的 `run_in_executor` 语法糖）；③ CPU 密集 → 进程池，因为线程对纯 Python 计算无并行（GIL，题 1-1）。Java 对照：这相当于"在 Tomcat 的请求线程里写死循环"——但 Tomcat 多线程下伤害半径只有一个请求，asyncio 单线程下是全部请求，**半径差异**是回答的加分点。

**5. 工程案例**：见 part03 ch13.1 引入实验与 EX-13-02：同样"睡 3 次 × 1 秒"，串行 time.sleep 约 3s、asyncio.gather + asyncio.sleep 约 1s；把 asyncio.sleep 误写成 time.sleep 的版本退回 3s——三组数字在同一脚本里可复现。ch13.7 的异步上下文管理器（EX-13-07）示范了"异步资源也要异步释放"的同族纪律。

**6. 追问与回答边界**：
- 追问 1：怎么系统性发现阻塞点？——要点：压测看 P99 尖刺与并发度不成比例；日志打"请求间隔调度延迟"；code review 清单专查同步库。
- 追问 2：`to_thread` 有什么坑？——要点：线程池有上限（默认随版本变化，以官方文档为准）、任务函数要线程安全、contextvars 需要显式传递。
- 边界：默认线程池容量数字随 Python 版本变化，别背；以所用版本 `asyncio` 文档为准。

### 题 2-3 [模拟题] gather、wait、TaskGroup 三个怎么选？

**1. 问题与考查点**：考并发原语的**异常语义**差异——多数人只会"跑并发"，说不清"一个失败后其他任务怎么样"。

**2. 常见错误回答**："都是并发跑，用哪个都一样。"——异常传播、取消行为、返回结构完全不同，生产事故常出在"默认以为一样"。

**3. 简洁合格回答**：`gather(*aws)` 一次并发全部，默认**一个异常不取消兄弟任务**（异常在 await 时抛出，其余继续跑完）；`gather(..., return_exceptions=True)` 把异常当结果收集，适合"部分失败可接受"的批量；`wait` 给超时/轮询级别的精细控制（返回 done/pending 集合）；TaskGroup（3.11+）是结构化并发：**任一异常取消全部兄弟并聚合成 ExceptionGroup**，离开 with 块时保证没有任务泄漏。新代码要严格语义用 TaskGroup；批量部分失败场景用 `gather(return_exceptions=True)`。

**4. 深入解释**：决策表——① "要么全成要么全败"：TaskGroup（异常时取消兄弟、聚合上报）；② "多路独立查询，谁成用谁"：gather + return_exceptions；③ "给整批一个总超时，超时的放弃、没超时的要结果"：wait + timeout；④ "扇出后逐个消费"：`as_completed`。注意取消语义：`task.cancel()` 后协程若在 await 点收到 CancelledError 且吞掉不 re-raise，取消会被"吃掉"——约定是捕获后必须 re-raise（见 part03 13.11 追问 2）。

**5. 工程案例**：见 part03 ch13——EX-13-03（create_task + gather）、EX-13-05（异常传播实测）、EX-13-04（wait_for 超时取消）。真实选型：P1 的"批量 embedding 入库"若换真实模型 API 就是 gather(return_exceptions=True) 场景——单条文档失败不该拖垮整批（见 综合项目/p1 README 第 7 节"入库耗时主要在 embedding 调用"）；P2 的并行取证思路（三路只读查询）同理（见 综合项目/p2 README 第 12 节扩展方向 3）。

**6. 追问与回答边界**：
- 追问 1：gather 里某个任务超时怎么处理？——要点：外层 `wait_for(gather(...), timeout)` 会取消整批；要"逐个超时"给每个协程包 wait_for 或用 wait 的 timeout 参数。
- 追问 2：TaskGroup 抛的 ExceptionGroup 怎么接？——要点：3.11 的 `except*` 语法；细节以官方文档为准。
- 边界：TaskGroup 取消传播的聚合顺序等细节本书未展开实测，答"以官方文档为准"。

### 题 2-4 [模拟题] 为什么调模型 API 要加 Semaphore？加多少怎么定？

**1. 问题与考查点**：考并发限制（并发数 ≠ 请求数）与背压意识——"无脑 gather 1000 个模型调用"是新手最贵的错误。

**2. 常见错误回答**："asyncio 本身就是并发的，直接 gather 就行。"——asyncio 调度并发不等于下游能承受；对限流的模型 API 无节制并发会收获大量 429，重试风暴还会把配额打得更碎（对照 part03 15.1 的"重试风暴"事故）。

**3. 简洁合格回答**：Semaphore 把"同时在飞"的请求数限制在 N：`async with sem: await call()`。N 的确定顺序：先看 API 配额（RPM/TPM 与并发上限），再看自己实例数（N_单实例 × 实例数 ≤ 配额），再留余量给重试。它同时是**背压**的实现：超出的协程在信号量上排队，上游自然变慢而不是把下游打挂。

**4. 深入解释**：三层限流位置——① 出口并发（Semaphore，进程内）；② 实例间配额（Redis INCR 固定窗口/令牌桶，跨进程共享，见 part03 ch19.3——INCR 原子性、固定窗口的边界毛刺）；③ 下游自带限流（429 + Retry-After，见专题三题 3-7）。三者是纵深关系，互不替代。Java 对照：Semaphore ≈ Resilience4j 的 Bulkhead/RateLimiter 单机版；Redis 限流 ≈ 分布式 RateLimiter——你在 Java 里学的"单机闸门+分布式闸门"分层完全平移。

**5. 工程案例**：见 part03 ch13 EX-13-06（Semaphore 并发限制实测：10 个任务只有 3 个同时在跑）与 ch19 EX-19-04（Redis 固定窗口限流，接入 ch17 服务）。P1 README 第 7 节明确"入库耗时主要在 embedding 调用（真实模型下是网络 IO，应批量与并发控制）"——生产迁移时第一件事就是给 embedding 批量调用套 Semaphore。

**6. 追问与回答边界**：
- 追问 1：Semaphore 和队列有什么区别？——要点：Semaphore 限"同时在飞"，有界队列限"排队上限"（超出即拒绝），背压设计两者常配合。
- 追问 2：并发数设错了怎么发现？——要点：429 率上升 / 尾延迟上升，配合每个请求的 usage 记录（专题三）复盘。
- 边界：各厂商配额模型（RPM/TPM/并发）不同且随合同变化，答"以所用厂商文档为准"。

### 题 2-5 [模拟题] FastAPI/uvicorn 的 worker 是什么模型？多开 worker 有什么坑？

**1. 问题与考查点**：考部署形态反推架构决策的能力——uvicorn 的 `--workers` 是**进程**模型，这一句话直接判掉一批背题的人。

**2. 常见错误回答**："worker 就是线程池里的线程，开多点并发高。"——错。uvicorn worker 是 OS 进程，进程间零共享；Java 里"Tomcat 线程池"的直觉在这里失效。

**3. 简洁合格回答**：uvicorn 默认单进程跑事件循环；`--workers N` 起一个管理进程 + N 个 worker **进程**，每个进程自带 GIL 与独立内存。作用：① 多核利用（绕开 GIL 的进程级方案）；② 隔离性。坑：进程内存里的限流计数器、缓存、单例状态全部失真——2 个 worker 让"60 次/分钟"变 120 次/分钟；跨进程状态必须外置（Redis）。worker 数参考 1~2×vCPU，最终以压测为准。

**4. 深入解释**：为什么进程而不是线程——Python 有 GIL，单进程 asyncio 吃满 IO 并发但 CPU 只用一个核；多进程每进程独立 GIL 才有真并行（ch14）。对比 Java：Tomcat 单进程多线程（JVM 线程真并行），Spring 单例的进程内缓存在多实例前同样要外置——**"水平扩展后状态必须外置"是通用纪律，只是 Python 在单机内就提前触发了**。滚动发布配套：优雅停机 + 就绪探针 + 客户端重试兜底（见 part03 20.11 追问 2）。

**5. 工程案例**：见 part03——ch17 面试追问 3 与 ch19.1 的"多实例部署后限流阈值翻倍"事故（计数器最初在进程内存），修复是 Redis INCR（EX-19-04）；ch20 EX-20-02 用 `--help` 实测 uvicorn 生产参数存在性（`--workers`/`--timeout-graceful-shutdown` 等）。ch20 的 Dockerfile 因沙箱无 Docker 仅完成 11 项静态检查——引用时如实说明验证边界。

**6. 追问与回答边界**：
- 追问 1：SSE 长连接和多 worker 什么关系？——要点：SSE 连接固定在某个 worker 进程上，worker 数影响单机可维持连接面；会话亲和不是必须（每个 SSE 自包含）。
- 追问 2：单 worker 想利用多核又想要事件循环怎么办？——要点：多 worker 各跑一个事件循环；或多实例容器，编排层扩容。
- 边界：多 worker 优雅停机行为未做长时压测（part03 run log 已声明），worker 数经验区间标注"工程经验非实测结论"。

### 题 2-6 [模拟题] 重试怎么设计？非幂等操作能重试吗？

**1. 问题与考查点**：考超时/重试/幂等三件套的整体观——重试不是孤立参数，是"可重试错误集合 × 退避策略 × 幂等保障"的组合决策。

**2. 常见错误回答**："失败就重试，加个次数限制。"——三个隐患说不出：什么错误才可重试、退避怎么排、非幂等操作重试的资损风险。

**3. 简洁合格回答**：三前提缺一不重试：**请求可重发（幂等或带幂等键）、下游能承受、调用方等得起**。可重试集合：传输层错误与 502/503/504（429 特殊：按 Retry-After 退避，见题 3-7）；4xx 参数类错误一律不重试。退避：指数退避 + 抖动，第 n 次等待上限 `min(max_delay, base×2^(n-1))`，抖动防"同一毫秒集体重试"。非幂等操作（创建工单、扣款）不能裸重试——带 Idempotency-Key，服务端以键记账、重复回放首次响应。

**4. 深入解释**：超时三件套先行（connect/read/pool 各自限时，read 是"两次数据到达之间"不是总时长）——没有超时的重试是"无限期挂住"。参数定法：总重试预算=调用方可容忍延迟；客户端超时 > 下游 P99.9 且 < 自身 SLA；参数写配置不写死。幂等键服务端实现：键为账本主键，首执记账、重复回放，键冲突但请求体指纹不同要拒绝（409/422）——本书 stub 未实现指纹校验，如实说这是生产必补项。Java 对照：Resilience4j Retry + 幂等消费的唯一业务键，思想完全同构。

**5. 工程案例**：见 part03 ch15——15.1 的三连事故（合成案例）：P99 从 2s 飙 60s（超时语义错）→ 非幂等重试创建三次工单 → 重试风暴打挂刚恢复的下游；EX-15-02 退避+抖动、EX-15-03 幂等键 stub。SDK 层：openai 3.35.1 内建重试默认 2 次、只对连接错误/408/429/部分 5xx 生效（见 part04 ch24.3，签名与默认值实测核实）——应用层再加重试时先算两层叠加的总预算。

**6. 追问与回答边界**：
- 追问 1：重试放在客户端还是网关？——要点：分层各管各的（SDK 层、应用层、网关层），叠放时明确每层预算，宁可少一层。
- 追问 2：超时后请求到底成没成功？——要点：你不知道——这正是幂等键存在的理由；对账以服务端为准。
- 边界：各厂商 429 的 Retry-After 格式（秒数/HTTP 日期）与语义差异以厂商文档为准；连接池在多 worker 下是每进程一份，池参数按进程视角算（part03 run log 未做压测验证，如实声明）。

### 题 2-7 [模拟题] 下游变慢、请求开始堆积，你的服务怎么自保？

**1. 问题与考查点**：考背压（backpressure）的完整设计——从"单点限流"到"有界资源+降级"的系统观，常见于"你的服务被打挂过吗"这类开放题。

**2. 常见错误回答**："加机器。"——下游慢时加机器只是让更多请求同时挂在那；缺"拒绝谁、保住谁"的策略层。

**3. 简洁合格回答**：四道闸门从外到内：① 入口限流（超出配额直接 429，别让请求进来排队）；② 有界并发（Semaphore 限同时在飞的上游调用数）；③ 有界等待（排队超时：等待超过预算直接失败，用户得到快速错误而非 60s 白屏）；④ 降级（模型不可用时回退缓存答案/兜底话术，只读功能优先保）。原则：**宁可快速拒绝，不要无限堆积**——堆积的每个请求都占着连接、内存和用户耐心。

**4. 深入解释**：背压的本质是"让过载信号向上游传播"：无界队列把过载藏起来（内存涨、延迟涨、最后 OOM），有界资源让上游立刻看到失败并采取行动。实现载体：FastAPI 层用 Depends 挂限流（ch17），计数放 Redis 跨进程共享（ch19 INCR 原子性 + 固定窗口毛刺的诚实说明）；等待超时用 `asyncio.wait_for`；失效策略二选一——限流组件挂了"放行但告警"（失效开放）还是"拒绝"（失效关闭），按业务风险定。Java 对照：Resilience4j 的 Bulkhead+RateLimiter+CircuitBreaker 组合，思想一一对应。

**5. 工程案例**：见 part03 ch17 综合演练（订单查询+风控限流服务，含限流 429 的测试断言）与 ch19 EX-19-04；P1 的 SSE 路径在拒绝时返回 `meta(status=refused)+done` 而非挂起（见 综合项目/p1 README 第 5 节失败路径），"快速失败"从接口语义上就有保障。项目二的"证据不足直接 UNKNOWN 拒答"是同一原则在结论层的体现：没有足够证据就快速给出明确的不确定（见 综合项目/p2 README 第 7 节）。

**6. 追问与回答边界**：
- 追问 1：限流阈值怎么定？——要点：从下游容量与自身 SLA 倒推，压测校准，写配置可热调。

### 专题二 · 30 分钟自测（模拟口试）

> 用法：同专题一。本专题每题先说"结论"，再给"机制"，最后给"参数从哪来"——顺序错了扣分。

1. **[模拟题] 30 秒讲清 asyncio 的吞吐来自哪里，CPU 密集任务的三条出路。** 评分要点——等待重叠而非计算加速；出路：`asyncio.to_thread`/进程池/拆独立服务；能引 EX-13-02 的三组耗时对照加分。
2. **[模拟题] `time.sleep(5)` 写进 async 函数，伤害半径多大？和 Tomcat 里的同类错误比呢？** 评分要点——卡住整个事件循环（不是单个请求）；发现靠压测 P99 尖刺与日志调度延迟；Java 对照：Tomcat 多线程下半径是一个请求、asyncio 单线程下是全部请求。
3. **[模拟题] 三个场景配对三个原语：要么全成全败 / 部分失败可接受 / 整批总超时。** 评分要点——TaskGroup（取消兄弟+ExceptionGroup）/gather(return_exceptions=True)/wait 的 timeout；说出"取消必须 re-raise，否则被吃掉"加分。
4. **[模拟题] 调模型 API 的 Semaphore 并发数 N 怎么定？它和 Redis 限流各管哪一层？** 评分要点——N 的推导顺序（下游配额→实例数→重试余量）；三层纵深：进程内出口并发/跨实例配额/下游自带限流（429+Retry-After）；引 EX-13-06 与 EX-19-04 加分。
5. **[模拟题] 重试的三前提是什么？openai SDK 内建重试与你应用层重试叠加，最多发出几次真实请求？** 评分要点——幂等可重发/下游能承受/调用方等得起；SDK 一层 1+2=3 次尝试，应用层 3 次尝试，两层叠加最坏 3×3=9 次真实请求（叠加会自我放大限流）；策略"只留一层并算清总预算"；幂等键服务端"首执记账、重复回放"。
