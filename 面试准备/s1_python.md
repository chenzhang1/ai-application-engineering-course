## 12.1 专题一：Python 基础与工程化

> 对应正文：part02a（ch04~ch08）、part02b（ch09~ch12）。这一专题考的是"Java 经验迁移后是否真正建立了 Python 对象模型"，题面常见、深水区在对象模型与语言规则的一致性。

### 题 1-1 [模拟题] 讲讲 GIL。Python 的多线程还有用吗？

**1. 问题与考查点**：考你能否按版本事实陈述 GIL，而不是背"GIL 已死/没用"的口号；能否区分 IO 密集与 CPU 密集。

**2. 常见错误回答**："GIL 就是 Python 不能多线程，要并发只能多进程。"——把 CPython 实现细节说成语言宿命，丢掉了 asyncio 与线程池对 IO 任务的价值，也答不出 free-threading 现状。

**3. 简洁合格回答**：GIL（Global Interpreter Lock，全局解释器锁）是 CPython 的互斥锁，保证同一时刻只有一个线程执行 Python 字节码。它只拖累 CPU 密集任务的线程并行；time.sleep、socket、文件 IO 会释放 GIL，所以 IO 密集场景用线程池或 asyncio 依然有效。3.13 起有 free-threading 实验构建，默认构建仍有 GIL，生态兼容在演进——以官方发布说明为准。

**4. 深入解释**：三个层次。① **它锁什么**：字节码执行的互斥，不是"整个解释器里什么都锁"——解释器每约 5ms 会强制当前线程让出 GIL，但"让出≠并行执行"。② **谁会释放它**：sleep、socket 读写、文件 IO 这些等待型操作会释放；numpy/torch 的底层 C 代码执行时也主动释放——这就是"调 numpy 的预处理用多线程有加速"的原因，加速来自 C 扩展而非 Python 字节码并行。③ **版本事实**：3.12 及以前所有正式版本默认带 GIL；3.13 提供 free-threading 实验性构建（非默认，生态适配有限）；本书沙箱（3.14.7）实测 Linux 默认 start method 已是 forkserver——版本相关结论一律标注"以官方发布说明为准"。

**5. 工程案例**：见 part03 ch14 的两个真实实验——EX-14-01：20 个 200ms 的模拟远程调用，单线程约 4s，线程池 10 workers 压到约 0.4s（等待重叠）；EX-14-02：1.2s 的纯 Python CPU 任务，四个线程与单线程同速，换进程池才真加速。AI 服务的典型组合见 14.11 追问：asyncio 作主干（调模型 API），`asyncio.to_thread` 包只有同步 SDK 的组件，常驻进程池包偶发重计算。

**6. 追问与回答边界**：
- 追问 1：free-threading 下单线程性能如何？——要点：实验版有开销，具体数字随版本变化，诚实说"未实测，以官方数据为准"。
- 追问 2：那 CPU 密集在 asyncio 服务里怎么办？——要点：`to_thread`/进程池/独立服务，别让重计算进事件循环（见专题二题 2-2）。
- 边界：free-threading 的生态兼容与性能数据、各平台默认 start method 的演进，回答"以官方发布说明与我实测的版本为准"是加分项；硬背一个具体数字是减分项。

### 题 1-2 [模拟题] 什么是可变默认参数陷阱？为什么语言不干脆禁止？

**1. 问题与考查点**：考对象模型（默认值在 def 时求值一次）与工程防呆意识；"为什么不禁"考你对语言设计一致性的理解。

**2. 常见错误回答**："这是 Python 的 bug，写的时候注意就行。"——说不出机制（`__defaults__`），也给不出系统化防呆手段，更答不出"为什么语言选择不特判"。

**3. 简洁合格回答**：默认参数在 `def` 执行时求值**一次**，存进函数对象的 `__defaults__`，之后所有调用共享同一个对象。默认值是可变对象（list/dict/set）时，一次调用里的原地修改会被下次调用看见。标准修复是 `None` 哨兵 + 函数体内新建；防呆靠 lint 规则（如 ruff 的 B006）。

**4. 深入解释**：语言选择"机制统一透明"而不是"特判可变对象"：默认值求值一次是统一规则，lambda 捕获、装饰器参数都依赖它；`__defaults__` 让行为完全可见可预测（EX-06-01 里直接打印它能看到污染现场）。可变默认值也有正当用法——当"跨调用缓存/固定注册表"用。修复写法 `def f(items: list[str] | None = None)` 体内 `if items is None: items = []`；Pydantic 的 `Field(default_factory=list)` 是同一思想的库化表达（见 part03 ch16.3）。

**5. 工程案例**：见 part02a ch06 EX-06-01：`add_task_bad` 连续调用两次，`r1` 与 `r2` 是同一个对象（`r1 is r2` 为 True），任务跨"请求"堆积——这正是 ch06 引入故事里客服 AI 服务"任务队列跨请求堆积"事故的根因（合成案例）。对照 ch07.1 的"类属性 `members = []` 所有实例共享"，是同一对象模型（名字绑定 + 共享可变对象）的两次投影。

**6. 追问与回答边界**：
- 追问 1：闭包的延迟绑定和它是同一个根因吗？——要点：同属"绑定延迟到调用时"——闭包捕获变量本身，循环里注册 lambda 全拿到最后值（EX-06-04）；修复可用默认参数固化（`lambda c, i=i: ...`）。
- 追问 2：什么场景故意用可变默认值？——要点：跨调用缓存、模块级注册表，但要接受"所有调用者共享"的语义并写注释。
- 边界：lint 规则编号（B006）随 ruff 版本变化，说"如 ruff 的 B006 一类规则"即可，别把编号当恒定事实。

### 题 1-3 [模拟题] 装饰器的原理是什么？和 Java 注解是一回事吗？

**1. 问题与考查点**：考"函数是一等公民→高阶函数→闭包→装饰器"这条推导链是否完整，以及 Spring AOP 经验能否准确对照。

**2. 常见错误回答**："装饰器就是 Java 的注解。"——混淆了元数据与行为：Java 注解本身没有行为，行为来自注解处理器/AOP 代理；Python 装饰器本身就是可执行的高阶函数，装饰发生在 import 时。

**3. 简洁合格回答**：装饰器是"接收函数、返回新函数"的函数，`@deco` 等价于 `f = deco(f)`——用包装后的新函数顶替原名字，装饰发生在定义时且只执行一次。功能上"Java 注解 + AOP 通知 ≈ Python 装饰器"，机制完全不同：一个靠容器代理织入，一个是语言原生的显式包装。

**4. 深入解释**：三层结构——wrapper 通过闭包记住 `func`（ch06 闭包）；`*args/**kwargs` 透传任意签名；带参装饰器再多一层工厂（`@retry(times=3)` 先求值 `retry(times=3)` 得到真装饰器）。`functools.wraps` 把原函数的 `__name__/__doc__/__wrapped__` 等元数据拷回 wrapper——不加的典型事故：按函数名注册的插件路由在装饰后全部变成 `wrapper`，互相覆盖导致请求错路由（见 part02b 10.11 追问 3）。类装饰器（`__init__` 收函数、`__call__` 执行）适合需要跨调用状态的场景。

**5. 工程案例**：见 part02b ch10 三个生产形态装饰器——EX-10-02 计时、EX-10-03 重试（对照 part03 ch15 的指数退避+抖动）、EX-10-04 调用日志。读框架代码也是同一件事：FastAPI 的 `@app.get`、LangChain 的 `@tool`、Pydantic 的 `@field_validator` 都是装饰器在"注册/包装"（见 part02b ch10 章首）。项目二的工具白名单与审计（见 综合项目/p2 审计日志）在思路上就是"切面"的图节点版。

**6. 追问与回答边界**：
- 追问 1：为什么带参数装饰器要三层？——要点：工厂收参数、装饰器收函数、wrapper 收调用参数。
- 追问 2：AOP 能做事务传播，装饰器能吗？——要点：裸装饰器没有框架运行时，需要什么能力就得显式传什么；不要硬说"能等价替代 Spring 事务"。
- 边界：装饰器与 PEP 695/649 等语法演进的关系本书未展开，答"以官方文档为准"。

### 题 1-4 [模拟题] 生成器和直接返回 list 有什么区别？在你的项目里哪里用到了？

**1. 问题与考查点**：考惰性求值省的到底是什么（中间物化 vs 总计算量），以及能否落到流式 LLM 输出这个本书主线上。

**2. 常见错误回答**："生成器省内存，性能更好。"——含糊且不完整：不省总计算量（该算的一个不少），"省内存"省的是**中间全量物化**；也答不出暂停/恢复语义的价值。

**3. 简洁合格回答**：迭代器是协议（`__next__` + `StopIteration`），生成器是"用 yield 自动实现该协议的函数"。与返回 list 相比省两件事：① 中间结果的物化——任一时刻只有一个"在路上的值"，不把全量结果攒进容器；② 首字节延迟——生产一个就能消费一个。流式 LLM 输出、大文件逐块处理、SSE 推送都是天然场景。

**4. 深入解释**：CPython 把生成器函数编译成特殊字节码帧：yield 时帧不销毁，栈与局部变量冻结在生成器对象里，`next()` 时恢复——状态保存在**函数帧**里而不是闭包变量。注意"省内存 ≠ 省计算"：总工作量不变，只是摊开到消费时。消费端提前放弃（break/连接断开）时，生成器被 GC 后帧销毁，后续 token 不再计算——但完整的服务端实现还要配合取消 HTTP 上游连接，只答"break 就行"不完整（见 part02b 9.11 追问 4）。

**5. 工程案例**：见 part02b ch09——EX-09-02 yield 语义、EX-09-03 惰性求值实测（急切方式物化 8.4MB 中间结果 vs 生成器 208 字节量级，3.14.7 实测值）、EX-09-04 LLM 流式输出。项目一的 SSE 路径（见 综合项目/p1 README 第 5 节：`meta` → `delta*` → `done`）服务端就是异步生成器驱动 StreamingResponse（见 part03 ch17.3）。

**6. 追问与回答边界**：
- 追问 1：生成器和迭代器什么区别？——要点：所有生成器都是迭代器，反之不成立；生成器的增量价值是暂停/恢复。
- 追问 2：生成器可以 `return` 值吗？——要点：值进 `StopIteration.value`，`yield from` 可接住；细节以官方语言参考为准。
- 边界：`sys.getsizeof` 具体字节数随版本浮动，引用时说"量级对比"而非精确数字。

### 题 1-5 [模拟题] 深拷贝和浅拷贝的区别？什么时候浅拷贝就够了？

**1. 问题与考查点**：考"名字→对象引用"模型（ch04）是否真正建立——拷贝复制的是"名字贴"还是"对象"。

**2. 常见错误回答**："copy.copy 复制值，copy.deepcopy 复制引用。"——方向说反了；或答不出"浅拷贝之后嵌套对象仍然共享"的具体后果。

**3. 简洁合格回答**：赋值只复制引用（两个名字贴同一对象）；浅拷贝新建外层容器、内层元素仍是共享引用；深拷贝递归复制所有层级（`copy.deepcopy` 自带备忘录机制处理循环引用）。浅拷贝够用的判据：外层要独立增删、内层全是不可变对象或只读。存在嵌套可变结构且要独立修改时必须深拷贝。

**4. 深入解释**：`b = a`、`b = a[:]`、`b = a.copy()`、`b = copy.deepcopy(a)` 四档语义依次增强。判断口诀：**拷贝了几层，取决于拷贝方式；共享了几层，取决于哪一层没有复制**。深拷贝的代价：性能（递归遍历）与语义（所有元素必须可深拷贝）。与 Java 的直觉差：Java 的 `clone()` 与集合拷贝构造同样是浅的，但 Java 里不可变集合（`List.of`）用得多，"共享可变状态"的暴露面小；Python 里嵌套 dict/list 是常态，更要主动想清楚层数。

**5. 工程案例**：见 part02a ch04 EX-04-05（四档拷贝的实测对照）与 EX-04-03（`==` 与 `is`）。项目里的真实风险点：P1 的 chunk 元数据 dict 若多处共享引用，一处改 `department` 全部"变节"——P1 的做法是入库时以不可变意图构造元数据并整体落盘（见 综合项目/p1 README 第 3 节 front-matter 设计），从源头减少"需要深拷贝"的场景。

**6. 追问与回答边界**：
- 追问 1：`deepcopy` 怎么处理循环引用？——要点：备忘录（memo）字典记录"已拷贝对象→新对象"映射，二次遇到直接取。
- 追问 2：frozen dataclass 能替代深拷贝吗？——要点：不可变结构共享引用是安全的，"用不可变替代拷贝"是更好的工程方向（见题 1-6）。
- 边界：deepcopy 对自定义类的行为取决于 `__deepcopy__`/`__copy__`/`__reduce__` 的实现，答到"可通过协议定制"即可，细节以官方 `copy` 模块文档为准。

### 题 1-6 [模拟题] dataclass、Pydantic BaseModel、TypedDict 怎么选？

**1. 问题与考查点**：考三个"结构化数据容器"的定位差异，本质考"运行时校验 vs 静态形状"这条边界（FACTS 术语基线：Pydantic ≠ DTO）。

**2. 常见错误回答**："都能定义字段，随便用。"——或"Pydantic 就是 Python 版 DTO"。漏掉了 Pydantic 的本质是**运行时校验器**：校验是构造行为本身，造不出校验不过的实例。

**3. 简洁合格回答**：内部数据结构、无运行时校验需求 → dataclass（轻、快，`@dataclass` 生成 `__init__/__repr__/__eq__`）；数据来自系统边界（HTTP 请求、配置文件、LLM 输出）需要校验与清晰错误 → Pydantic；只是给"字典形状的数据"声明键值类型、追求零运行时开销（如 LangGraph 的 State）→ TypedDict。一句话：**dataclass 管形状，Pydantic 管门禁，TypedDict 管字典的类型视图**。

**4. 深入解释**：① dataclass 默认可变，`frozen=True` 才不可变——对照 Java record（不可变）要指出这一差异；② Pydantic v2 校验核心是 Rust 实现的 pydantic-core，宽松模式默认做无损转换（"3"→3），`ValidationError.errors()` 给出 `loc/type/msg/input` 的机器可读错误；③ TypedDict 运行时就是普通 dict，静态检查器查键名与值类型，LangGraph 的 `MessagesState` 就是它的典型应用（见 part08 ch44.3）；④ 三者可组合：LangGraph State 用 TypedDict，节点内部业务对象用 dataclass，API 契约用 Pydantic。

**5. 工程案例**：见 part02a ch07 EX-07-04（dataclass 实测）与 7.11 追问 1；part03 ch16（Pydantic 四个 EX：basics/validators/settings/json_schema）；part08 ch44.3（MessagesState）。项目一的服务契约层是 Pydantic（综合项目/p1 `app/schemas.py`，README 第 2 节目录结构），而 LangGraph 编排的项目二状态是 TypedDict + Annotated reducer（综合项目/p2 `triage/state.py`，README 第 4 节第 1 条）——两个项目正好是"边界校验用 Pydantic、图状态用 TypedDict"的对照样本。

**6. 追问与回答边界**：
- 追问 1：为什么定义了 `__eq__` 还要管 `__hash__`？——要点：哈希协议要求"a==b 则 hash 相等"；自定义 `__eq__` 后 Python 把 `__hash__` 置 None（显式不可哈希）防止静默错误。
- 追问 2：Pydantic 校验失败怎么兜底？——要点：分层——schema 简化、错误喂回重试（一次为限）、降级分支（见专题三题 3-5）。
- 边界：dataclass 的 `slots=True/kw_only=True`（3.10+）语义细节、Pydantic 各小版本对可变默认值的处理差异，以各自官方文档为准。

### 题 1-7 [模拟题] Python 的类型注解运行时会强制吗？和 Pydantic 什么关系？

**1. 问题与考查点**：考"静态检查与运行时校验"的分工——这是 Java 工程师最容易带偏的模型（Java 注解 `@NotNull` 也常要靠框架，但编译期类型检查是硬的）。

**2. 常见错误回答**："写了 `def f(x: int)`，传字符串就会报错。"——不会。注解只是元数据，存进 `__annotations__`，解释器默认完全不校验。

**3. 简洁合格回答**：注解默认不强制，它是给两类工具读的：mypy/pyright 这类**静态检查器**在不运行代码时按注解做数据流检查；Pydantic/FastAPI 在**运行时**读注解做校验与转换。静态保证靠检查器（CI 里跑），运行时保证靠 Pydantic——两者互补不互替。这句话是类型系统的全部要点。

**4. 深入解释**：现代写法（3.10+）：`list[int]` 而非 `List[int]`、`str | None` 而非 `Optional[str]`、`TypedDict`/`Protocol`/`Literal`/`Annotated` 各司其职（对照表见 part02b ch11.3）。`from __future__ import annotations` 让注解惰性化（变字符串），EX-11-04 输出里 `'int'` 带引号是实证。`Protocol` 是结构化子类型：不看继承声明，有方法即满足，运行时默认不校验（`@runtime_checkable` 只查方法存在性）。工程纪律：注解覆盖率进 CI，配合 Pydantic 管"边界"，内部函数靠 mypy 防"手滑"。

**5. 工程案例**：见 part02b ch11——EX-11-03 现代类型写法、EX-11-04 注解的运行时形态。全书代码按"类型注解全量"标准编写（见 编辑规范/STYLE_GUIDE.md C 节），项目二的 `TriageState`（TypedDict + `Annotated[list, merge_lists]`）是"注解承载框架语义"的例子：reducer 就写在 `Annotated` 里，LangGraph 读它决定归并规则（见 综合项目/p2 README 第 4 节第 1 条）。

**6. 追问与回答边界**：
- 追问 1：mypy 和 Pydantic 会"打架"吗？——要点：不会，一个看源码一个看数据；要小心的是 Pydantic 的宽松转换让"运行时通过"的数据与静态声明的类型不完全一致，严格场景配 `StrictInt` 等。

### 题 1-8 [模拟题] 讲讲异常链和上下文管理器。`__exit__` 返回 True 会怎样？

**1. 问题与考查点**：考"无 checked exception 的世界里怎么保持可排障性"与资源清理纪律——两问常连着问，因为都关于"异常路径下的完整性"。

**2. 常见错误回答**："catch 里抛新异常就行。"——丢失原始异常（`raise RuntimeError("调用失败")` 把 429 的哪个模型、重试预算全丢了）；或"`__exit__` 返回 True 是清理用的"。——返回 True 的语义是**吞掉 with 块内的异常**。

**3. 简洁合格回答**：异常链：except 块内再抛新异常时，`raise NewError(...) from exc` 把原异常挂到 `__cause__`（报错文案 "direct cause"），堆栈完整可回溯；裸 `raise X` 只有隐式 `__context__`（"During handling..."）；`from None` 抑制内部细节（对外接口防泄露用，代价是丢线索）。上下文管理器：`with` 保证 `__exit__` 执行；`__exit__` 返回 True 会**吞掉**块内异常——合理场景只有 `contextlib.suppress`、事务回滚后不再上抛这类"明确要吞"的地方，业务代码默认返回 False。

**4. 深入解释**：Python 没有 checked exception，所有异常 unchecked——补偿设计是四件套：业务异常分层与基类统一捕获、异常处理器集中映射错误码（FastAPI `exception_handler`，见 part03 ch17.3）、关键函数文档声明可能抛什么、监控按异常类型统计。`with` 比 Java try-with-resources 强的地方：`__exit__` 参与异常决策（返回 True 吞异常），且 `@contextmanager` 能把任意代码段包装成资源管理器。EAFP 风格不是"不要 if"，而是错误路径优先用异常表达，尤其在"检查与使用之间有竞态窗口"的场景。

**5. 工程案例**：见 part02a ch08——8.1 引入案例"一次被吞掉的 429"（合成案例）：`except Exception: return fallback()` 把编程 bug 与网络抖动混为一谈；EX-08-03 异常链、EX-08-04 上下文管理器。项目二的工具查询节点是"错误即数据"的实例：数据源异常被捕获后写进 `evidence(kind=tool_error)` 与审计日志，不炸整图（见 综合项目/p2 README 第 4 节第 7 条）——这是"异常处理策略要为下游可诊断性服务"的示范。

**6. 追问与回答边界**：
- 追问 1：Python 为什么没有 checked exception？——要点：鸭子类型与高阶函数（装饰器/回调）下强制声明不可持续；靠分层与文档补偿。
- 追问 2：3.11 的 ExceptionGroup/except* 用在哪？——要点：并发任务聚合异常（TaskGroup 抛的就是它，见专题二题 2-3）；细节以官方文档为准。
- 边界：`ExceptionGroup` 的语义细节本章正文未展开实测，答"知道适用场景，细节以官方文档为准"即可。
