## 12.3 专题三：模型 API 与结构化输出

> 对应正文：part04（ch21~ch25）。这个专题的面试官通常自己调过 API，糊弄不过去——数字要给实测口径，边界要给"以厂商文档为准"。

### 题 3-1 [模拟题] token 和上下文窗口是什么？为什么不能用 len(text)//4 估算？

**1. 问题与考查点**：考 token 的度量精度意识与窗口的真实结构——这两个认知直接决定预算代码的正确性。

**2. 常见错误回答**："token 大概就是一个词，英文 4 字符一个，中文也差不多。"——对英文粗略成立，对中文严重失真；预算场景"低估"=放行超额请求=线上 400。

**3. 简洁合格回答**：token 是模型处理文本的最小单位（BPE 分词产物），计费、窗口、限流都按它算。上下文窗口是**输入+输出共享**的总预算，多数服务另有独立的单次输出上限。估算必须用目标模型对应的 tokenizer（tiktoken 等）；本书实测：13 个汉字按 len//4 算约 3 个 token，实际 13 个——低估约 4 倍。无法精确时回退方案要放大系数并用真实 usage 校准。

**4. 深入解释**：窗口的工程含义三层：① 输入+输出共享，历史管理（截断/摘要）是在给输入腾预算；② 输出逐 token 生成，成本与延迟都高于输入，超长输出设计成多轮/分段；③ 滚雪球：多轮对话历史每轮全量重发（ch23 无状态会话），20 轮会话的平均费用可达 5 轮的数倍（part05 27.1 的客服场景数据：6 倍，合成案例）。工程工具：tiktoken 精确计数（EX-21-01）、token 预算表把窗口拆成 system/历史/输入/回答预留四个账户（EX-27-03）。

**5. 工程案例**：见 part04 ch21——EX-21-01（tiktoken 计数实验：中文 13 字符/13 token）、EX-21-02（上下文预算）、EX-21-03（Mock 确定性）。P1 的成本账（综合项目/p1 README 第 7 节）：单次问答 ≈ embedding 1 次 + LLM 1 次（编号证据 prompt 约 1~2k token 输入），top_k 与 chunk_size 是成本杠杆；EX-34-01 的预算装箱实验（预算 320：2 块装入、3 块整块丢弃）演示"预算不足时按分数截断"的真实行为。

**6. 追问与回答边界**：
- 追问 1：窗口 8k，为什么输出常常远小于 8k？——要点：输出另有独立上限参数；输出逐 token 生成，成本延迟双高。
- 追问 2：为什么要费劲控 token，不能等报错再改？——要点：预算是设计输入（切分大小、历史策略、top_k 都由它倒推），事后 400 是故障。
- 边界：各模型的窗口/价格/输出上限变化快，本书刻意不写死任何真实模型数字——回答时同样只给方法不给死数（以所用模型官方文档为准）。

### 题 3-2 [模拟题] temperature 设为 0，输出就完全确定了吗？

**1. 问题与考查点**：考对"模型不确定性"的真实边界认知——既不神化随机性，也不夸大确定性。

**2. 常见错误回答**："temperature=0 就是确定的，测试环境跑什么线上跑什么。"——实际上两次调用仍可能有差异；把"确定性"当 SLA 承诺会在评审时被打回。

**3. 简洁合格回答**：不一定。temperature=0 是近似贪心采样，仍有浮点非确定性与服务端批处理影响；部分服务提供 seed 参数提高一致性（openai 3.35.1 签名已核实含 seed），但"100% 一致"要以实测为准。工程上**靠回归测试兜底**而不是指望采样确定：golden set + 规则断言（ch28）。temperature 调的是"从概率分布里怎么挑 token"，治不了知识错误——事实错误要靠检索/拒答，不是调参。

**4. 深入解释**：参数分工表：temperature（分布尖锐度，事实问答/抽取类调低，创意类调高）、top_p（核采样截断，与 temperature 二选一动）、max_tokens（输出上限）、stop（终止序列）。Mock 模式的教学意义：本书 llm_client 的 Mock 是确定性实现（同输入同输出），让你能对管线做回归——**把"确定性"建在自己的代码层**（缓存、约束解码、模板化输出）比指望模型更可靠。选型建议：结构化抽取/分类 → 低温 + 结构化输出；对话/文案 → 中高温 + 评估集守护。

**5. 工程案例**：见 part04 ch23 EX-23-02（参数演示）与 23.11 追问 2；part05 ch28 的 Prompt 回归（EX-28-01）是把不确定性变成工程问题的正解。P1/P2 在 Mock 下全流程可复现（同输入同输出），正是"管线确定性"与"模型不确定性"分离设计的示范（见 综合项目/p1 README 第 0 段声明）。

**6. 追问与回答边界**：
- 追问 1：seed 参数跨请求稳定吗？——要点：文档承诺的是"尽力而为"，且系统/服务端升级可能破坏一致性；以实测为准。
- 追问 2：产品要求"回答 100% 准确"怎么回应？——要点：概率模型做不到；能承诺的是工程指标（引用可溯源、拒答率、抽样错误率上限），高风险输出走人工审核（part04 21.11 追问 3）。
- 边界：temperature/top_p 的实际效果幅度因模型而异（本书沙箱无 Key 未实测真实分布），回答时给方法与原则、不给具体模型的行为断言。

### 题 3-3 [模拟题] 流式输出怎么实现？客户端断开怎么办？

**1. 问题与考查点**：考流式的端到端链路（SDK chunk → 服务端 SSE → 前端渲染）与断连的资源回收——两个"看起来是前端的事"其实都是服务端责任。

**2. 常见错误回答**："接口返回得快就是流式。"——混淆首字节延迟与流式；或者答不出 chunk 拼接与"逐 chunk 解码乱码"的根因。

**3. 简洁合格回答**：SDK 侧 `stream=True` 返回 chunk 迭代器（生成器，题 1-4），每个 chunk 带增量 delta，累积 `delta.content` 得到全文；服务端用 SSE（`StreamingResponse` + `media_type="text/event-stream"`）逐片推给前端。客户端断开：消费端放弃迭代器 + 服务端取消上游 HTTP 连接，两者都要做；SSE 消息格式 `event:`/`data:`，注意反向代理的响应缓冲要关闭。

**4. 深入解释**：三个易错点——① chunk 是增量不是全量，拼接逻辑要自己写；② 多字节字符（中文）可能被切在 chunk 中间，按"字节→字符"错误解码会出乱码，正确姿势是累积到 token 级增量再解码（SDK 通常已处理，自实现时要留意）；③ SSE 与 WebSocket 选型：单向推送用 SSE（HTTP 直通、自动重连、代理友好），双向才用 WebSocket（见 part03 17.11 追问 2）。计费与风控含义：中途断开按已生成 token 计费；流式内容逐段可见，审核需要流式审核或事后撤回机制（23.11 追问 3）。

**5. 工程案例**：见 part02b ch09 EX-09-04（生成器驱动的流式）与 part03 ch17 EX-17-04（SSE 完整实现：事件格式、断连检测 `request.is_disconnected()`、finally 兜底）。P1 的 `/ask/stream` 是生产形态样本（见 综合项目/p1 README 第 5 节）：先发 `meta`（引用元信息，前端先渲染依据卡片）再逐片 `delta` 最后 `done`；拒答路径只有 meta+done、无 delta——协议状态机完整覆盖成功与失败。

**6. 追问与回答边界**：
- 追问 1：为什么 P1 要先发 meta 再发正文？——要点：引用先行让前端先展示"依据"，降低等待焦虑，也让拒答有独立语义。
- 追问 2：nginx 下 SSE 卡住怎么办？——要点：`X-Accel-Buffering: no` 透传、关闭代理缓冲（P1 README 第 8 节排障表有此项）。
- 边界：`is_disconnected()` 在不同 ASGI 服务器/代理组合下的触发时机有差异（part03 run log 声明沙箱走的是 uvicorn 取消生成器路径），生产应两条路径都保留。

### 题 3-4 [模拟题] 为什么"JSON Schema 约束"比"在提示词里求模型输出 JSON"可靠？

**1. 问题与考查点**：考约束的**层级**理解——提示词是概率级倾向，schema 约束是解码级机制。

**2. 常见错误回答**："提示词写得清楚就行，加一句'请输出 JSON'。"——模型会输出 JSON 但可能混入 Markdown 围栏、多余字段、枚举越界；概率级手段对"必须正确"的场景不够。

**3. 简洁合格回答**：JSON Schema 约束（response_format 的 json_schema 严格模式）在**解码阶段**约束每一步 token 的选择，语法级保证输出符合 schema；提示词只改变概率分布的倾向，是概率级手段。但工程上两者都不能裸信：schema 约束未必被所有"OpenAI 兼容"服务支持，输出仍要过 Pydantic 校验 + 失败重试兜底。

**4. 深入解释**：约束强度光谱：提示词求 JSON（最弱）→ json_mode（保证合法 JSON、不保证符合 schema）→ function_calling 复用工具协议（函数签名级约束）→ json_schema 严格模式（最强，服务端支持才有）。openai SDK 两条路：`create(response_format=...)` 与更高层的 `chat.completions.parse()`（3.35.1 已核实存在；**不含 stream 参数**——流式与结构化输出的组合要逐厂商核实）。LangChain 的 `with_structured_output` 三种 method 对应同一光谱（见专题五题 5-3）。任何一层都不是终点：Pydantic 校验是统一兜底（ch16 → ch24 的闭环）。

**5. 工程案例**：见 part04 ch24——EX-24-02（结构化输出 + Pydantic）、ch16 EX-16-04（Pydantic 生成 JSON Schema）。part04 24.1 的换厂商事故（合成案例）：换"OpenAI 兼容"服务后 JSON 里多了 Markdown 围栏、`tool_calls` 偶发不返回——约束的"支持边界"必须逐项核实，这正是题 3-8 的主题。

**6. 追问与回答边界**：
- 追问 1：schema 太复杂（深嵌套、大枚举）会怎样？——要点：约束解码失败率与模型能力相关，工程手段是简化 schema（拍平嵌套、枚举替代自由文本）+ 校验兜底。
- 追问 2：流式 + 结构化输出能同时要吗？——要点：取决于厂商支持（增量结构化流是较新能力），逐家核实；本书未实测，如实声明。
- 边界：严格模式对各兼容服务的覆盖面、`additionalProperties` 等细节要求，以厂商文档为准（part04 待核实清单已声明）。

### 题 3-5 [模拟题] 模型返回的 JSON 解析失败了，你的兜底链路是什么？

**1. 问题与考查点**：考"失败设计"——结构化输出从"能跑通"到"能上线"的差距全在失败路径。

**2. 常见错误回答**："try/except 包住，失败返回 null。"——把可恢复错误与不可恢复错误混为一谈，还把失败原因藏起来了；正确思路是分层自救。

**3. 简洁合格回答**：三层兜底：① **自纠重试**（一次为限）：把 ValidationError 的字段级错误信息（哪个字段、什么规则、原输入）喂回模型让它修——模型看到具体错误比看到"重新输出"有效得多；② **schema 收紧**：嵌套拍平、自由文本换枚举、必填字段最小化；③ **降级分支**：明确返回"无法解析"的结构化错误并告警，绝不静默吞掉。同时监控解析失败率——失败率高到回退常态化就是故障信号，要改模板/schema 而不是加宽回退通道。

**4. 深入解释**：为什么"喂回错误"有效：ValidationError 的 `errors()` 给出 `loc/type/msg/input`（机器可读），模型定位问题不需要猜；为什么"一次为限"：重试放大延迟与成本，两轮还失败说明是 schema/任务本身的问题，重试无益。为什么监控回退率：part05 26.11 追问 3 的原则——回退是止血不是治疗，常态化回退 = Prompt/设计有病。Java 对照：等价于"参数校验失败把 BindingResult 回显给调用方修正"，而不是"统一 500"。

**5. 工程案例**：见 part03 ch16.11 追问 2（兜底链路的三层答案）与 part04 ch24.4；引用校验的实例见 part06 EX-34-02：回答引用了不存在的 [5] → 程序拦截 → 回退抽取式回答——"校验失败→程序接管"的完整示范。P1 的 LLMJudge 设计里"判定失败按拒答兜底（宁拒不编）"是同族原则（见 综合项目/p1 README 第 9 节第 4 条）。

**6. 追问与回答边界**：
- 追问 1：重试时 temperature 要调吗？——要点：可略降温度提高服从性，但根因修复在 schema/Prompt；调参不是修复。
- 追问 2：解析失败的用户体验怎么设计？——要点：给明确状态与重试引导，不展示半截 JSON；失败样本落盘回填测试集。
- 边界：自纠重试对强 schema 违规（枚举外值）的成功率因模型而异，本书未实测真实模型行为——给方法不给成功率数字。

### 题 3-6 [模拟题] 工具调用的完整闭环是什么？模型能自己执行工具吗？

**1. 问题与考查点**：考闭环的消息协议（tool_calls → ToolMessage 配对）与安全架构（执行权在谁手里）——两问经常连考。

**2. 常见错误回答**："模型自己去查数据库。"——模型没有执行能力；它能做的是生成"想调哪个工具+参数"的意图，执行永远在你的程序里（part01 ch01 面试追问 2 就在纠正这个）。

**3. 简洁合格回答**：闭环四步：① 模型返回 `tool_calls`（工具名 + JSON 参数）；② 你的程序校验参数并执行真函数；③ 把结果包成 `tool` 角色消息、**必须带对应 `tool_call_id`** 追加进 messages；④ 重新请求模型，它基于结果继续（可能再要工具或给最终回答）。执行权留在客户端换来三件事：权限控制在你的代码里（模型绕不过鉴权）、副作用可审计可幂等、工具实现与模型解耦。

**4. 深入解释**：协议细节：一轮可以并行发多个工具调用，`tool_call_id` 是模型把结果对回请求的唯一依据，错配会让模型读到错位上下文（agent 输出错乱的经典来源，part08 46.11 追问 3）；历史里 assistant-with-tool_calls 与对应 tool 消息必须成对出现，截断历史时以"轮"为单位否则 400（part05 27.3 pair 完整性）。参数校验在执行前：Pydantic/手写白名单都行——模型给的参数不可信（对照 P2 的白名单三道校验：工具名→参数名→参数值，见 综合项目/p2 README 第 9 节）。

**5. 工程案例**：见 part04 ch24 EX-24-03（裸 SDK 完整工具循环：请求→执行→回传→总结）；part08 ch46 EX-46-01（图中工具循环，消息序列 6 条、call_001/call_002 配对，run log 有实测记录）；P2 的 `query_tools` 节点是生产形态：白名单拒绝越权参数并写审计 `tool_rejected`（综合项目/p2 README 第 7 节失败路径表）。

**6. 追问与回答边界**：
- 追问 1：工具执行失败了怎么办？——要点：预期内失败转成模型可读反馈让它自纠，预期外异常炸出来告警（详见专题五题 5-4）。
- 追问 2：为什么不让模型并行执行工具？——要点：模型根本没有"执行"能力，并行是**你的程序**并发执行多个 tool_calls——asyncio/线程池都行。
- 边界：并行工具调用（parallel tool calls）的开关参数名随 SDK 版本与厂商而异，以所用 SDK 文档为准。

### 题 3-7 [模拟题] 遇到 429 怎么处理？SDK 的自动重试和你的重试怎么共存？

**1. 问题与考查点**：考限流信号的语义理解与"重试叠加"这个隐性炸弹——高频且实战性强。

**2. 常见错误回答**："429 就立即重试。"——立即重试正好撞在限流枪口上；正确处理必须尊重 Retry-After 与退避；两层重试叠加的总预算也很少有人算。

**3. 简洁合格回答**：429 是"限流"不是"失败"：① 尊重 `Retry-After` 头（秒数或 HTTP 日期，格式以厂商文档为准）；② 没有该头就指数退避+抖动；③ openai SDK（3.35.1 实测）默认 `max_retries=2`，对 429/连接错误/部分 5xx 自动重试——**应用层再加重试就是两层叠加**：SDK 一层 1+2=3 次尝试 × 应用层 3 次尝试 = 最坏 9 次真实请求，会自我放大限流；策略是只留一层（通常关小 SDK 层或去掉应用层）并算清总预算；④ 持续 429 说明并发超配额，回头调 Semaphore/限流（题 2-4），不是无脑重试。

**4. 深入解释**：429 与 5xx 的处理差异：5xx 是"我坏了"（可重试但看预算），429 是"你太快了"（必须按节奏来）。分租户视角：多租户网关要按租户隔离配额与限流（见 part04 24.11 追问 2 的多租户网关层清单），一个租户打满不该拖死其他租户——Semaphore 与计数都要按租户分桶。监控：429 率、重试后成功率、重试导致的延迟尾部都要有曲线，429 率趋势上升就是容量信号。

**5. 工程案例**：见 part02a ch08.1 的"一次被吞掉的 429"引入案例与 part03 ch15.1 的重试风暴事故（合成案例）；EX-15-02 退避+抖动实现。part04 24.3 实测核实了 SDK 重试默认值与触发条件（连接错误、408、429 与部分 5xx；401/403/400 不重试）——这两个事实来自对 3.35.1 的实际探测，可以放心引用。

**6. 追问与回答边界**：
- 追问 1：Retry-After 没给怎么办？——要点：指数退避+抖动，上限受调用频率约束；持续 429 升级为容量问题。
- 追问 2：SDK 重试对幂等有要求吗？——要点：SDK 重试发生在 HTTP 层，重复请求可能到达服务端——同题 2-6 的幂等键逻辑，读操作与带幂等键的写操作才安全。
- 边界：各厂商 429 响应体结构、配额维度（RPM/TPM）与 Retry-After 格式差异大，一律"以厂商文档与抓包实测为准"。

### 题 3-8 [模拟题] 换了一家"OpenAI 兼容"的服务，你要核实什么？

**1. 问题与考查点**：考兼容性核实方法论——这是本书 ch24 的核心生存技能，也是区分"用过 SDK"与"上过生产"的试金石。

**2. 常见错误回答**："改个 base_url 就行，说兼容就是兼容。"——"OpenAI 兼容"通常只兼容请求/响应的**形状**，不承诺功能全集；本书 ch24 的引入事故（半夜崩了）就是这么来的。

**3. 简洁合格回答**：按清单逐项核实，默认"不支持"直到验证通过：① 基础对话与流式（chunk 结构、finish_reason 语义）；② 结构化输出（response_format/parse 的严格模式支持度）；③ 工具调用（tool_calls 结构、并行调用、流式中的工具调用）；④ 多模态；⑤ 错误码语义（429 是否给 Retry-After、超时行为）；⑥ embeddings 等其他端点是否在同一兼容面内。核实手段：签名探测（`inspect.signature`）+ 小流量实测 + 契约测试进 CI。

**4. 深入解释**：类比的边界（part04 24.2"国道标准"）：形状兼容≠功能兼容——国道不承诺每个服务区都营业。工程兜底：自建薄接口层（本书 `示例代码/公共/llm_client.py` 就是 Mock/Real 双模式的示范）把厂商差异收敛在一处；关键功能（结构化输出、工具调用）上双保险（schema 约束 + Pydantic 校验）；兼容性契约测试用 respx 固化（ch18），换厂商只改测试的响应样本即可回归。

**5. 工程案例**：见 part04 ch24.1 的事故叙事（合成案例）与 24.11 追问清单；本书 llm_client 的双模式设计（第四部分 ch24 定义、全书复用，见 编辑规范/STYLE_GUIDE.md C 节）是"厂商差异收敛层"的活样本；P1 的 RealEmbedder/LLMJudge 按 openai 3.35.1 签名编写但未实调（沙箱无 Key，见 综合项目/p1 README 第 12 节未验证项）——引用时如实说明这个验证边界。

**6. 追问与回答边界**：
- 追问 1：核实清单里哪项最容易踩坑？——要点：工具调用的流式形态与结构化输出的严格模式（各家实现差异最大）。
- 追问 2：怎么防止厂商悄悄变更？——要点：契约测试常态化跑 + 对 usage/错误码的监控告警。
- 边界：各家兼容面的具体结论变化快，本书只给核实方法不给厂商结论——面试里主动说"这是方法论，具体清单以实测为准"很加分。

### 专题三 · 30 分钟自测（模拟口试）

> 用法：同前。本专题评分双门槛：数字必须带口径（怎么来的、适用范围），边界必须落在"以官方/厂商文档为准"——缺一个扣 1 分。

1. **[模拟题] 现场算一笔 token 账：为什么 `len(text)//4` 对中文危险？窗口结构对预算代码意味着什么？** 评分要点——本书实测 13 个汉字按 len//4 约算 3 个、实际 13 个（低估约 4 倍）；窗口=输入+输出共享预算、输出另有独立上限；多轮滚雪球（20 轮会话费用可达 5 轮的数倍量级）。
2. **[模拟题] temperature=0 能承诺输出确定吗？产品要"100% 一致"你怎么回应？** 评分要点——近似贪心仍有浮点与服务端因素、seed 是"尽力而为"；工程兜底靠 golden set+规则断言回归（ch28）；能承诺的是工程指标（引用可溯源/拒答率/抽样错误率上限），高风险输出走人工。
3. **[模拟题] 流式输出三个易错点各一句话：chunk 拼接、中文乱码、SSE 卡住。** 评分要点——chunk 是增量要自己拼；多字节字符可能被切在中间（按 token 级增量再解码）；反代缓冲要关（`X-Accel-Buffering: no`）；能讲 P1 的 meta→delta→done 协议加分。
4. **[模拟题] 模型 JSON 解析失败的三层兜底链？为什么"喂回错误信息"有效且"一次为限"？** 评分要点——自纠重试（ValidationError 的 loc/type/msg/input 喂回）→schema 收紧（拍平/枚举化）→结构化降级+告警；错误信息让模型精确定位、两轮仍败说明是 schema/任务问题；监控回退率，常态化回退=设计有病。
5. **[模拟题] 换一家"OpenAI 兼容"服务，报出至少 5 项核实清单与核实手段。** 评分要点——流式 chunk 结构/结构化输出严格模式/工具调用（含流式形态与并行）/错误码语义（429+Retry-After）/embeddings 端点；手段：签名探测+小流量实测+契约测试进 CI；金句"默认不支持，直到验证通过"。
