## 12.7 专题七：Agent 与 MCP

> 对应正文：第九部分大纲（ch52~ch56，正文交付前以本节与 examples/ch52、ch53、ch55 示例及项目二为准）。这个专题考察"判断力"：Workflow 还是 Agent、单 Agent 还是多 Agent、工具怎么治理、MCP 到底解决什么——全部是取舍题，没有背诵题。

### 题 7-1 [模拟题] 什么任务该用 Agent，什么该用固定 Workflow？

**1. 问题与考查点**：三条硬问题（ch52）——这是"能不能上生产"的判断题；能否把"自主性"当成要花钱买的能力来评估。

**2. 常见错误回答**："复杂的用 Agent，简单的用工作流。"——"复杂"不是判据；或"Agent 更智能所以优先 Agent"——把概率决策当免费午餐，忽略成本不可控与不可测试的代价。

**3. 简洁合格回答**：三问（EX-52-01 的决策表）：**Q1 路径能不能提前画出来？**（能→Workflow：控制流写死反而可测试、可审计）；**Q2 失败了要不要"换一条路再试"？**（要→Agent 的自主改道有价值）；**Q3 出错时业务能接受多大代价？**（代价高→收敛控制流、加人工审批）。组合判断：路径可画=Workflow；路径不可画但代价高=Agent+审批+预算护栏；代价低且探索性强=裸 Agent。一句话定性：Agent 的"自主"是在**有限循环内**按概率选下一步，不是真有意图——护栏（步数上限/审批）是默认配置，不是可选优化。

**4. 深入解释**：决策表要做成**代码**（EX-52-01：需求特征打分→结论+理由），评审时跑给架构师看——比"业界都在用"可辩护。治理抓手是 Agent loop 的**外部可观察行为**（EX-52-02）：步数、工具调用轨迹、终态——这些都可记录、可回归。plan-verify 循环（EX-52-03：先规划后验证）是给 Agent 加刹车的中间形态：模型仍自主，但每步产物过验证节点。需求漂移预案：Workflow 半年后加需求可能变成 Agent 形态——重新跑决策表，别沿用口头结论（与 ch37 的决策表同构）。

**5. 工程案例**：P2 是"Workflow 为主+一个审批闸门"：主干线性（解析→预筛→取证→假设→评估→结论），因为路径可画（Q1=能）；"要不要重启"用 interrupt 人工决策而不是让模型决定（Q3=代价高）。对照 ch42 的天气 Agent（代价低、探索性）——同一本书里两个形态各有其位。

**6. 追问与回答边界**：
- 追问 1：Agent 一定比 Workflow 贵吗？——要点：轮数不可控=成本不可控；预算护栏（步数上限/并发限制）把成本上限变成配置项，这是 Agent 方案的必备件。
- 追问 2：怎么向老板解释"看起来简单"的需求不该用 Agent？——要点：用 Q1——路径能画出来时，Workflow 每一步可测试可审计，Agent 每一步都是概率；"可控性是需求，不是偏好"。
- 边界：ch52~ch56 章节号按 syllabus 引用（正文交付前以本节与示例代码为准）；示例在 examples/ch52_workflow_agent、ch53_single_vs_multi。

### 题 7-2 [模拟题] 什么时候需要多 Agent？单 Agent 不够用的信号是什么？

**1. 问题与考查点**：架构拆分判断——考"不堆概念，给判断标准"（ch53 的教学目标）；能否说出多 Agent 的真实成本而不是画组织架构图。

**2. 常见错误回答**："多个 Agent 协作更智能，铁定要上多 Agent。"——多 Agent 的通信协议、状态一致性、失败传播、排障复杂度都是真实成本；或把"多工具"误当"多 Agent"（一个 Agent 挂 20 个工具仍是单 Agent）。

**3. 简洁合格回答**：单 Agent 优先。拆多 Agent 的三个信号：① **上下文超载**——提示词+工具清单+历史互相稀释，模型开始忘事、选错工具；② **权限要隔离**——不同环节权限边界不同（查询 Agent 只读、执行 Agent 受审批），拆开后各 Agent 护栏独立；③ **并行分工**——多路独立任务要并行推进。多 Agent 的三个成本：通信消息协议（谁说什么、什么格式）、共享状态归并（谁的事实为准）、失败传播与级联重试（一个 Agent 挂了下游怎么办）。先单 Agent+好工具，撑不住了再拆。

**4. 深入解释**：多 Agent 的常见形态（主管-执行者/流水线/对等协作）各有失败模式（主管成瓶颈、流水线误差传播、对等协作死锁）——**形态不重要，"状态怎么归并、失败怎么传播"才重要**，回答时主动把话题拉到这两点。LangGraph 的落地手段就是子图+共享状态 schema（ch49）：子图有自己的状态与检查点，边界是控制流级的。评估也随拆分变难：每个 Agent 独立四层测试（题 6-8）+ 集成测试锁消息协议（协议即契约）。

**5. 工程案例**：见 examples/ch53——EX-53-01（单 Agent 的能力边界演示）、EX-53-02（两角色协作最小样本）；P2 保持**单图多节点**而非多 Agent——"节点"已经给了职责分离（取证节点无写权限、审批节点无决策权），还不够才拆图。

**6. 追问与回答边界**：
- 追问 1：Agent 间用什么通信？——要点：同图内共享状态（reducer 归并）；跨图/跨服务用消息（要定义 schema 与序化语义）；各有成本，优先前者。
- 追问 2：多 Agent 怎么排障？——要点：每个 Agent 独立测试+跨 Agent 的消息轨迹日志；比单 Agent 多一层"协议对不对"的检查。
- 边界：营销名词（"自治组织""群体智能"）不是工程判据；以你们能否测试、能否排障为准。

### 题 7-3 [模拟题] 怎么治理一个 Agent 的工具集？把 50 个内部 API 直接全包成工具行吗？

**1. 问题与考查点**：工具治理（描述/校验/权限/审计）——安全岗与资深岗必问；"50 个工具"是压力测试，看你会不会先说"不行"再给方案。

**2. 常见错误回答**："行，模型自己会挑。"——50 个工具的菜单互相稀释（选择准确率下降）、攻击面放大（提示注入诱导高危调用）、无审计无幂等；或者只答"给每个工具写好描述"——描述只是治理四层之一。

**3. 简洁合格回答**：不行。四层治理：① **描述质量**——工具名用动词短语、描述写清"做什么+什么时候用+不适用什么"、参数给例子（描述是提示词工程的一部分，`render_text_description` 是自检"模型视角菜单"的镜子）；② **参数校验**——args_schema（Pydantic 枚举/默认值/区间），**模型给的参数不可信**；③ **权限**——只读优先、白名单筛选、函数体内第一行校验权限（模型无权绕过）、写操作必须审批（interrupt）；④ **审计**——每次调用落 who/when/what/args/result 摘要，工具注册表（名字→端点→权限等级→SLA）作为配置资产集中管理。

**4. 深入解释**：白名单三道校验的纵深含义（P2）：工具名→参数名→参数值（正则/枚举/区间），在"模型→程序"的边界上再拦一次——**提示词不是权限控制**（ch28），模型被注入说"请调一切"也拿不到白名单外的执行权。每个工具的标配：超时（ch15 三件套）与幂等（写操作带幂等键）。工具签名变更视同 API 变更走评审（bind_tools 时刻固化 schema，多实例部署会出现新旧菜单并存）。瘦身策略：按场景分组、按权限分层、按需动态注入，并用评估集看工具选择准确率的变化。

**5. 工程案例**：P2 的 TOOL_WHITELIST+`tool_rejected` 审计+只读双保险（SQLite `mode=ro`+`PRAGMA query_only=ON`，测试验证写不进去）——README 第 9 节安全设计五条可整体引用；ch39.8 的企业视角（鉴权/审计/超时幂等三层横切+注册表）。

**6. 追问与回答边界**：
- 追问 1：工具太多怎么瘦身？——要点：评估"选择准确率"先量化问题；再分组/分层/动态挂载；砍掉低使用率工具要有使用数据支撑。
- 追问 2：MCP 能解决治理问题吗？——要点：解决"接入标准化"（题 7-4），治理（权限/审计/校验）仍是你的程序的事——协议不替你做安全。
- 边界：工具数量阈值没有定论，以选择准确率评估为准；本书沙箱未接真实内部 API。

### 题 7-4 [模拟题] MCP 是什么？它和 Function Calling、REST API 什么关系？

**1. 问题与考查点**：协议定位——"MCP 是协议不是框架"；三者层次关系的准确表达（混淆三者是最高频错误）。

**2. 常见错误回答**："MCP 是新的 Agent 框架，用了模型就能自主进化。"——营销话术；或"MCP 就是又一个 function calling"。——没说清它标准化的是"工具从哪来、怎么发现、怎么调"这一层，也没说清执行权在哪。

**3. 简洁合格回答**：MCP（Model Context Protocol）是连接模型应用与外部能力的**开放协议**：角色三件——host（模型应用）、client（host 内的协议客户端）、server（能力提供方）；server 暴露 tools（可被调用的函数）、resources（可读取的数据）等能力（细节以当前官方规范为准）。与 Function Calling 的关系：**互补不在一个层**——FC 是"模型点名工具"的模型侧机制（ch24 的闭环），MCP 标准化的是工具的**发现、描述与接入**；MCP server 的工具最终仍经 tool_calls 协议被模型点名。与 REST 的关系：REST 是通用接口风格，MCP 在其上加了"能力发现+统一工具描述+会话语义"，让同一个 host 接不同 server 不用各写适配。**执行权依旧在 host 程序**——MCP 不改变"模型点名、程序执行"的安全模型。

**4. 深入解释**：落地形态（ch55 示例）：stdio 传输——host 把 server 作为子进程拉起，stdin/stdout 承载 JSON-RPC 消息（**stdout 只能是协议帧**：print/logging 走 stderr，否则协议帧被污染、client 解析直接失败——ex_55_02 文件头明确写了这条纪律）；另有 HTTP 类传输用于远程常驻服务（细节以官方规范为准）。价值判断：能力多、来源杂、要跨团队复用时，MCP 的标准化划算；两三个内部工具直接写 @tool 更简单——**协议也有接入成本**。Java 侧对接思路：把已有 Java 服务包成 MCP server（或经网关暴露），Python host 经 client 接入——ch56 的方向。

**5. 工程案例**：examples/ch55_mcp——ex_55_02 最小 stdio server（2 工具+1 资源+1 提示模板，FastMCP 风格）、ex_55_03 client、ex_55_04 langchain-mcp-adapters 适配示例；server 端把 ValueError 转成协议级错误响应的做法（工具异常→协议错误帧）。

**6. 追问与回答边界**：
- 追问 1：MCP server 崩了 Agent 会怎样？——要点：工具不可用是预期内失败——转成模型可读反馈或错误即数据；host 要做连接管理与超时。
- 追问 2：MCP 的安全边界？——要点：server 是信任边界外的能力提供方——白名单、参数校验、审计在 host 侧照做不误。
- 边界：MCP 规范演进快（传输与能力集都在加版本），本书只对示例演示的 stdio 形态负责，其余以官方文档为准。

### 题 7-5 [模拟题] stdio 模式下为什么一句 print 就会把 MCP 弄挂？生产用哪种传输？

**1. 问题与考查点**：传输机制的工程细节——区分"读过文档"与"踩过坑"；能否给出传输选型与调试方法。

**2. 常见错误回答**："print 只是打个日志，没影响。"——stdio 下 stdout 就是协议通道，print 进去等于往 JSON-RPC 流里塞脏数据，client 解析直接失败（这是"协议通道被业务输出污染"的经典事故）。

**3. 简洁合格回答**：stdio 传输里，host 把 server 作为子进程拉起，双方用 stdin/stdout 交换 JSON-RPC 消息——**stdout 被协议独占**，任何 print/logging 必须走 stderr（本书 ex_55_02 文件头即此纪律；验证方法是"单独启动 server，stdout 必须沉默"）。生产选型：本地同机、开发/个人场景用 stdio（免端口免鉴权，进程父子关系即信任）；远程/共享服务用 HTTP 类传输（server 常驻、可鉴权可扩缩）——具体传输类型与握手细节以所用版本官方规范为准。两条通用纪律：连接生命周期管理（server 崩溃重启、健康检查）、协议版本协商失败 fail-fast 并留日志。

**4. 深入解释**：为什么 stdio 适合本地——零网络配置、随 host 生命周期启停；代价是单机、单连接、调试要"两看"（client 日志看协议帧、server stderr 看业务日志）。HTTP 类传输引入的是网络世界的问题——超时/重试/鉴权/TLS，ch15 的稳定性清单照用；这正好呼应 Java 工程师的老经验："协议换成网络协议后，稳定性课单一个不少。"

**5. 工程案例**：ex_55_02/ex_55_03 的 server/client 对（含 stdout 沉默验证）；server 端 `raise ValueError(f"计划 {plan_id} 不存在")` 被协议层转成错误响应——业务异常与协议错误的分界示范。

**6. 追问与回答边界**：
- 追问 1：怎么调试 stdio server？——要点：先单独验证"启动不打印"；client 侧开协议日志；业务日志全部引到 stderr/文件。
- 追问 2：多工具 server 要不要拆？——要点：按权限与变更频率拆（高危独立部署），与题 7-3 的治理一致。
- 边界：各传输的正式名称与参数以官方规范为准；本书沙箱只演示了 stdio，HTTP 传输未实测——如实声明。

### 题 7-6 [模拟题] 一个要跑 10 分钟的 Agent 任务，HTTP 接口怎么设计？

**1. 问题与考查点**：长任务模式——请求内循环/异步任务化/分步推进的三形态选型（ch46.8）；考"HTTP 语义与长任务天然冲突"的意识。

**2. 常见错误回答**："把网关超时调大。"——占住连接 10 分钟：超时重试、负载均衡、用户体验全坏；进程一重启任务全丢；或者"让前端一直转圈等"——同样的问题，只是把锅甩给了浏览器。

**3. 简洁合格回答**：三形态：① **请求内循环**——一次 HTTP 里跑完整图，适合轮数可控、总时长 <10s（简单，但循环期间占着连接）；② **异步任务化**（本题答案）——请求只做"受理"，立即返回 thread_id+任务号；图在后台 worker 推进，checkpointer 持久化保证进程重启可续；前端轮询 `get_state` 或订阅 SSE（stream_mode=updates 给"取证中…评估中…"的节点级进度）；工具循环长、涉及慢工具、要人工审批时的标配；③ **分步推进**——每次请求推进一步（利用检查点续跑语义），仅强交互向导用。配套设计：任务状态机（受理/运行中/等审批/完成/失败）、审批走 interrupt+回调、受理接口幂等（同业务单号返回同任务）。

**4. 深入解释**：为什么形态 2 与 LangGraph 天然适配——状态在检查点上，worker 可无状态化、换机器接手（凭 thread_id 寻址）；超时语义分层（受理响应秒级、任务本身无 HTTP 超时、审批有 SLA+外部超时升级——题 6-3）；取消语义：取消=写状态标记+节点在安全点检查标记，不是 kill 进程。与 Java 集成的分工：Java 网关只转发受理与查询接口，长连接 SSE 可透传（ch57 的模式）。

**5. 工程案例**：ch46.8 的三形态与选型判断（"循环轮数 ≤3 且总时长 <10s 用形态 1；轮数不可控或慢工具用形态 2"）；P2 的 CLI 是形态 1 的教学版，服务化路线即形态 2（README 第 12 节扩展方向）；审批对接 IM（interrupt 载荷推审批卡，`Command(resume)` 由回调驱动）。

**6. 追问与回答边界**：
- 追问 1：受理后重复提交怎么防？——要点：幂等键（业务单号）+thread_id 复用：同键返回同任务，不重复起跑。
- 追问 2：worker 挂了任务怎么续？——要点：新 worker 凭 thread_id get_state"三看"（next/values/metadata）后继续推进——检查点是续跑的依据。
- 边界：任务队列选型（Celery 类/云服务/自研）不在本书展开，按团队现状；形态 3 的适用面很窄，别当默认答案。

### 题 7-7 [模拟题] 你怎么评估一个 Agent 系统的好坏？

**1. 问题与考查点**：评估意识从 RAG 延伸到 Agent——结果质量+过程约束双维度；能否给出可落地口径而不是"看效果"。

**2. 常见错误回答**："看它能不能完成任务。"——没有可计算定义；或只看答案质量不看步数/工具调用/成本——一个"答对了但刷了 30 次工具"的 Agent 是事故不是功能。

**3. 简洁合格回答**：两个维度：① **结果质量**——任务成功率（场景评估集：给定输入+期望终态）、拒答/升级正确率（该交人工的交了吗——P2 的 UNKNOWN+缺口清单）、结论可追溯性（每个结论能对应到证据与审计记录）；② **过程指标**——步数分布、工具调用次数与选择正确率、成本（token/调用数）、时长分布。护栏触发本身是信号：recursion_limit 或步数上限**打满的 thread 就是问题名单**（提示词或工具有毛病）。全部进回归：场景评估集+Mock 剧本控制流回归（题 6-8）+真模型夜间评估。

**4. 深入解释**：Agent 评估与 RAG 评估的增量——路径不唯一使"对齐标准答案"不适用，改评"**终态等价类+过程约束**"（没越权、没超预算、证据留痕）；消融实验定位组件价值（去掉某个工具/提示词段落后成功率变化多少）；线上反馈闭环（用户采纳/撤销动作落库回填评估集）。成功率门槛的回答姿势：没有普适数——低风险场景可灰度试、高风险动作必须人工闸门；指标是持续运营对象，不是一次性门槛。

**5. 工程案例**：P2 的评估口径三条（拒答正确率/结论可追溯性/副作用安全，README 第 8 节）；14 个测试是"过程约束"的离线版（白名单拒绝、递归熔断、重放幂等都是过程指标的可测形态）。

**6. 追问与回答边界**：
- 追问 1：模型升级后 Agent 行为漂移怎么办？——要点：契约测试+场景回归集双保险；版本三元组（模型/Prompt/工具清单）记录，变更可解释。
- 追问 2：怎么区分"模型变笨"和"提示词变坏"？——要点：固定模型跑 Prompt 回归、固定 Prompt 跑模型评估——一次只动一个变量。
- 边界：Agent 评估的学界标准不在本书范围；本书给的是工程可落地的口径（终态+过程+回归）。

### 专题七 · 30 分钟自测（模拟口试）

> 用法：同前。本专题评分重点：每题都要"先给判断、再给判据"——只报概念不给取舍的，按不合格处理。

1. **[模拟题] 用三问法现场判断"发票审核助手"该 Workflow 还是 Agent。** 评分要点——Q1 发票类型与审核规则能否画全（大多能→Workflow 为主）；Q2 证据缺失要不要改道（可加有限 Agent 环节）；Q3 误判代价（高→人工闸门）；能说出"混合形态：Workflow 主干+受限 Agent 环节"加分。
2. **[模拟题] 说出拆多 Agent 的三个信号与三个成本。** 评分要点——信号：上下文超载/权限隔离/并行分工；成本：通信协议/状态归并/失败传播；结论必须落"单 Agent 优先"。
3. **[模拟题] 背出工具治理四层与白名单三道校验。** 评分要点——描述/校验/权限/审计；工具名→参数名→参数值；金句"提示词不是权限控制，模型无权绕过函数体内的校验"。
4. **[模拟题] 讲清 MCP 三角色与 FC/REST 的层次关系；stdio 下 stdout 纪律是什么？** 评分要点——host/client/server；FC=模型点名机制、MCP=发现与接入标准化、REST=接口风格（层次不同不互斥）；stdout 只承载协议帧、日志走 stderr。
5. **[模拟题] 给"跑 10 分钟的 Agent"画受理-轮询-审批时序图。** 评分要点——受理（幂等键→thread_id+任务号）→后台推进（checkpointer）→轮询 get_state 或 SSE→审批 interrupt/回调 resume→终态；说出"进程重启可续"的依据。
