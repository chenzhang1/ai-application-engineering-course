## 12.1 专题一：Python 基础与工程化

> 对应正文：part02a（ch04~ch08）、part02b（ch09~ch12）。这一专题考的是"Java 经验迁移后是否真正建立了 Python 对象模型"，题面常见、深水区在对象模型与语言规则的一致性。

### 题 1-1 [模拟题] 讲讲 GIL。Python 的多线程还有用吗？

**1. 问题与考查点**：考你能否按版本事实陈述 GIL，而不是背"GIL 已死/没用"的口号；能否区分 IO 密集与 CPU 密集。

**2. 常见错误回答**："GIL 就是 Python 不能多线程，要并发只能多进程。"——把 CPython 实现细节说成语言宿命，丢掉了 asyncio 与线程池对 IO 任务的价值，也答不出 free-threading 现状。

**3. 简洁合格回答**：GIL（Global Interpreter Lock，全局解释器锁）是 CPython 的互斥锁，保证同一时刻只有一个线程执行 Python 字节码。它只拖累 CPU 密集任务的线程并行；time.sleep、socket、文件 IO 会释放 GIL，所以 IO 密集场景用线程池或 asyncio 依然有效。3.13 起有 free-threading 实验构建，默认构建仍有 GIL，生态兼容在演进——以官方发布说明为准。

**4. 深入解释**：三个层次。① **它锁什么**：字节码执行的互斥，不是"整个解释器里什么都锁"——解释器每约 5ms 会强制当前线程让出 GIL，但"让出≠并行执行"。② **谁会释放它**：sleep、socket 读写、文件 IO 这些等待型操作会释放；numpy/torch 的底层 C 代码执行时也主动释放——这就是"调 numpy 的预处理用多线程有加速"的原因，加速来自 C 扩展而非 Python 字节码并行。③ **版本事实**：3.12 及以前所有正式版本默认带 GIL；3.13 提供 free-threading 实验性构建（非默认，生态适配有限）；本书沙箱（3.14.7）实测 Linux 默认 start method 已是 forkserver——版本相关结论一律标注"以官方发布说明为准"。

**5. 工程案例**：见 part03 ch14 的两个真实实验——EX-14-01：20 个 200ms 的模拟远程调用，单线程约 4s，线程池 10 workers 压到约 0.4s（等待重叠）；EX-14-02：1.2s 的纯 Python CPU 任务，四个线程与单线程同速，换进程池才真加速。AI 服务的典型组合见 14.11 追问：asyncio 作主干（调模型 API），`asyncio.to_thread` 包只有同步 SDK 的组件，常驻进程池包偶发重计算。

**6. 追问与回答边界**：
- 追问 1：free-threading 下单线程性能如何？——要点：实验版有开销，具体数字随版本变化，诚实说"未实测，以官方数据为准"。
- 追问 2：那 CPU 密集在 asyncio 服务里怎么办？——要点：`to_thread`/进程池/独立服务，别让重计算进事件循环（见专题二题 2-2）。
- 边界：free-threading 的生态兼容与性能数据、各平台默认 start method 的演进，回答"以官方发布说明与我实测的版本为准"是加分项；硬背一个具体数字是减分项。

### 题 1-2 [模拟题] 什么是可变默认参数陷阱？为什么语言不干脆禁止？

**1. 问题与考查点**：考对象模型（默认值在 def 时求值一次）与工程防呆意识；"为什么不禁"考你对语言设计一致性的理解。

**2. 常见错误回答**："这是 Python 的 bug，写的时候注意就行。"——说不出机制（`__defaults__`），也给不出系统化防呆手段，更答不出"为什么语言选择不特判"。

**3. 简洁合格回答**：默认参数在 `def` 执行时求值**一次**，存进函数对象的 `__defaults__`，之后所有调用共享同一个对象。默认值是可变对象（list/dict/set）时，一次调用里的原地修改会被下次调用看见。标准修复是 `None` 哨兵 + 函数体内新建；防呆靠 lint 规则（如 ruff 的 B006）。

**4. 深入解释**：语言选择"机制统一透明"而不是"特判可变对象"：默认值求值一次是统一规则，lambda 捕获、装饰器参数都依赖它；`__defaults__` 让行为完全可见可预测（EX-06-01 里直接打印它能看到污染现场）。可变默认值也有正当用法——当"跨调用缓存/固定注册表"用。修复写法 `def f(items: list[str] | None = None)` 体内 `if items is None: items = []`；Pydantic 的 `Field(default_factory=list)` 是同一思想的库化表达（见 part03 ch16.3）。

**5. 工程案例**：见 part02a ch06 EX-06-01：`add_task_bad` 连续调用两次，`r1` 与 `r2` 是同一个对象（`r1 is r2` 为 True），任务跨"请求"堆积——这正是 ch06 引入故事里客服 AI 服务"任务队列跨请求堆积"事故的根因（合成案例）。对照 ch07.1 的"类属性 `members = []` 所有实例共享"，是同一对象模型（名字绑定 + 共享可变对象）的两次投影。

**6. 追问与回答边界**：
- 追问 1：闭包的延迟绑定和它是同一个根因吗？——要点：同属"绑定延迟到调用时"——闭包捕获变量本身，循环里注册 lambda 全拿到最后值（EX-06-04）；修复可用默认参数固化（`lambda c, i=i: ...`）。
- 追问 2：什么场景故意用可变默认值？——要点：跨调用缓存、模块级注册表，但要接受"所有调用者共享"的语义并写注释。
- 边界：lint 规则编号（B006）随 ruff 版本变化，说"如 ruff 的 B006 一类规则"即可，别把编号当恒定事实。

### 题 1-3 [模拟题] 装饰器的原理是什么？和 Java 注解是一回事吗？

**1. 问题与考查点**：考"函数是一等公民→高阶函数→闭包→装饰器"这条推导链是否完整，以及 Spring AOP 经验能否准确对照。

**2. 常见错误回答**："装饰器就是 Java 的注解。"——混淆了元数据与行为：Java 注解本身没有行为，行为来自注解处理器/AOP 代理；Python 装饰器本身就是可执行的高阶函数，装饰发生在 import 时。

**3. 简洁合格回答**：装饰器是"接收函数、返回新函数"的函数，`@deco` 等价于 `f = deco(f)`——用包装后的新函数顶替原名字，装饰发生在定义时且只执行一次。功能上"Java 注解 + AOP 通知 ≈ Python 装饰器"，机制完全不同：一个靠容器代理织入，一个是语言原生的显式包装。

**4. 深入解释**：三层结构——wrapper 通过闭包记住 `func`（ch06 闭包）；`*args/**kwargs` 透传任意签名；带参装饰器再多一层工厂（`@retry(times=3)` 先求值 `retry(times=3)` 得到真装饰器）。`functools.wraps` 把原函数的 `__name__/__doc__/__wrapped__` 等元数据拷回 wrapper——不加的典型事故：按函数名注册的插件路由在装饰后全部变成 `wrapper`，互相覆盖导致请求错路由（见 part02b 10.11 追问 3）。类装饰器（`__init__` 收函数、`__call__` 执行）适合需要跨调用状态的场景。

**5. 工程案例**：见 part02b ch10 三个生产形态装饰器——EX-10-02 计时、EX-10-03 重试（对照 part03 ch15 的指数退避+抖动）、EX-10-04 调用日志。读框架代码也是同一件事：FastAPI 的 `@app.get`、LangChain 的 `@tool`、Pydantic 的 `@field_validator` 都是装饰器在"注册/包装"（见 part02b ch10 章首）。项目二的工具白名单与审计（见 projects/p2 审计日志）在思路上就是"切面"的图节点版。

**6. 追问与回答边界**：
- 追问 1：为什么带参数装饰器要三层？——要点：工厂收参数、装饰器收函数、wrapper 收调用参数。
- 追问 2：AOP 能做事务传播，装饰器能吗？——要点：裸装饰器没有框架运行时，需要什么能力就得显式传什么；不要硬说"能等价替代 Spring 事务"。
- 边界：装饰器与 PEP 695/649 等语法演进的关系本书未展开，答"以官方文档为准"。

### 题 1-4 [模拟题] 生成器和直接返回 list 有什么区别？在你的项目里哪里用到了？

**1. 问题与考查点**：考惰性求值省的到底是什么（中间物化 vs 总计算量），以及能否落到流式 LLM 输出这个本书主线上。

**2. 常见错误回答**："生成器省内存，性能更好。"——含糊且不完整：不省总计算量（该算的一个不少），"省内存"省的是**中间全量物化**；也答不出暂停/恢复语义的价值。

**3. 简洁合格回答**：迭代器是协议（`__next__` + `StopIteration`），生成器是"用 yield 自动实现该协议的函数"。与返回 list 相比省两件事：① 中间结果的物化——任一时刻只有一个"在路上的值"，不把全量结果攒进容器；② 首字节延迟——生产一个就能消费一个。流式 LLM 输出、大文件逐块处理、SSE 推送都是天然场景。

**4. 深入解释**：CPython 把生成器函数编译成特殊字节码帧：yield 时帧不销毁，栈与局部变量冻结在生成器对象里，`next()` 时恢复——状态保存在**函数帧**里而不是闭包变量。注意"省内存 ≠ 省计算"：总工作量不变，只是摊开到消费时。消费端提前放弃（break/连接断开）时，生成器被 GC 后帧销毁，后续 token 不再计算——但完整的服务端实现还要配合取消 HTTP 上游连接，只答"break 就行"不完整（见 part02b 9.11 追问 4）。

**5. 工程案例**：见 part02b ch09——EX-09-02 yield 语义、EX-09-03 惰性求值实测（急切方式物化 8.4MB 中间结果 vs 生成器 208 字节量级，3.14.7 实测值）、EX-09-04 LLM 流式输出。项目一的 SSE 路径（见 projects/p1 README 第 5 节：`meta` → `delta*` → `done`）服务端就是异步生成器驱动 StreamingResponse（见 part03 ch17.3）。

**6. 追问与回答边界**：
- 追问 1：生成器和迭代器什么区别？——要点：所有生成器都是迭代器，反之不成立；生成器的增量价值是暂停/恢复。
- 追问 2：生成器可以 `return` 值吗？——要点：值进 `StopIteration.value`，`yield from` 可接住；细节以官方语言参考为准。
- 边界：`sys.getsizeof` 具体字节数随版本浮动，引用时说"量级对比"而非精确数字。

### 题 1-5 [模拟题] 深拷贝和浅拷贝的区别？什么时候浅拷贝就够了？

**1. 问题与考查点**：考"名字→对象引用"模型（ch04）是否真正建立——拷贝复制的是"名字贴"还是"对象"。

**2. 常见错误回答**："copy.copy 复制值，copy.deepcopy 复制引用。"——方向说反了；或答不出"浅拷贝之后嵌套对象仍然共享"的具体后果。

**3. 简洁合格回答**：赋值只复制引用（两个名字贴同一对象）；浅拷贝新建外层容器、内层元素仍是共享引用；深拷贝递归复制所有层级（`copy.deepcopy` 自带备忘录机制处理循环引用）。浅拷贝够用的判据：外层要独立增删、内层全是不可变对象或只读。存在嵌套可变结构且要独立修改时必须深拷贝。

**4. 深入解释**：`b = a`、`b = a[:]`、`b = a.copy()`、`b = copy.deepcopy(a)` 四档语义依次增强。判断口诀：**拷贝了几层，取决于拷贝方式；共享了几层，取决于哪一层没有复制**。深拷贝的代价：性能（递归遍历）与语义（所有元素必须可深拷贝）。与 Java 的直觉差：Java 的 `clone()` 与集合拷贝构造同样是浅的，但 Java 里不可变集合（`List.of`）用得多，"共享可变状态"的暴露面小；Python 里嵌套 dict/list 是常态，更要主动想清楚层数。

**5. 工程案例**：见 part02a ch04 EX-04-05（四档拷贝的实测对照）与 EX-04-03（`==` 与 `is`）。项目里的真实风险点：P1 的 chunk 元数据 dict 若多处共享引用，一处改 `department` 全部"变节"——P1 的做法是入库时以不可变意图构造元数据并整体落盘（见 projects/p1 README 第 3 节 front-matter 设计），从源头减少"需要深拷贝"的场景。

**6. 追问与回答边界**：
- 追问 1：`deepcopy` 怎么处理循环引用？——要点：备忘录（memo）字典记录"已拷贝对象→新对象"映射，二次遇到直接取。
- 追问 2：frozen dataclass 能替代深拷贝吗？——要点：不可变结构共享引用是安全的，"用不可变替代拷贝"是更好的工程方向（见题 1-6）。
- 边界：deepcopy 对自定义类的行为取决于 `__deepcopy__`/`__copy__`/`__reduce__` 的实现，答到"可通过协议定制"即可，细节以官方 `copy` 模块文档为准。

### 题 1-6 [模拟题] dataclass、Pydantic BaseModel、TypedDict 怎么选？

**1. 问题与考查点**：考三个"结构化数据容器"的定位差异，本质考"运行时校验 vs 静态形状"这条边界（FACTS 术语基线：Pydantic ≠ DTO）。

**2. 常见错误回答**："都能定义字段，随便用。"——或"Pydantic 就是 Python 版 DTO"。漏掉了 Pydantic 的本质是**运行时校验器**：校验是构造行为本身，造不出校验不过的实例。

**3. 简洁合格回答**：内部数据结构、无运行时校验需求 → dataclass（轻、快，`@dataclass` 生成 `__init__/__repr__/__eq__`）；数据来自系统边界（HTTP 请求、配置文件、LLM 输出）需要校验与清晰错误 → Pydantic；只是给"字典形状的数据"声明键值类型、追求零运行时开销（如 LangGraph 的 State）→ TypedDict。一句话：**dataclass 管形状，Pydantic 管门禁，TypedDict 管字典的类型视图**。

**4. 深入解释**：① dataclass 默认可变，`frozen=True` 才不可变——对照 Java record（不可变）要指出这一差异；② Pydantic v2 校验核心是 Rust 实现的 pydantic-core，宽松模式默认做无损转换（"3"→3），`ValidationError.errors()` 给出 `loc/type/msg/input` 的机器可读错误；③ TypedDict 运行时就是普通 dict，静态检查器查键名与值类型，LangGraph 的 `MessagesState` 就是它的典型应用（见 part08 ch44.3）；④ 三者可组合：LangGraph State 用 TypedDict，节点内部业务对象用 dataclass，API 契约用 Pydantic。

**5. 工程案例**：见 part02a ch07 EX-07-04（dataclass 实测）与 7.11 追问 1；part03 ch16（Pydantic 四个 EX：basics/validators/settings/json_schema）；part08 ch44.3（MessagesState）。项目一的服务契约层是 Pydantic（projects/p1 `app/schemas.py`，README 第 2 节目录结构），而 LangGraph 编排的项目二状态是 TypedDict + Annotated reducer（projects/p2 `triage/state.py`，README 第 4 节第 1 条）——两个项目正好是"边界校验用 Pydantic、图状态用 TypedDict"的对照样本。

**6. 追问与回答边界**：
- 追问 1：为什么定义了 `__eq__` 还要管 `__hash__`？——要点：哈希协议要求"a==b 则 hash 相等"；自定义 `__eq__` 后 Python 把 `__hash__` 置 None（显式不可哈希）防止静默错误。
- 追问 2：Pydantic 校验失败怎么兜底？——要点：分层——schema 简化、错误喂回重试（一次为限）、降级分支（见专题三题 3-5）。
- 边界：dataclass 的 `slots=True/kw_only=True`（3.10+）语义细节、Pydantic 各小版本对可变默认值的处理差异，以各自官方文档为准。

### 题 1-7 [模拟题] Python 的类型注解运行时会强制吗？和 Pydantic 什么关系？

**1. 问题与考查点**：考"静态检查与运行时校验"的分工——这是 Java 工程师最容易带偏的模型（Java 注解 `@NotNull` 也常要靠框架，但编译期类型检查是硬的）。

**2. 常见错误回答**："写了 `def f(x: int)`，传字符串就会报错。"——不会。注解只是元数据，存进 `__annotations__`，解释器默认完全不校验。

**3. 简洁合格回答**：注解默认不强制，它是给两类工具读的：mypy/pyright 这类**静态检查器**在不运行代码时按注解做数据流检查；Pydantic/FastAPI 在**运行时**读注解做校验与转换。静态保证靠检查器（CI 里跑），运行时保证靠 Pydantic——两者互补不互替。这句话是类型系统的全部要点。

**4. 深入解释**：现代写法（3.10+）：`list[int]` 而非 `List[int]`、`str | None` 而非 `Optional[str]`、`TypedDict`/`Protocol`/`Literal`/`Annotated` 各司其职（对照表见 part02b ch11.3）。`from __future__ import annotations` 让注解惰性化（变字符串），EX-11-04 输出里 `'int'` 带引号是实证。`Protocol` 是结构化子类型：不看继承声明，有方法即满足，运行时默认不校验（`@runtime_checkable` 只查方法存在性）。工程纪律：注解覆盖率进 CI，配合 Pydantic 管"边界"，内部函数靠 mypy 防"手滑"。

**5. 工程案例**：见 part02b ch11——EX-11-03 现代类型写法、EX-11-04 注解的运行时形态。全书代码按"类型注解全量"标准编写（见 _meta/STYLE_GUIDE.md C 节），项目二的 `TriageState`（TypedDict + `Annotated[list, merge_lists]`）是"注解承载框架语义"的例子：reducer 就写在 `Annotated` 里，LangGraph 读它决定归并规则（见 projects/p2 README 第 4 节第 1 条）。

**6. 追问与回答边界**：
- 追问 1：mypy 和 Pydantic 会"打架"吗？——要点：不会，一个看源码一个看数据；要小心的是 Pydantic 的宽松转换让"运行时通过"的数据与静态声明的类型不完全一致，严格场景配 `StrictInt` 等。
- 追问 2：Protocol 和 ABC 怎么选？——要点：Protocol 零侵入适合"给既有类套接口"；ABC 名义化、可提供模板方法，团队强约束场景更醒目。
- 边界：PEP 649/749 在 3.14 的最终形态、mypy 各版本规则差异，答"以官方发布说明为准"。

### 题 1-8 [模拟题] 讲讲异常链和上下文管理器。`__exit__` 返回 True 会怎样？

**1. 问题与考查点**：考"无 checked exception 的世界里怎么保持可排障性"与资源清理纪律——两问常连着问，因为都关于"异常路径下的完整性"。

**2. 常见错误回答**："catch 里抛新异常就行。"——丢失原始异常（`raise RuntimeError("调用失败")` 把 429 的哪个模型、重试预算全丢了）；或"`__exit__` 返回 True 是清理用的"。——返回 True 的语义是**吞掉 with 块内的异常**。

**3. 简洁合格回答**：异常链：except 块内再抛新异常时，`raise NewError(...) from exc` 把原异常挂到 `__cause__`（报错文案 "direct cause"），堆栈完整可回溯；裸 `raise X` 只有隐式 `__context__`（"During handling..."）；`from None` 抑制内部细节（对外接口防泄露用，代价是丢线索）。上下文管理器：`with` 保证 `__exit__` 执行；`__exit__` 返回 True 会**吞掉**块内异常——合理场景只有 `contextlib.suppress`、事务回滚后不再上抛这类"明确要吞"的地方，业务代码默认返回 False。

**4. 深入解释**：Python 没有 checked exception，所有异常 unchecked——补偿设计是四件套：业务异常分层与基类统一捕获、异常处理器集中映射错误码（FastAPI `exception_handler`，见 part03 ch17.3）、关键函数文档声明可能抛什么、监控按异常类型统计。`with` 比 Java try-with-resources 强的地方：`__exit__` 参与异常决策（返回 True 吞异常），且 `@contextmanager` 能把任意代码段包装成资源管理器。EAFP 风格不是"不要 if"，而是错误路径优先用异常表达，尤其在"检查与使用之间有竞态窗口"的场景。

**5. 工程案例**：见 part02a ch08——8.1 引入案例"一次被吞掉的 429"（合成案例）：`except Exception: return fallback()` 把编程 bug 与网络抖动混为一谈；EX-08-03 异常链、EX-08-04 上下文管理器。项目二的工具查询节点是"错误即数据"的实例：数据源异常被捕获后写进 `evidence(kind=tool_error)` 与审计日志，不炸整图（见 projects/p2 README 第 4 节第 7 条）——这是"异常处理策略要为下游可诊断性服务"的示范。

**6. 追问与回答边界**：
- 追问 1：Python 为什么没有 checked exception？——要点：鸭子类型与高阶函数（装饰器/回调）下强制声明不可持续；靠分层与文档补偿。
- 追问 2：3.11 的 ExceptionGroup/except* 用在哪？——要点：并发任务聚合异常（TaskGroup 抛的就是它，见专题二题 2-3）；细节以官方文档为准。
- 边界：`ExceptionGroup` 的语义细节本章正文未展开实测，答"知道适用场景，细节以官方文档为准"即可。

## 12.2 专题二：异步编程与服务性能

> 对应正文：part03（ch13~ch14、ch15、ch17、ch19、ch20）。这一专题的高频误区是"asyncio=更快"，合格回答的锚点永远是：**吞吐来自等待重叠，不是计算加速**。

### 题 2-1 [模拟题] asyncio 是单线程的，为什么能提高吞吐？

**1. 问题与考查点**：考你对并发模型的机制级理解——"单线程为什么快"是区分"用过 asyncio"与"理解 asyncio"的分水岭。

**2. 常见错误回答**："asyncio 是异步的，所以比同步快。"——没说清"快"的是吞吐还是延迟、快在哪个阶段；CPU 密集任务在 asyncio 下毫无收益这一点通常也答不出。

**3. 简洁合格回答**：吞吐提升来自**等待重叠**：一个协程在 `await` 处等 IO（网络/磁盘）时，事件循环调度其他协程运行，几十个"等模型 API 响应"的请求共享一个线程。它不加速计算——CPU 密集任务在 asyncio 下毫无收益（要进程池）。正确表述是"IO 密集、高并发、单机"场景的吞吐方案。

**4. 深入解释**：事件循环维护就绪回调队列，`await` 把控制权交回循环并挂起当前协程，IO 完成后回调恢复协程——本质是"用户态调度的状态机"，对比线程：省掉内核线程切换与每线程栈内存，也省掉大量锁（单线程内无抢占）。代价是"纪律"：任何同步阻塞（`time.sleep`、同步 HTTP、重计算）都会卡住**所有**协程（见题 2-2）。与 Java 对照：心智上接近虚拟线程/CompletableFuture 编排，但 asyncio 的"协作式调度"意味着阻塞点必须显式 `await`——好处是切换点可见，坏处是漏写 await 或混入阻塞库就是事故。

**5. 工程案例**：见 part03 ch13——EX-13-02（time.sleep vs asyncio.sleep 的耗时对照实验）、EX-13-08（并发抓取：N 个请求总耗时 ≈ 最慢一个而非 N 倍）。AI 服务的主路径全是"等模型 API"（秒级网络 IO），这正是 asyncio 的最佳场景——P1 的 SSE 问答与 P2 的图编排（异步模式）都建立在这个地基上（见 part03 第三部分小结的能力表）。

**6. 追问与回答边界**：
- 追问 1：CPU 密集怎么办？——要点：`to_thread`/进程池/拆独立服务，事件循环只做编排。
- 追问 2：事件循环底层是什么？——要点：selector/epoll 就绪通知；性能调优（uvloop 等）不在本书范围，答"知道分层即可"。
- 边界：TaskGroup 取消传播的细节顺序、uvloop 数据，本书未实测——答"以官方文档与实测为准"。

### 题 2-2 [模拟题] 在 async 函数里调用了 time.sleep(5) 会发生什么？怎么发现和避免？

**1. 问题与考查点**：考"sync 阻塞对事件循环的伤害"——asyncio 事故榜第一名，也是"知道语法"与"能上线"的差距。

**2. 常见错误回答**："会阻塞这个请求 5 秒。"——错在范围：阻塞的不是这一个请求，是**整个事件循环上的所有请求**；而且这种阻塞在单实例压测里常被误判为"下游慢"。

**3. 简洁合格回答**：`time.sleep(5)` 是同步阻塞，它把整个线程（事件循环）卡住 5 秒——期间所有协程都无法调度，服务表现为"全实例请求集体变慢"。避免：等待用 `asyncio.sleep`；阻塞调用（同步 SDK、重计算）用 `asyncio.to_thread` 或线程/进程池隔离；发现靠压测下的延迟尖刺 + 日志里的调度延迟。

**4. 深入解释**：协作式调度没有抢占——协程不 `await`，循环就没有交接点。判别清单：① 纯等待 → 换异步原语（`asyncio.sleep`/`asyncio.wait_for`）；② 只有同步实现的库（某向量库 SDK、某加密库）→ `to_thread` 包一层（它是线程池上的 `run_in_executor` 语法糖）；③ CPU 密集 → 进程池，因为线程对纯 Python 计算无并行（GIL，题 1-1）。Java 对照：这相当于"在 Tomcat 的请求线程里写死循环"——但 Tomcat 多线程下伤害半径只有一个请求，asyncio 单线程下是全部请求，**半径差异**是回答的加分点。

**5. 工程案例**：见 part03 ch13.1 引入实验与 EX-13-02：同样"睡 3 次 × 1 秒"，串行 time.sleep 约 3s、asyncio.gather + asyncio.sleep 约 1s；把 asyncio.sleep 误写成 time.sleep 的版本退回 3s——三组数字在同一脚本里可复现。ch13.7 的异步上下文管理器（EX-13-07）示范了"异步资源也要异步释放"的同族纪律。

**6. 追问与回答边界**：
- 追问 1：怎么系统性发现阻塞点？——要点：压测看 P99 尖刺与并发度不成比例；日志打"请求间隔调度延迟"；code review 清单专查同步库。
- 追问 2：`to_thread` 有什么坑？——要点：线程池有上限（默认随版本变化，以官方文档为准）、任务函数要线程安全、contextvars 需要显式传递。
- 边界：默认线程池容量数字随 Python 版本变化，别背；以所用版本 `asyncio` 文档为准。

### 题 2-3 [模拟题] gather、wait、TaskGroup 三个怎么选？

**1. 问题与考查点**：考并发原语的**异常语义**差异——多数人只会"跑并发"，说不清"一个失败后其他任务怎么样"。

**2. 常见错误回答**："都是并发跑，用哪个都一样。"——异常传播、取消行为、返回结构完全不同，生产事故常出在"默认以为一样"。

**3. 简洁合格回答**：`gather(*aws)` 一次并发全部，默认**一个异常不取消兄弟任务**（异常在 await 时抛出，其余继续跑完）；`gather(..., return_exceptions=True)` 把异常当结果收集，适合"部分失败可接受"的批量；`wait` 给超时/轮询级别的精细控制（返回 done/pending 集合）；TaskGroup（3.11+）是结构化并发：**任一异常取消全部兄弟并聚合成 ExceptionGroup**，离开 with 块时保证没有任务泄漏。新代码要严格语义用 TaskGroup；批量部分失败场景用 `gather(return_exceptions=True)`。

**4. 深入解释**：决策表——① "要么全成要么全败"：TaskGroup（异常时取消兄弟、聚合上报）；② "多路独立查询，谁成用谁"：gather + return_exceptions；③ "给整批一个总超时，超时的放弃、没超时的要结果"：wait + timeout；④ "扇出后逐个消费"：`as_completed`。注意取消语义：`task.cancel()` 后协程若在 await 点收到 CancelledError 且吞掉不 re-raise，取消会被"吃掉"——约定是捕获后必须 re-raise（见 part03 13.11 追问 2）。

**5. 工程案例**：见 part03 ch13——EX-13-03（create_task + gather）、EX-13-05（异常传播实测）、EX-13-04（wait_for 超时取消）。真实选型：P1 的"批量 embedding 入库"若换真实模型 API 就是 gather(return_exceptions=True) 场景——单条文档失败不该拖垮整批（见 projects/p1 README 第 7 节"入库耗时主要在 embedding 调用"）；P2 的并行取证思路（三路只读查询）同理（见 projects/p2 README 第 12 节扩展方向 3）。

**6. 追问与回答边界**：
- 追问 1：gather 里某个任务超时怎么处理？——要点：外层 `wait_for(gather(...), timeout)` 会取消整批；要"逐个超时"给每个协程包 wait_for 或用 wait 的 timeout 参数。
- 追问 2：TaskGroup 抛的 ExceptionGroup 怎么接？——要点：3.11 的 `except*` 语法；细节以官方文档为准。
- 边界：TaskGroup 取消传播的聚合顺序等细节本书未展开实测，答"以官方文档为准"。

### 题 2-4 [模拟题] 为什么调模型 API 要加 Semaphore？加多少怎么定？

**1. 问题与考查点**：考并发限制（并发数 ≠ 请求数）与背压意识——"无脑 gather 1000 个模型调用"是新手最贵的错误。

**2. 常见错误回答**："asyncio 本身就是并发的，直接 gather 就行。"——asyncio 调度并发不等于下游能承受；对限流的模型 API 无节制并发会收获大量 429，重试风暴还会把配额打得更碎（对照 part03 15.1 的"重试风暴"事故）。

**3. 简洁合格回答**：Semaphore 把"同时在飞"的请求数限制在 N：`async with sem: await call()`。N 的确定顺序：先看 API 配额（RPM/TPM 与并发上限），再看自己实例数（N_单实例 × 实例数 ≤ 配额），再留余量给重试。它同时是**背压**的实现：超出的协程在信号量上排队，上游自然变慢而不是把下游打挂。

**4. 深入解释**：三层限流位置——① 出口并发（Semaphore，进程内）；② 实例间配额（Redis INCR 固定窗口/令牌桶，跨进程共享，见 part03 ch19.3——INCR 原子性、固定窗口的边界毛刺）；③ 下游自带限流（429 + Retry-After，见专题三题 3-7）。三者是纵深关系，互不替代。Java 对照：Semaphore ≈ Resilience4j 的 Bulkhead/RateLimiter 单机版；Redis 限流 ≈ 分布式 RateLimiter——你在 Java 里学的"单机闸门+分布式闸门"分层完全平移。

**5. 工程案例**：见 part03 ch13 EX-13-06（Semaphore 并发限制实测：10 个任务只有 3 个同时在跑）与 ch19 EX-19-04（Redis 固定窗口限流，接入 ch17 服务）。P1 README 第 7 节明确"入库耗时主要在 embedding 调用（真实模型下是网络 IO，应批量与并发控制）"——生产迁移时第一件事就是给 embedding 批量调用套 Semaphore。

**6. 追问与回答边界**：
- 追问 1：Semaphore 和队列有什么区别？——要点：Semaphore 限"同时在飞"，有界队列限"排队上限"（超出即拒绝），背压设计两者常配合。
- 追问 2：并发数设错了怎么发现？——要点：429 率上升 / 尾延迟上升，配合每个请求的 usage 记录（专题三）复盘。
- 边界：各厂商配额模型（RPM/TPM/并发）不同且随合同变化，答"以所用厂商文档为准"。

### 题 2-5 [模拟题] FastAPI/uvicorn 的 worker 是什么模型？多开 worker 有什么坑？

**1. 问题与考查点**：考部署形态反推架构决策的能力——uvicorn 的 `--workers` 是**进程**模型，这一句话直接判掉一批背题的人。

**2. 常见错误回答**："worker 就是线程池里的线程，开多点并发高。"——错。uvicorn worker 是 OS 进程，进程间零共享；Java 里"Tomcat 线程池"的直觉在这里失效。

**3. 简洁合格回答**：uvicorn 默认单进程跑事件循环；`--workers N` 起一个管理进程 + N 个 worker **进程**，每个进程自带 GIL 与独立内存。作用：① 多核利用（绕开 GIL 的进程级方案）；② 隔离性。坑：进程内存里的限流计数器、缓存、单例状态全部失真——2 个 worker 让"60 次/分钟"变 120 次/分钟；跨进程状态必须外置（Redis）。worker 数参考 1~2×vCPU，最终以压测为准。

**4. 深入解释**：为什么进程而不是线程——Python 有 GIL，单进程 asyncio 吃满 IO 并发但 CPU 只用一个核；多进程每进程独立 GIL 才有真并行（ch14）。对比 Java：Tomcat 单进程多线程（JVM 线程真并行），Spring 单例的进程内缓存在多实例前同样要外置——**"水平扩展后状态必须外置"是通用纪律，只是 Python 在单机内就提前触发了**。滚动发布配套：优雅停机 + 就绪探针 + 客户端重试兜底（见 part03 20.11 追问 2）。

**5. 工程案例**：见 part03——ch17 面试追问 3 与 ch19.1 的"多实例部署后限流阈值翻倍"事故（计数器最初在进程内存），修复是 Redis INCR（EX-19-04）；ch20 EX-20-02 用 `--help` 实测 uvicorn 生产参数存在性（`--workers`/`--timeout-graceful-shutdown` 等）。ch20 的 Dockerfile 因沙箱无 Docker 仅完成 11 项静态检查——引用时如实说明验证边界。

**6. 追问与回答边界**：
- 追问 1：SSE 长连接和多 worker 什么关系？——要点：SSE 连接固定在某个 worker 进程上，worker 数影响单机可维持连接面；会话亲和不是必须（每个 SSE 自包含）。
- 追问 2：单 worker 想利用多核又想要事件循环怎么办？——要点：多 worker 各跑一个事件循环；或多实例容器，编排层扩容。
- 边界：多 worker 优雅停机行为未做长时压测（part03 run log 已声明），worker 数经验区间标注"工程经验非实测结论"。

### 题 2-6 [模拟题] 重试怎么设计？非幂等操作能重试吗？

**1. 问题与考查点**：考超时/重试/幂等三件套的整体观——重试不是孤立参数，是"可重试错误集合 × 退避策略 × 幂等保障"的组合决策。

**2. 常见错误回答**："失败就重试，加个次数限制。"——三个隐患说不出：什么错误才可重试、退避怎么排、非幂等操作重试的资损风险。

**3. 简洁合格回答**：三前提缺一不重试：**请求可重发（幂等或带幂等键）、下游能承受、调用方等得起**。可重试集合：传输层错误与 502/503/504（429 特殊：按 Retry-After 退避，见题 3-7）；4xx 参数类错误一律不重试。退避：指数退避 + 抖动，第 n 次等待上限 `min(max_delay, base×2^(n-1))`，抖动防"同一毫秒集体重试"。非幂等操作（创建工单、扣款）不能裸重试——带 Idempotency-Key，服务端以键记账、重复回放首次响应。

**4. 深入解释**：超时三件套先行（connect/read/pool 各自限时，read 是"两次数据到达之间"不是总时长）——没有超时的重试是"无限期挂住"。参数定法：总重试预算=调用方可容忍延迟；客户端超时 > 下游 P99.9 且 < 自身 SLA；参数写配置不写死。幂等键服务端实现：键为账本主键，首执记账、重复回放，键冲突但请求体指纹不同要拒绝（409/422）——本书 stub 未实现指纹校验，如实说这是生产必补项。Java 对照：Resilience4j Retry + 幂等消费的唯一业务键，思想完全同构。

**5. 工程案例**：见 part03 ch15——15.1 的三连事故（合成案例）：P99 从 2s 飙 60s（超时语义错）→ 非幂等重试创建三次工单 → 重试风暴打挂刚恢复的下游；EX-15-02 退避+抖动、EX-15-03 幂等键 stub。SDK 层：openai 3.35.1 内建重试默认 2 次、只对连接错误/408/429/部分 5xx 生效（见 part04 ch24.3，签名与默认值实测核实）——应用层再加重试时先算两层叠加的总预算。

**6. 追问与回答边界**：
- 追问 1：重试放在客户端还是网关？——要点：分层各管各的（SDK 层、应用层、网关层），叠放时明确每层预算，宁可少一层。
- 追问 2：超时后请求到底成没成功？——要点：你不知道——这正是幂等键存在的理由；对账以服务端为准。
- 边界：各厂商 429 的 Retry-After 格式（秒数/HTTP 日期）与语义差异以厂商文档为准；连接池在多 worker 下是每进程一份，池参数按进程视角算（part03 run log 未做压测验证，如实声明）。

### 题 2-7 [模拟题] 下游变慢、请求开始堆积，你的服务怎么自保？

**1. 问题与考查点**：考背压（backpressure）的完整设计——从"单点限流"到"有界资源+降级"的系统观，常见于"你的服务被打挂过吗"这类开放题。

**2. 常见错误回答**："加机器。"——下游慢时加机器只是让更多请求同时挂在那；缺"拒绝谁、保住谁"的策略层。

**3. 简洁合格回答**：四道闸门从外到内：① 入口限流（超出配额直接 429，别让请求进来排队）；② 有界并发（Semaphore 限同时在飞的上游调用数）；③ 有界等待（排队超时：等待超过预算直接失败，用户得到快速错误而非 60s 白屏）；④ 降级（模型不可用时回退缓存答案/兜底话术，只读功能优先保）。原则：**宁可快速拒绝，不要无限堆积**——堆积的每个请求都占着连接、内存和用户耐心。

**4. 深入解释**：背压的本质是"让过载信号向上游传播"：无界队列把过载藏起来（内存涨、延迟涨、最后 OOM），有界资源让上游立刻看到失败并采取行动。实现载体：FastAPI 层用 Depends 挂限流（ch17），计数放 Redis 跨进程共享（ch19 INCR 原子性 + 固定窗口毛刺的诚实说明）；等待超时用 `asyncio.wait_for`；失效策略二选一——限流组件挂了"放行但告警"（失效开放）还是"拒绝"（失效关闭），按业务风险定。Java 对照：Resilience4j 的 Bulkhead+RateLimiter+CircuitBreaker 组合，思想一一对应。

**5. 工程案例**：见 part03 ch17 综合演练（订单查询+风控限流服务，含限流 429 的测试断言）与 ch19 EX-19-04；P1 的 SSE 路径在拒绝时返回 `meta(status=refused)+done` 而非挂起（见 projects/p1 README 第 5 节失败路径），"快速失败"从接口语义上就有保障。项目二的"证据不足直接 UNKNOWN 拒答"是同一原则在结论层的体现：没有足够证据就快速给出明确的不确定（见 projects/p2 README 第 7 节）。

**6. 追问与回答边界**：
- 追问 1：限流阈值怎么定？——要点：从下游容量与自身 SLA 倒推，压测校准，写配置可热调。
- 追问 2：熔断和限流的区别？——要点：限流防"请求过多"，熔断防"下游已坏还前赴后继"；本书在 ch15 讲了退避错峰，熔断器参数化的完整展开在后续生产章节，如实说明。
- 边界：熔断器具体参数与滑窗/令牌桶的选型对比，本书只覆盖固定窗口与思想层——答"知道更平滑的方案存在，选型以压测与运维约束为准"。

## 12.3 专题三：模型 API 与结构化输出

> 对应正文：part04（ch21~ch25）。这个专题的面试官通常自己调过 API，糊弄不过去——数字要给实测口径，边界要给"以厂商文档为准"。

### 题 3-1 [模拟题] token 和上下文窗口是什么？为什么不能用 len(text)//4 估算？

**1. 问题与考查点**：考 token 的度量精度意识与窗口的真实结构——这两个认知直接决定预算代码的正确性。

**2. 常见错误回答**："token 大概就是一个词，英文 4 字符一个，中文也差不多。"——对英文粗略成立，对中文严重失真；预算场景"低估"=放行超额请求=线上 400。

**3. 简洁合格回答**：token 是模型处理文本的最小单位（BPE 分词产物），计费、窗口、限流都按它算。上下文窗口是**输入+输出共享**的总预算，多数服务另有独立的单次输出上限。估算必须用目标模型对应的 tokenizer（tiktoken 等）；本书实测：13 个汉字按 len//4 算约 3 个 token，实际 13 个——低估约 4 倍。无法精确时回退方案要放大系数并用真实 usage 校准。

**4. 深入解释**：窗口的工程含义三层：① 输入+输出共享，历史管理（截断/摘要）是在给输入腾预算；② 输出逐 token 生成，成本与延迟都高于输入，超长输出设计成多轮/分段；③ 滚雪球：多轮对话历史每轮全量重发（ch23 无状态会话），20 轮会话的平均费用可达 5 轮的数倍（part05 27.1 的客服场景数据：6 倍，合成案例）。工程工具：tiktoken 精确计数（EX-21-01）、token 预算表把窗口拆成 system/历史/输入/回答预留四个账户（EX-27-03）。

**5. 工程案例**：见 part04 ch21——EX-21-01（tiktoken 计数实验：中文 13 字符/13 token）、EX-21-02（上下文预算）、EX-21-03（Mock 确定性）。P1 的成本账（projects/p1 README 第 7 节）：单次问答 ≈ embedding 1 次 + LLM 1 次（编号证据 prompt 约 1~2k token 输入），top_k 与 chunk_size 是成本杠杆；EX-34-01 的预算装箱实验（预算 320：2 块装入、3 块整块丢弃）演示"预算不足时按分数截断"的真实行为。

**6. 追问与回答边界**：
- 追问 1：窗口 8k，为什么输出常常远小于 8k？——要点：输出另有独立上限参数；输出逐 token 生成，成本延迟双高。
- 追问 2：为什么要费劲控 token，不能等报错再改？——要点：预算是设计输入（切分大小、历史策略、top_k 都由它倒推），事后 400 是故障。
- 边界：各模型的窗口/价格/输出上限变化快，本书刻意不写死任何真实模型数字——回答时同样只给方法不给死数（以所用模型官方文档为准）。

### 题 3-2 [模拟题] temperature 设为 0，输出就完全确定了吗？

**1. 问题与考查点**：考对"模型不确定性"的真实边界认知——既不神化随机性，也不夸大确定性。

**2. 常见错误回答**："temperature=0 就是确定的，测试环境跑什么线上跑什么。"——实际上两次调用仍可能有差异；把"确定性"当 SLA 承诺会在评审时被打回。

**3. 简洁合格回答**：不一定。temperature=0 是近似贪心采样，仍有浮点非确定性与服务端批处理影响；部分服务提供 seed 参数提高一致性（openai 3.35.1 签名已核实含 seed），但"100% 一致"要以实测为准。工程上**靠回归测试兜底**而不是指望采样确定：golden set + 规则断言（ch28）。temperature 调的是"从概率分布里怎么挑 token"，治不了知识错误——事实错误要靠检索/拒答，不是调参。

**4. 深入解释**：参数分工表：temperature（分布尖锐度，事实问答/抽取类调低，创意类调高）、top_p（核采样截断，与 temperature 二选一动）、max_tokens（输出上限）、stop（终止序列）。Mock 模式的教学意义：本书 llm_client 的 Mock 是确定性实现（同输入同输出），让你能对管线做回归——**把"确定性"建在自己的代码层**（缓存、约束解码、模板化输出）比指望模型更可靠。选型建议：结构化抽取/分类 → 低温 + 结构化输出；对话/文案 → 中高温 + 评估集守护。

**5. 工程案例**：见 part04 ch23 EX-23-02（参数演示）与 23.11 追问 2；part05 ch28 的 Prompt 回归（EX-28-01）是把不确定性变成工程问题的正解。P1/P2 在 Mock 下全流程可复现（同输入同输出），正是"管线确定性"与"模型不确定性"分离设计的示范（见 projects/p1 README 第 0 段声明）。

**6. 追问与回答边界**：
- 追问 1：seed 参数跨请求稳定吗？——要点：文档承诺的是"尽力而为"，且系统/服务端升级可能破坏一致性；以实测为准。
- 追问 2：产品要求"回答 100% 准确"怎么回应？——要点：概率模型做不到；能承诺的是工程指标（引用可溯源、拒答率、抽样错误率上限），高风险输出走人工审核（part04 21.11 追问 3）。
- 边界：temperature/top_p 的实际效果幅度因模型而异（本书沙箱无 Key 未实测真实分布），回答时给方法与原则、不给具体模型的行为断言。

### 题 3-3 [模拟题] 流式输出怎么实现？客户端断开怎么办？

**1. 问题与考查点**：考流式的端到端链路（SDK chunk → 服务端 SSE → 前端渲染）与断连的资源回收——两个"看起来是前端的事"其实都是服务端责任。

**2. 常见错误回答**："接口返回得快就是流式。"——混淆首字节延迟与流式；或者答不出 chunk 拼接与"逐 chunk 解码乱码"的根因。

**3. 简洁合格回答**：SDK 侧 `stream=True` 返回 chunk 迭代器（生成器，题 1-4），每个 chunk 带增量 delta，累积 `delta.content` 得到全文；服务端用 SSE（`StreamingResponse` + `media_type="text/event-stream"`）逐片推给前端。客户端断开：消费端放弃迭代器 + 服务端取消上游 HTTP 连接，两者都要做；SSE 消息格式 `event:`/`data:`，注意反向代理的响应缓冲要关闭。

**4. 深入解释**：三个易错点——① chunk 是增量不是全量，拼接逻辑要自己写；② 多字节字符（中文）可能被切在 chunk 中间，按"字节→字符"错误解码会出乱码，正确姿势是累积到 token 级增量再解码（SDK 通常已处理，自实现时要留意）；③ SSE 与 WebSocket 选型：单向推送用 SSE（HTTP 直通、自动重连、代理友好），双向才用 WebSocket（见 part03 17.11 追问 2）。计费与风控含义：中途断开按已生成 token 计费；流式内容逐段可见，审核需要流式审核或事后撤回机制（23.11 追问 3）。

**5. 工程案例**：见 part02b ch09 EX-09-04（生成器驱动的流式）与 part03 ch17 EX-17-04（SSE 完整实现：事件格式、断连检测 `request.is_disconnected()`、finally 兜底）。P1 的 `/ask/stream` 是生产形态样本（见 projects/p1 README 第 5 节）：先发 `meta`（引用元信息，前端先渲染依据卡片）再逐片 `delta` 最后 `done`；拒答路径只有 meta+done、无 delta——协议状态机完整覆盖成功与失败。

**6. 追问与回答边界**：
- 追问 1：为什么 P1 要先发 meta 再发正文？——要点：引用先行让前端先展示"依据"，降低等待焦虑，也让拒答有独立语义。
- 追问 2：nginx 下 SSE 卡住怎么办？——要点：`X-Accel-Buffering: no` 透传、关闭代理缓冲（P1 README 第 8 节排障表有此项）。
- 边界：`is_disconnected()` 在不同 ASGI 服务器/代理组合下的触发时机有差异（part03 run log 声明沙箱走的是 uvicorn 取消生成器路径），生产应两条路径都保留。

### 题 3-4 [模拟题] 为什么"JSON Schema 约束"比"在提示词里求模型输出 JSON"可靠？

**1. 问题与考查点**：考约束的**层级**理解——提示词是概率级倾向，schema 约束是解码级机制。

**2. 常见错误回答**："提示词写得清楚就行，加一句'请输出 JSON'。"——模型会输出 JSON 但可能混入 Markdown 围栏、多余字段、枚举越界；概率级手段对"必须正确"的场景不够。

**3. 简洁合格回答**：JSON Schema 约束（response_format 的 json_schema 严格模式）在**解码阶段**约束每一步 token 的选择，语法级保证输出符合 schema；提示词只改变概率分布的倾向，是概率级手段。但工程上两者都不能裸信：schema 约束未必被所有"OpenAI 兼容"服务支持，输出仍要过 Pydantic 校验 + 失败重试兜底。

**4. 深入解释**：约束强度光谱：提示词求 JSON（最弱）→ json_mode（保证合法 JSON、不保证符合 schema）→ function_calling 复用工具协议（函数签名级约束）→ json_schema 严格模式（最强，服务端支持才有）。openai SDK 两条路：`create(response_format=...)` 与更高层的 `chat.completions.parse()`（3.35.1 已核实存在；**不含 stream 参数**——流式与结构化输出的组合要逐厂商核实）。LangChain 的 `with_structured_output` 三种 method 对应同一光谱（见专题五题 5-3）。任何一层都不是终点：Pydantic 校验是统一兜底（ch16 → ch24 的闭环）。

**5. 工程案例**：见 part04 ch24——EX-24-02（结构化输出 + Pydantic）、ch16 EX-16-04（Pydantic 生成 JSON Schema）。part04 24.1 的换厂商事故（合成案例）：换"OpenAI 兼容"服务后 JSON 里多了 Markdown 围栏、`tool_calls` 偶发不返回——约束的"支持边界"必须逐项核实，这正是题 3-8 的主题。

**6. 追问与回答边界**：
- 追问 1：schema 太复杂（深嵌套、大枚举）会怎样？——要点：约束解码失败率与模型能力相关，工程手段是简化 schema（拍平嵌套、枚举替代自由文本）+ 校验兜底。
- 追问 2：流式 + 结构化输出能同时要吗？——要点：取决于厂商支持（增量结构化流是较新能力），逐家核实；本书未实测，如实声明。
- 边界：严格模式对各兼容服务的覆盖面、`additionalProperties` 等细节要求，以厂商文档为准（part04 待核实清单已声明）。

### 题 3-5 [模拟题] 模型返回的 JSON 解析失败了，你的兜底链路是什么？

**1. 问题与考查点**：考"失败设计"——结构化输出从"能跑通"到"能上线"的差距全在失败路径。

**2. 常见错误回答**："try/except 包住，失败返回 null。"——把可恢复错误与不可恢复错误混为一谈，还把失败原因藏起来了；正确思路是分层自救。

**3. 简洁合格回答**：三层兜底：① **自纠重试**（一次为限）：把 ValidationError 的字段级错误信息（哪个字段、什么规则、原输入）喂回模型让它修——模型看到具体错误比看到"重新输出"有效得多；② **schema 收紧**：嵌套拍平、自由文本换枚举、必填字段最小化；③ **降级分支**：明确返回"无法解析"的结构化错误并告警，绝不静默吞掉。同时监控解析失败率——失败率高到回退常态化就是故障信号，要改模板/schema 而不是加宽回退通道。

**4. 深入解释**：为什么"喂回错误"有效：ValidationError 的 `errors()` 给出 `loc/type/msg/input`（机器可读），模型定位问题不需要猜；为什么"一次为限"：重试放大延迟与成本，两轮还失败说明是 schema/任务本身的问题，重试无益。为什么监控回退率：part05 26.11 追问 3 的原则——回退是止血不是治疗，常态化回退 = Prompt/设计有病。Java 对照：等价于"参数校验失败把 BindingResult 回显给调用方修正"，而不是"统一 500"。

**5. 工程案例**：见 part03 ch16.11 追问 2（兜底链路的三层答案）与 part04 ch24.4；引用校验的实例见 part06 EX-34-02：回答引用了不存在的 [5] → 程序拦截 → 回退抽取式回答——"校验失败→程序接管"的完整示范。P1 的 LLMJudge 设计里"判定失败按拒答兜底（宁拒不编）"是同族原则（见 projects/p1 README 第 9 节第 4 条）。

**6. 追问与回答边界**：
- 追问 1：重试时 temperature 要调吗？——要点：可略降温度提高服从性，但根因修复在 schema/Prompt；调参不是修复。
- 追问 2：解析失败的用户体验怎么设计？——要点：给明确状态与重试引导，不展示半截 JSON；失败样本落盘回填测试集。
- 边界：自纠重试对强 schema 违规（枚举外值）的成功率因模型而异，本书未实测真实模型行为——给方法不给成功率数字。

### 题 3-6 [模拟题] 工具调用的完整闭环是什么？模型能自己执行工具吗？

**1. 问题与考查点**：考闭环的消息协议（tool_calls → ToolMessage 配对）与安全架构（执行权在谁手里）——两问经常连考。

**2. 常见错误回答**："模型自己去查数据库。"——模型没有执行能力；它能做的是生成"想调哪个工具+参数"的意图，执行永远在你的程序里（part01 ch01 面试追问 2 就在纠正这个）。

**3. 简洁合格回答**：闭环四步：① 模型返回 `tool_calls`（工具名 + JSON 参数）；② 你的程序校验参数并执行真函数；③ 把结果包成 `tool` 角色消息、**必须带对应 `tool_call_id`** 追加进 messages；④ 重新请求模型，它基于结果继续（可能再要工具或给最终回答）。执行权留在客户端换来三件事：权限控制在你的代码里（模型绕不过鉴权）、副作用可审计可幂等、工具实现与模型解耦。

**4. 深入解释**：协议细节：一轮可以并行发多个工具调用，`tool_call_id` 是模型把结果对回请求的唯一依据，错配会让模型读到错位上下文（agent 输出错乱的经典来源，part08 46.11 追问 3）；历史里 assistant-with-tool_calls 与对应 tool 消息必须成对出现，截断历史时以"轮"为单位否则 400（part05 27.3 pair 完整性）。参数校验在执行前：Pydantic/手写白名单都行——模型给的参数不可信（对照 P2 的白名单三道校验：工具名→参数名→参数值，见 projects/p2 README 第 9 节）。

**5. 工程案例**：见 part04 ch24 EX-24-03（裸 SDK 完整工具循环：请求→执行→回传→总结）；part08 ch46 EX-46-01（图中工具循环，消息序列 6 条、call_001/call_002 配对，run log 有实测记录）；P2 的 `query_tools` 节点是生产形态：白名单拒绝越权参数并写审计 `tool_rejected`（projects/p2 README 第 7 节失败路径表）。

**6. 追问与回答边界**：
- 追问 1：工具执行失败了怎么办？——要点：预期内失败转成模型可读反馈让它自纠，预期外异常炸出来告警（详见专题五题 5-4）。
- 追问 2：为什么不让模型并行执行工具？——要点：模型根本没有"执行"能力，并行是**你的程序**并发执行多个 tool_calls——asyncio/线程池都行。
- 边界：并行工具调用（parallel tool calls）的开关参数名随 SDK 版本与厂商而异，以所用 SDK 文档为准。

### 题 3-7 [模拟题] 遇到 429 怎么处理？SDK 的自动重试和你的重试怎么共存？

**1. 问题与考查点**：考限流信号的语义理解与"重试叠加"这个隐性炸弹——高频且实战性强。

**2. 常见错误回答**："429 就立即重试。"——立即重试正好撞在限流枪口上；正确处理必须尊重 Retry-After 与退避；两层重试叠加的总预算也很少有人算。

**3. 简洁合格回答**：429 是"限流"不是"失败"：① 尊重 `Retry-After` 头（秒数或 HTTP 日期，格式以厂商文档为准）；② 没有该头就指数退避+抖动；③ openai SDK（3.35.1 实测）默认 `max_retries=2`，对 429/连接错误/部分 5xx 自动重试——**应用层再加重试就是两层叠加**：2 次 SDK 重试 × 应用 3 次 = 最多 6 次真实请求，会自我放大限流；策略是只留一层（通常关小 SDK 层或去掉应用层）并算清总预算；④ 持续 429 说明并发超配额，回头调 Semaphore/限流（题 2-4），不是无脑重试。

**4. 深入解释**：429 与 5xx 的处理差异：5xx 是"我坏了"（可重试但看预算），429 是"你太快了"（必须按节奏来）。分租户视角：多租户网关要按租户隔离配额与限流（见 part04 24.11 追问 2 的多租户网关层清单），一个租户打满不该拖死其他租户——Semaphore 与计数都要按租户分桶。监控：429 率、重试后成功率、重试导致的延迟尾部都要有曲线，429 率趋势上升就是容量信号。

**5. 工程案例**：见 part02a ch08.1 的"一次被吞掉的 429"引入案例与 part03 ch15.1 的重试风暴事故（合成案例）；EX-15-02 退避+抖动实现。part04 24.3 实测核实了 SDK 重试默认值与触发条件（连接错误、408、429 与部分 5xx；401/403/400 不重试）——这两个事实来自对 3.35.1 的实际探测，可以放心引用。

**6. 追问与回答边界**：
- 追问 1：Retry-After 没给怎么办？——要点：指数退避+抖动，上限受调用频率约束；持续 429 升级为容量问题。
- 追问 2：SDK 重试对幂等有要求吗？——要点：SDK 重试发生在 HTTP 层，重复请求可能到达服务端——同题 2-6 的幂等键逻辑，读操作与带幂等键的写操作才安全。
- 边界：各厂商 429 响应体结构、配额维度（RPM/TPM）与 Retry-After 格式差异大，一律"以厂商文档与抓包实测为准"。

### 题 3-8 [模拟题] 换了一家"OpenAI 兼容"的服务，你要核实什么？

**1. 问题与考查点**：考兼容性核实方法论——这是本书 ch24 的核心生存技能，也是区分"用过 SDK"与"上过生产"的试金石。

**2. 常见错误回答**："改个 base_url 就行，说兼容就是兼容。"——"OpenAI 兼容"通常只兼容请求/响应的**形状**，不承诺功能全集；本书 ch24 的引入事故（半夜崩了）就是这么来的。

**6. 追问与回答边界**：
- 追问 1：核实清单里哪项最容易踩坑？——要点：工具调用的流式形态与结构化输出的严格模式（各家实现差异最大）。

- 边界：各家兼容面的具体结论变化快，本书只给核实方法不给厂商结论——面试里主动说"这是方法论，具体清单以实测为准"很加分。

### 题 4-1 [模拟题] 上下文窗口越来越长，为什么还要 RAG？什么时候不该用 RAG？

**1. 问题与考查点**：技术演进下的架构判断+"反向边界"——能说清"何时不该用"比背"是什么"高一个层级；顺带考你把幻觉、成本、权限三个维度分开谈的能力。

**2. 常见错误回答**："窗口小所以需要 RAG，窗口大了 RAG 就淘汰了。"——把 RAG 的价值押在窗口大小这一个变量上；或者说不出 RAG 自己的成本面（好像它是免费的）。

**3. 简洁合格回答**：窗口解决"塞得下"，RAG 解决三件窗口解决不了的事：① **成本**——全量知识每次请求重付 token，费用随知识量线性涨；② **权限**——按用户过滤必须在检索层做，塞窗口等于把全部文档发给每个用户；③ **时效与治理**——改文档即生效，索引可增量更新、可审计。反过来四种情况不该用：知识量小且稳定（几千 token 内，直接放 Prompt/长上下文）；要实时数据（走工具查询）；要改风格/格式（微调或 few-shot）；问题本质是"算"不是"查"（工具）。一句口诀收尾：**微调教"怎么做"，RAG 送"要知道什么"，工具查"现在是什么"**。

**4. 深入解释**：决策工具是"四连问"：知识会变吗、有多大、要按人隔离吗、答案要实时吗——两个以上"是"选 RAG，全"否"用长上下文/纯 Prompt，"查系统数据"用工具（见 ch30 的四方案对照表）。幻觉要拆三层谈：知识缺失型（RAG 直接对症）、上下文背离型（RAG 缓解，忠实性指标对症）、推理错误型（RAG 无能为力，工具对症）——"上了 RAG 就不会胡说"是本专题最典型的错误答案。RAG 的完整成本不止 token：一次性建设（清洗/切分调参/评估集）、检索延迟（embedding 在真实模式下是一次网络调用）、运维（同步/重建/坏例分析）、评估回归（每次换模型改参数都要重跑）。加分动作：现场用 EX-30-02 的 token 算术把两种方案的每日输入量算给面试官看。

**5. 工程案例**：见 part06 ch30——EX-30-01 三场景演示（编造的制度条款）、EX-30-02 决策表（长上下文 277 token/次 vs RAG top-3 187 token/次，日请求 1 万时差距放大且未计检索侧）；P1 的立项依据就是三条命中：制度会改、要按部门隔离、要拒答（projects/p1 README 第 1 节）。

**6. 追问与回答边界**：
- 追问 1：百万级窗口普及后 RAG 形态会怎么变？——要点：top-k 能给的块更多、切分可以更粗，但成本/权限/时效三条理由不变，检索层的地位反而更突出。
- 追问 2：RAG 和微调能混用吗？——要点：能且常见：微调管输出风格与格式服从，RAG 管事实供给；对应 ch62 的选择树。
- 边界：各模型窗口/价格变化快，本书刻意不写死任何真实模型数字——面试同样只给方法与算式，具体以厂商文档为准。

### 题 4-2 [模拟题] chunk_size 怎么定？切分有没有"最佳实践"？

**1. 问题与考查点**：反对背数字——考"参数是评估出来的"这条纪律，以及切分器机制（overlap 生效条件、结构与元数据）的理解深度。

**2. 常见错误回答**："业界最佳实践 512。""越大越好，塞的上下文多。"——报数字的人答不出数字从哪来；前者是把别人语料的校准值当普适真理，后者忽略"一块混多主题、向量被稀释"的反向伤害。

**3. 简洁合格回答**：没有跨语料的万能值，只有方法：① 从"一条完整规则/一个语义单元"的典型长度定初值；② 理解两个参数各管什么——chunk_size 是检索单元粒度（太小→语义单元被劈开、单块命中残缺；太大→无关内容稀释向量、引用粒度粗），overlap 是边界容错（通常取 size 的 10%~20%，且只在"内容超过 size 需要续切"时生效）；③ 有结构信号的文档先按标题分节、再节内细切（两级管线），让"门牌号"变成元数据；④ 改参数必须重跑评估集看 hit@k 与端到端答案质量取交点，发布走"重建影子索引→评估对比→灰度切换"。

**4. 深入解释**：三个容易被追问的细节：① 字符 vs token 口径——默认 `length_function=len` 按字符数，token 口径管窗口预算、字符口径管 embedding 上限，中文含数字文本两者差异大；② 元数据在入库瞬间定死（溯源/权限/展示三类，必需字段缺失拒绝入库 fail fast）——"需要时再补"会让向量与元数据失同步；③ 表格三类做法（小表整块转 markdown、大表行级切分并复制表头、结构化数据抽字段走工具查询）——展平丢行列对应关系几乎必错；④ 中文必须显式传分隔符，默认分隔符面向英文，会退化到字符级硬切（ch41 实测）。

**5. 工程案例**：见 part06 ch32 三个 EX——EX-32-01（固定长度的"半句话"）、EX-32-02（递归切分与"5 字标题块"盲区）、EX-32-03（两级管线+元数据设计）；P1 的 200/30 是在 16 条评估集上试出来的（README 第 2 节选型表），不是 industry standard——这句话本身就是标准答案的一部分。

**6. 追问与回答边界**：
- 追问 1：语义切分（按 embedding 相似度找断点）好吗？——要点：工程顺序先结构、后句界、最后语义断点；语义切分入库要多算相似度且断点质量依赖模型，除非评估证明结构切分不够。
- 追问 2：为什么"5 字块"是问题？——要点：`##` 是门牌号，纯长度切分不认识它；两级管线把标题消费成"边界+元数据"。
- 边界：200/30、0.16 等数字只对本合成语料+MockEmbedder 有效，引用时说"示例值，须用自家语料重校"。

### 题 4-3 [模拟题] 为什么只有向量检索不够？混合检索怎么做？

**1. 问题与考查点**：两路检索的互补机制+融合的工程理由（RRF 为什么只用名次）——考"检索系统"而非"调了个 embedding API"。

**2. 常见错误回答**："向量检索是语义的，比关键词高级，直接用它就行。"——把两路说成替代关系；或答不出"两路分数直接加权相加"为什么是错的。

**3. 简洁合格回答**：两路各治一种失败：向量路管"意思接近"（同义改述、跨表述），BM25 管"词面精确"（工单号 K3、专有名词、罕见缩写——真实 embedding 对词表外的编号同样没有稳定语义）。融合用 RRF：把两路结果折算成"名次倒数"再累加（k=60 是平化常数），天然免疫两路的量纲差异（BM25 0~20+ 对余弦 −1~1），直接加权会让分数大的一方独裁。top-k 管上下文预算（塞几块）、阈值管"最像的也够不像"（该不该拒答）——两个不同的闸门，取值都来自评估集（k 用 hit@k 曲线找召回饱和点；阈值取应答分数下界与应拒分数上界之间的空隙）。

**4. 深入解释**：BM25 三个参数各管一件事：IDF 是灵魂（只在 1/6 文档出现的词得到高区分度，处处出现的"的"几乎不得分）；k1 让词频增益饱和；b 惩罚长文档。中文的地基是分词，且**入库与查询必须用同一个分词器**（两侧不一致是"BM25 全零分"的第一根因）。向量侧：入库前 L2 归一化让点积=余弦，分数才有跨记录可比性，阈值才有意义。生产形态是"两路+一融合+一重排"：企业里 BM25 路常常就是现成的 Elasticsearch（8.x 的 hybrid query 原生支持 BM25+kNN+rrf），**你不需要为 BM25 路新建任何基础设施**——这正是混合检索在企业落地便宜的原因。查询改写是增益项且会漂（改写是生成行为），必须进评估回归。

**5. 工程案例**：见 part06 ch33——EX-33-01（numpy 归一化点积，25 块微秒级）、EX-33-02（BM25 手写与"K3 实验"：精确词 BM25 赢）、EX-33-03（RRF 融合：同义改述向量赢）；P1 的词面重排 `fused = 0.5*cos + 0.5*lex` 是 MockEmbedder 词表外区分度不足时的补偿设计（README 第 2 节），真实 embedding 下权重要重校。

**6. 追问与回答边界**：
- 追问 1：数据到千万级怎么办？——要点：ANN 索引（HNSW/IVF）+向量库选型四问（规模/权限过滤下推/更新频率/运维），近似召回率要用 hit@k 验收，不能只看延迟。
- 追问 2：为什么不用"分数归一化后加权"？——要点：RRF 免调参、对分数分布漂移鲁棒；先拿 80 分，评估证明不够再升级加权/LTR。
- 边界：FAISS 本书沙箱未安装（ch33.A 声明）；ES hybrid query 的参数名以官方文档核实为准。

### 题 4-4 [模拟题] 重排（rerank）什么时候值得上？代价是什么？

**1. 问题与考查点**：成本-收益判断——资深岗用这题区分"堆组件的人"与"算账的人"。

**2. 常见错误回答**："重排一定提升精度，直接上最强模型。"——不计成本与位置；或"重排就是再算一遍余弦"。——混淆双塔与交叉编码器。

**3. 简洁合格回答**：当评估显示"**召回对但排序错**"占坏例大头时才值得。交叉编码器把查询与候选拼在一起打分，精度显著高于双塔（向量检索是各自编码再比相似度，交叉编码是逐对细读），但每条候选一次模型推理，延迟与成本按候选数线性涨。常见配置：双塔召回 top-50 → 重排取 top-5 进上下文；用评估集验证重排前后的 hit@1 与答案质量，**涨了才留**。

**4. 深入解释**：两个结构认知：双塔的向量可以离线预计算（查询侧只算一次），交叉编码必须在线逐对算——这是延迟差异的根源；重排治不了"召回就没有"（那是切分/embedding 问题，先分层定位再上重排）。工程位置：权限过滤要在重排之前（无权候选不值得花重排算力）；重排前后的 hit@1 差值进监控，作为"这个组件还值不值得在"的持续证据。重排不是只能用模型——P1 的词面重排就是"便宜版"，关键是它有评估数据支撑。

**5. 工程案例**：见 part06 33.11 追问 3 的配置口径；P1 README 第 2 节对词面重排"存在理由与真实模型下的撤回条件"的记录——一个组件带着它的退出条件上线，这是可以主动讲的设计成熟度信号。

**6. 追问与回答边界**：
- 追问 1：重排与查询改写先做哪个？——要点：按坏例归因分桶：问法不匹配（改写）vs 排序错（重排），评估集说了算。
- 追问 2：重排模型怎么选？——要点：给方法不给品牌——延迟预算、部署形态（API/自托管）、评估集实测收益；本书未实测任何具体 rerank 模型，以实测为准。
- 边界：交叉编码器精度优势是机制层结论；具体模型的具体收益数字必须来自你自己的评估集。

### 题 4-5 [模拟题] 引用怎么做才能"可溯源"？模型总忘写 [n] 怎么办？

**1. 问题与考查点**："引用是接口约定，不是模型自觉"——三层防线的设计；顺带考预算装箱与流式协议的细节一致性。

**2. 常见错误回答**："在 Prompt 里要求模型写引用就行。"——Prompt 是软约束，模型偶发幻觉引用（引一个不存在的 [5]）；上线评审时这叫"不可验收"。或者反过来"让模型输出整个 JSON 含 citations"，但 citations 仍由模型自由发挥、没有程序校验。

**3. 简洁合格回答**：三层：① **Prompt 层**——编号证据块+few-shot 示例+"只依据编号证据"约束（软）；② **程序校验**——回答中 `[n]` ⊆ 本次检索返回的编号集合，校验失败当场拦截并回退抽取式回答（硬，必做）；③ **架构层**——结构化输出让 answer 与 citations 分字段返回，citations 由程序从"实际使用的块"生成，不靠模型写编号。配套两条纪律：块编号必须稳定且在 Prompt、回答、citations 三处指向同一个块；预算装不下的块**整块丢弃**——截半块会让模型基于"不可结转被截成可结转"的残句作答，比没有证据更危险。

**4. 深入解释**：三个高频事故的机制：① citations 与回答不同源（异步/流式下两处 top_k 不一致）→ 不变式"回答中的标记 ⊆ citations 编号"必须做成测试（P1 的 `test_ask_answered_with_valid_citations`）；② 忠实性自动校验的盲区——数字锚点便宜有效（制度类语料核心事实几乎都带数字），但"无数字的事实篡改"（"需审批"说成"无需审批"）要 LLM 判官初筛+人工终审；③ 引用数据结构每个字段给谁用（index 给前端、doc_id/chunk_id 给溯源、score 给排障、snippet 给展示）——能按消费方讲字段，比背字段名高一档。

**5. 工程案例**：见 part06 ch34——EX-34-01（编号证据+预算装箱：预算 320 装 2 丢 3）、EX-34-02（幻觉引用拦截：回答引用不存在的 [5] → 程序接管回退抽取式）；P1 的 SSE 三事件协议先发 meta（引用先行，README 第 5 节），拒答路径只有 meta+done。

**6. 追问与回答边界**：
- 追问 1：引用校验失败率升高说明什么？——要点：Prompt 漂移或检索质量下降，先看坏例归因再动约束；监控该率本身就是答案。
- 追问 2：多轮对话里引用怎么带？——要点：引用绑定"本轮证据"；跨轮指代先做查询改写重新检索，不沿用上一轮编号。
- 边界：内容级忠实性的自动指标有盲区（EX-35-03 的假阳性/假阴性），人工抽检环节不可省。

### 题 4-6 [模拟题] 多租户 RAG 的权限过滤为什么必须在检索层？怎么落地？

**1. 问题与考查点**：安全架构的位置感——"三个不"；这是 Java 工程师经验平移最顺的一题，答好它等于展示了"权限系统老手"的身份。

**2. 常见错误回答**："检索完把没权限的从结果里删掉就行。"——事后过滤泄露存在性（从"证据不足"与响应差异可推断被删内容的存在）、浪费召回名额（无权文档挤占 top-k），更糟的情况是内容已经进过模型上下文——输出过滤为时已晚。

**3. 简洁合格回答**：三个"不"：无权文档**不参与排序**（否则挤占召回名额）、**不进上下文**（进了就等于模型看过）、**不出现在引用里**（不泄露存在性）。落地：权限字段（tenant_id/department）是 chunk 元数据的一部分、入库时定死；过滤发生在打分函数**入口**（候选集先过滤再算相似度）；生产把过滤下推到向量库/ES 的 metadata filter（避免拉全量，且"过滤后 top-k"的召回名额不被无权文档挤占）。身份只来自请求上下文（JWT/Session），**绝不来自问题文本或模型输出**——ch28 红线在 RAG 场景的落点。

**4. 深入解释**：与 Java 经验的精确对照：检索前 ACL ≈ SQL 的 `WHERE tenant_id = ?`（参数化、在查询层），而不是查出来再在应用层删——你写过的每一行行级权限代码都是这里的经验。权限模型设计：部门继承等规则放权限模块，检索模块只消费"一个集合"的抽象（职责分离，改继承不动检索）。fail-closed：过滤逻辑异常时宁可全拒不可全放——权限组件是安全闸不是可用性闸。测试要锁"无权用户的检索结果里不存在该文档"（存在性测试），不只是"返回为空"。

**5. 工程案例**：见 part06 ch34 EX-34-03（mallory 视角里 acme 文档"不存在"——与"查无此文"体验一致，没有"存在但无权"的暗示）；P1 的 can_read 是 kb.py 检索第一步（README 第 2 节架构图），finance 用户问年假得到 `refused` 而非权限暗示（第 5 节失败路径表）；tests/test_p1.py 的租户隔离与部门 ACL 用例。

**6. 追问与回答边界**：
- 追问 1：权限过滤与向量库 filter 什么关系？——要点：教学实现内存过滤（25 块无所谓），生产必须下推；"过滤下推能力"是向量库核心选型指标之一。
- 追问 2：文档权限变了但向量没重嵌入，怎么办？——要点：权限在元数据不在向量里，更新元数据即可；若切分边界依赖密级（按章节密级分块），才需要重建。
- 边界：数据库行级安全（RLS）与向量库组合的细节随产品而异，以所用组件文档为准；本书沙箱未接真实 RBAC 系统。

### 题 4-7 [模拟题] RAG 的效果怎么评估？hit@k、忠实性这些指标怎么落地？

**1. 问题与考查点**：把"好不好"变成可计算数字——这是 AI 应用岗与"调 API 玩票"的分水岭，也是 ch35 的验收标准。

**2. 常见错误回答**："人工看几条，感觉还行。"或"用 GPT 打个分。"——没有可计算定义就没有回归：改任何参数（切分/阈值/模型/Prompt）都在裸奔，"感觉变好"不是工程。

**3. 简洁合格回答**：评估集先行：20~50 条起步，**应答与应拒答两类用例都要有**，每条带期望（期望命中文档/关键词/拒答标记）。四类可计算指标：① 检索层 **hit@k 与 MRR**——hit 管"正确文档进没进前 k"（用户可见性），MRR 管"平均排第几"（排序敏感度），hit 平稳而 MRR 下滑说明排序在退化，两个一起看互当校验；② **忠实性代理**——数字锚点（回答中的数字必须出现在被引块里，制度类语料的便宜兜底）；③ **引用正确性**——回答中 `[n]` ⊆ citations；④ **拒答正确率**——该拒的拒、不该拒的不误伤（误拒与漏拒是一对跷跷板）。指标进 pytest 做 CI 回归；LLM-as-judge 只做规模化初筛，判官要定期与人工判读对齐一致率。

**4. 深入解释**：自动评估的两大局限要有名字：**假阳性**（词面全中但张冠李戴——自动通过人工不通过）处置是补指标（引用-句子对齐）；**假阴性**（正确转述换词——自动拦截人工通过）处置是放宽指标或补同义词。评估集纪律：与被测系统独立评审（不许"顺手改期望"）、badcase 脱敏回填、与版本三元组（切分/模型/Prompt）绑定——任何一元变更都能解释指标变化。上线门槛是"自动指标+人工抽检"双门槛：自动全绿只说明已知风险守住了，不等于线上没问题（分布外用例）。

**5. 工程案例**：见 part06 ch35 三个 EX（EX-35-01 hit@2=100% 而 MRR=0.833 的互补实证、EX-35-02 四种失败形态与数字锚点、EX-35-03 假阳/假阴）；P1 的 16 条评估集四指标 100%（README 第 6 节），并且主动声明"词面级/结构级指标只能做回归守门，答案是否真对要人工抽检"——这句诚实声明在面试里本身就是加分项。

**6. 追问与回答边界**：
- 追问 1：评估集多少条够？——要点：看覆盖度不看条数：高频问题全覆盖、每类失败形态至少 1 条、badcase 全回填；做"两种 embedding 谁好"级别的比较要百条级并关注波动。
- 追问 2：评估全绿但用户说答错了？——要点：分布外——脱敏回填先复现失败；复现不了说明缺多轮/会话上下文维度（ch27）。
- 边界：LLM 判官的一致率因模型与任务而异，本书未实测真实判官——给机制与对齐方法，不给数字。

### 题 4-8 [模拟题] 用户反馈"RAG 答错了"，你的排障路径是什么？

**1. 问题与考查点**：分层排障方法论——第六部分的验收标准（"给出至少 3 类定位手段"），也是把前面 7 题串成流程的收口题。

**2. 常见错误回答**："先调 Prompt。"或"换个更强的模型。"——不分层瞎调，改完没有评估佐证，同类错误下周照来；更糟的是"每次都改 Prompt"会把本来是检索问题的坏例越调越坏。

**3. 简洁合格回答**：三步定位：① **分层复算**——单独跑检索层算 hit@k（不看生成）：没中→检索问题（文档没入库/切分切碎/索引过期/问法不匹配）；中了再看生成层（忠实性/引用校验）：命中还错→Prompt 约束或模型问题；② **看分数分布**——top-k 分数整体偏低说明语料-模型不匹配或阈值过松；应答与应拒用例的分数区间重叠说明阈值没分开（重校）；③ **拒答原因分桶**——`no_relevant_evidence` 多=知识缺口（补文档）、`below_score_threshold` 多=问法不匹配（查询改写/同义词表）、`evidence_insufficient_judge` 多=召回内容跑题（切分粒度/embedding 质量）。修复后重跑评估集证明有效，再灰度上线。

**4. 深入解释**：能把排障做成"三桶分流"的前提是**结构化 refusal_reason**——这就是为什么拒答原因必须是枚举三态而不是一段话（ch34 的设计动机）。hit@k 突降但没人改代码时，先分三类漂移再动手：数据漂移（语料变了）/配置漂移（阈值过滤变了）/基准漂移（评估集被改）。还有一类"检索和生成都没错但用户不满意"——问法/粒度问题，评估集补样本、考虑查询改写。会话类问题（多轮指代）不在单轮评估覆盖内，要单独补维度（ch27）。

**5. 工程案例**：P1 的排障流程已经写进面试讲法（README 第 10 节原话："先看 refusal_reason 分流，再看 top-k 分数分布判断是检索问题还是生成问题"）；两道闸各拦住过不同坏例的实证——跨租户查询靠余弦分数越过 gate1、被 gate2 词面判定拦下（run log 有记录，README 第 5 节）；ch30 调试题参考答案给出"年假可以结转"错答的三类原因定位。

**6. 追问与回答边界**：
- 追问 1：怎么防止同类错误复发？——要点：badcase 脱敏回填评估集 + 原因码统计驱动改进排序（哪类原因多先修哪类）。
- 追问 2：定位手段的前提是什么？——要点：可观测——citations、refusal_reason、分数都要落日志（"可回放模型当时看到了什么"），没有留痕就没有排障。
- 边界：阈值/权重数字只对本书合成语料有效；"答错"的最终判据要人工定义，自动化只能守结构与回归。

### 专题四 · 30 分钟自测（模拟口试）

> 用法：同前。本专题评分重点：决策题要"给出判据"，机制题要"给出版本/位置"，数字题要"给出处"。

1. **[模拟题] 用四连问法现场分析"公司价值观手册问答"该不该上 RAG。** 评分要点——30 页约几千 token、年更、全员可见、无实时要求→四问全否→长上下文或纯 Prompt；能补 RAG 成本结构至少两项（建设/延迟/运维/评估）加分。
2. **[模拟题] top-k 和阈值是两道什么闸门？取值怎么定？** 评分要点——top-k 管上下文预算、阈值管"该不该拒答"；k 用 hit@k 曲线找召回饱和点，阈值取应答/应拒分数分布的空隙；说"都是评估出来的，不是拍的"。
3. **[模拟题] 口头推导：RRF 为什么只用名次不用原始分？** 评分要点——两路量纲不同（BM25 0~20+ vs 余弦 −1~1）；对分数分布漂移鲁棒、免调参；代价是丢"分数置信度"；能补"加权归一化是升级路线，评估证明不够再上"加分。
4. **[模拟题] 拒答双保险各拦什么？举一个 gate1 放行但 gate2 拦下的例子。** 评分要点——gate1 拦"检索器不自信"、gate2 拦"自信的跑题"；P1 跨租户案例（词面撞上文档分数过 0.16、词面重合不足被拦）；判定器失效 fail-closed。
5. **[模拟题] 白板画出"RAG 答错"的三步排障流程。** 评分要点——分层复算（hit@k 分清检索/生成）→分数分布（阈值两侧是否分开）→拒答原因分桶（知识缺口/问法/召回跑题）；修复后必须重跑评估+灰度。

## 12.5 专题五：LangChain

> 对应正文：part07（ch37~ch42）。这个专题考的是"框架素养"：不是背 API，而是能说清**框架接手了什么、留下了什么、什么时候不该用它**——以及版本意识（0.x 与 1.x 是两套答案）。

### 题 5-1 [模拟题] 你们为什么用（不用）LangChain？什么时候不该用它？

**1. 问题与考查点**：选型论证——考"决策表"而不是"站队"；能否把"要不要用框架"变成可辩护、可重评的工程决策。

**2. 常见错误回答**："业界都用。""教程是这么写的。""我们全用裸 SDK，框架都是垃圾。"——三个都是情绪不是论证；共同缺陷是说不出框架接手了什么、留下了什么、什么场景它净收益为负。

**3. 简洁合格回答**：按决策表判定（EX-37-01，判定顺序=阻断性从高到低）：① 需要人工审批/中断恢复/持久化 → 这是**状态机需求**，链表达不了，直接 LangGraph；② 单轮+单步+无工具+不换模型 → 裸 SDK，框架是纯认知开销；③ 需要工具调用循环 → `create_agent`，框架收益最大的场景（消息回写/tool_call_id 配对/循环终止样板全部接走）；④ 需要检索/换模型/多步管道 → 组件级使用（切分器/Retriever/Runnable），不引入 Agent。因为需求会漂移，决策表要做成**可执行函数**，需求评审时重跑一遍，别依赖口头结论。

**4. 深入解释**：包分工要能报出来（1.x）：langchain-core 是地基（消息/Runnable/工具协议/Fake 模型），langchain 是门面（create_agent/中间件/init_chat_model），langchain-openai 是厂商集成，langchain-community 已宣布 sunset（导入时实测警告），langchain-classic 是兼容包（装 langchain 时带入，存着老 API）。"框架替你做了什么"的标准句式（EX-37-02）：消息对象化、模板注入、统一执行协议接走了；**token 统计、业务正确性、密钥管理从来都在你这边**。对"为了以后换厂商现在就上框架"的回应：换厂商需求强度要先核实；真需要抽象时最小手段是自建薄接口层（本书 llm_client 双模式即示范）或 `init_chat_model`，不必为假设的灵活性引入整个框架。

**5. 工程案例**：见 part07 ch37 判断案例 A/B/C（分类器→裸 SDK、知识库→组件级、运维助手→create_agent）；P1 是"组件级使用"样本（只用了 text-splitters，检索自实现），P2 是"LangGraph"样本——一个仓库里三种决策的活对照。

**6. 追问与回答边界**：
- 追问 1：LangChain 和 LangGraph 的边界？——要点：组件+简单链+标准 Agent 循环 vs 状态机（持久化/恢复/人工介入）；`create_agent` 内部就是一张 LangGraph 图——两者分层不竞争。
- 追问 2：0.x 教程代码现在还能跑吗？——要点：不能，1.x 入口变了（详见题 5-6）；看到老写法先"翻译"再动手。
- 边界：各包长期维护策略（community sunset 后续）以官方发布说明为准；本书只对锁定版本（langchain 1.4.6 / langchain-core 1.6.12）的实测行为负责。

### 题 5-2 [模拟题] LCEL 的 `|` 是什么？相比手写函数组合好在哪？什么时候手写更好？

**1. 问题与考查点**：协议思维——`|` 的本质（Runnable 协议组合）与"第二消费姿势"判断标准；类型错位的真实踩坑是加分证据。

**2. 常见错误回答**："就是函数链式调用的语法糖。"——错过协议价值（batch/stream/async/config 全部继承）；或反向把 LCEL 吹成性能优化（它不是）。

**3. 简洁合格回答**：`prompt | model | parser` 产生 RunnableSequence——本质是 Runnable 协议的组合：每段实现同一套执行入口（invoke/batch/stream/ainvoke/astream），**链自动继承**——所以"换消费姿势"（要流式了、要并发批了、要注入 tags/metadata 配置了）不用改代码。附加价值：可检视（`get_prompts()` 看真实下发的 prompt、`get_graph().nodes` 看结构）、生态组件即插即用（模型/解析器/Retriever 都是 Runnable）。判断标准一句话：**会不会需要第二种消费方式**——两次纯函数调用、永远同步直调，手写更直白。

**4. 深入解释**：LCEL 不做类型适配——真实踩坑：`assign` 把整个 dict 喂给吃 str 的 Retriever，`AttributeError: 'dict' object has no attribute 'lower'`，标准解法是 `itemgetter("question") | retriever` 先把 dict 降为 str（EX-41-03 的案发现场）。RunnableConfig 是横切关注的正规通道：tags/metadata 贯穿每个节点（函数签名带 config 自动注入），asyncio 下比 ThreadLocal 安全；`recursion_limit` 也在同一通道。异常原样冒泡不包装——业务代码沿用 ch08 的异常分层。`.with_retry()`/`.with_fallbacks()` 是管道级重试/降级，参数化强但策略可定制性弱于手写，按需选。调试三板斧：get_prompts / get_graph().nodes / astream_events。

**5. 工程案例**：见 part07 ch40 三个 EX（EX-40-01 管道本质与"链也是组件"、EX-40-02 assign+Parallel+config 贯穿实测、EX-40-03 异常传播与异步流式）；ch41.5 的类型错位踩坑记录；P1 的检索**没有**走 LCEL 是有意选择（内存检索+阈值逻辑用普通函数更可测）——"不用"也是决策。

**6. 追问与回答边界**：
- 追问 1：管道中间类型怎么防错？——要点：管道写完先手动 invoke 看中间类型；关键节点用 RunnableLambda 包类型注解齐全的函数；给每段标注输入输出类型。
- 追问 2：管道里一步很慢怎么控失败影响？——要点：该步内超时+降级值；管道级 with_retry/with_fallbacks；区分可重试（网络类）与不可重试（参数类）。
- 边界：RunnableBranch 与 astream_events 自定义事件未在本书实测（导出已核实存在），以官方文档为准。

### 题 5-3 [模拟题] with_structured_output 和裸 SDK 的 response_format 什么关系？怎么选？

**1. 问题与考查点**：结构化输出的多路线光谱（与题 3-4 呼应）+封装层的价值与边界——考"知道每个抽象底下是什么"。

**2. 常见错误回答**："LangChain 才能做结构化输出，裸 SDK 不行。"——方向反了：response_format/parse 是底层能力（ch24），with_structured_output 是封装；或以为"有了结构化输出就不需要校验"——任何一层都不是终点。

**3. 简洁合格回答**：`with_structured_output(PydanticModel)` 内部走的还是模型的结构化能力，method 参数对应不同约束强度——function_calling（复用工具协议）、json_schema（严格模式）、json_mode（仅保证合法 JSON）——取值与默认随版本与厂商而异，**以所用版本的官方文档为准**。选择原则：裸 SDK 直调场景用 response_format/parse；已在 LCEL 管道里、要和 Pydantic 类无缝衔接、要跨厂商换模型时用 with_structured_output。统一兜底不变：Pydantic 校验+失败回退链（题 3-5 的三层）。

**4. 深入解释**：封装换来的三样东西：错误形态统一（ValidationError 而非原始 JSON 解析错误，`errors()` 机器可读可喂回）、模型可换（同一 Pydantic 类在不同厂商模型间迁移）、Fake 可测（离线测试链路）。约束强度光谱与题 3-4 完全同构：提示词求 JSON（最弱）→ json_mode → function_calling → json_schema 严格模式（最强，需服务端支持）。兼容性核实纪律不变——换"OpenAI 兼容"厂商时 method 支持度必须实测（题 3-8 清单）。

**5. 工程案例**：见 part07 ch38 EX-38-03（PromptTemplate+结构化输出链）；ch45.8 的"分类三段式"（schema 枚举约束→校验失败重试一次→回退 general 通道打标 `classification_fallback=true`）是"结构化输出+路由兜底"的完整样板；P2 的 hypothesize 节点走 `chat_structured` 契约（README 第 4 节第 4 条），Mock/Real 双模式同 schema。

**6. 追问与回答边界**：
- 追问 1：流式+结构化输出能同时要吗？——要点：取决于厂商支持（增量结构化流是较新能力），逐家核实；本书未实测，如实声明。
- 追问 2：模型输出枚举外的值怎么办？——要点：Pydantic 先报错→喂回重试一次→回退通道打标；别让校验异常直接炸调用方。
- 边界：method 各取值在各厂商的覆盖面变化快——面试答"给方法+以实测为准"比背取值稳。

### 题 5-4 [模拟题] 工具执行失败怎么处理？为什么不能 try/except 包住整个 Agent？

**1. 问题与考查点**：错误语义分层——"预期内失败 vs 预期外异常"的两分法；API 细节（handle_tool_error 在哪配）是"真用过"的证据。

**2. 常见错误回答**："工具函数里 try/except 返回 None。"——模型拿到 None 不知道发生了什么，循环继续空转；或外层包一个大 try/except——把业务规则失败和 bug 混为一谈，既剥夺模型自纠机会，又吞掉告警信号。

**3. 简洁合格回答**：两分法：**预期内失败**（业务规则：金额超限、枚举非法、单据不存在）抛 `ToolException` 并配置 `handle_tool_error`（str 或 callable）——异常被转成模型可读文案、作为 ToolMessage 回传，模型可自纠参数或向用户澄清，循环继续；**预期外异常**（bug、基础设施故障）让它炸出来触发监控告警，绝不吞。参数校验类失败单独配 `handle_validation_error`（模型填错参数时的同构机制）。API 细节：`handle_tool_error` 是工具**实例属性**而不是 `@tool` 装饰器参数——写成装饰器参数会 `TypeError`（真实报错，EX-39-02 实测）。

**4. 深入解释**：为什么外层大 try/except 是反模式——所有失败长一个样（模型无法区分"改一下参数就能成"和"系统坏了"），且告警信号被吞。未配置任何错误处理时，工具在 create_agent 里抛异常会让**整次 run 失败**（ToolNode 默认原样抛出）——所以"每个工具的错误策略"是部署清单项不是可选项。错误文案是给模型读的提示词："转账失败：金额超限，建议拆分或转人工审批"比 "error" 有用得多。与 ch50"错误即数据"的同族性：LangGraph 里是捕获预期异常写状态+条件边走降级——失败是合法输出。

**5. 工程案例**：见 part07 ch39——EX-39-02（三种错误策略实测）、EX-39-03（Agent 内恢复链路：ToolException 文案变 ToolMessage、循环继续、最终回答）；P2 的白名单拒绝写审计 `tool_rejected`（拒绝也是信息，README 第 7 节失败路径表）；P1 的 LLMJudge 判定失败按拒答兜底（fail-closed，宁拒不编）。

**6. 追问与回答边界**：
- 追问 1：怎么判断一个失败归哪类？——要点：问"模型知道了能不能做得更好"：能（改参数/换工具/向用户澄清）→预期内；不能（代码 bug）→预期外。
- 追问 2：工具重试和错误回传冲突吗？——要点：重试适合瞬态故障（网络抖动），回传适合业务失败；中间件 ToolRetryMiddleware（默认 max_retries=2、backoff_factor=2.0、初始 1.0s、带抖动）只对"值得重试"的错误。
- 边界：`response_format='content_and_artifact'`（内容+制品分离）等高级形态本书未实测，以官方文档为准。

### 题 5-5 [模拟题] create_agent 替你做了什么？什么时候要展开手写 LangGraph？

**1. 问题与考查点**：六步闭环的"归属感"（每一步谁做的）+护栏意识（中间件）——判断"用过框架"还是"看过框架"。

**2. 常见错误回答**："create_agent 就是个 while 循环封装，没什么。"——说不出它接走了哪六步、护栏在哪配；或不知道它返回什么类型（是一个 LangGraph 编译图）。

**3. 简洁合格回答**：`create_agent(model, tools, system_prompt, middleware, checkpointer, response_format, ...)` 返回 `CompiledStateGraph`——一个 LangGraph 编译图。它替你接走裸 SDK 手写循环的六步（EX-42-01 [3] 的对照）：① 工具 schema 声明与自动 bind_tools；② tool_calls 解析（结构化 dict，不用 json.loads）；③ assistant 消息回写（裸 SDK 最易漏）；④ 按名分发执行；⑤ ToolMessage 生成并配对 tool_call_id；⑥ 循环终止判断。护栏走中间件：ModelCallLimitMiddleware（步数保险丝，exit_behavior 可选抛错或优雅收尾）、ToolRetryMiddleware、SummarizationMiddleware（对接 ch27）、HumanInTheLoopMiddleware（工具级审批）。checkpointer+thread_id 提供跨请求记忆；stream 三模式（values/updates/messages）覆盖调试与 SSE。你仍负责：工具实现本身、权限校验、超时与幂等——模型是"点菜的人"，不是"进厨房的人"。

**4. 深入解释**：何时展开手写图——**控制流要定制**时：tools 前插审批节点、agent 后加证据评估、不同工具不同重试策略（ch46.11 的标准答案）。两者状态结构兼容、迁移平滑，常见路径是"先 create_agent，出现定制控制流需求再展开成图"。bind_tools 是模型与框架的契约点：GenericFakeChatModel 没实现它 → `NotImplementedError`（实测）——教学里三行子类补齐，这个练习本身就是理解"框架与模型的契约在哪"的最快方式。

**5. 工程案例**：见 part07 ch42 三个 EX（EX-42-01 最小循环+六步对照、EX-42-02 checkpointer 多轮+三种流式实测、EX-42-03 护栏两种 exit_behavior+历史考古）；P2 故意不用 ToolNode 而是"先落取证计划、审查后执行"的白名单节点——取证需要 plan→audit→execute 三段，是"定制控制流"的活样本。

**6. 追问与回答边界**：
- 追问 1：怎么防模型刷工具？——要点：三层——recursion_limit 硬保险丝、业务轮次计数提前收尾返回部分结果、工具侧限流（题 6-6 详述）。
- 追问 2：create_agent 的多轮记忆从哪来？——要点：checkpointer+thread_id；没有它两次 invoke 互不相识（EX-42-02 实测 4 条消息快照）。
- 边界：store/cache/transformers 等参数本书未展开，以官方文档为准；中间件清单随版本演进，以 1.4.6 实测为准。

### 题 6-1 [模拟题] LangGraph 的状态更新为什么设计成"部分更新 + reducer"？

**1. 问题与考查点**：通道（channel）模型的机制理解——LangGraph 面试的第一分水岭；能否精确说出覆盖语义、追加语义、add_messages 三态。

**2. 常见错误回答**："每个节点返回整个新状态，后面的覆盖前面的。"——"覆盖"只是无 reducer 字段的默认语义；说不出并行写入怎么办、add_messages 的按 id upsert；更常见的错误是把所有字段都加上追加 reducer（过度设计）。

**3. 简洁合格回答**：每个状态字段是一个通道：不带 reducer 的通道是**覆盖语义**（后写顶掉先写），带 reducer 的通道按你声明的合并函数归并——`Annotated[list, merge]`。节点返回值是**部分更新**（只声明"我要改哪个字段"）。三个设计理由：① 节点解耦——只声明自己关心的字段；② 并行安全——同一超步多节点写入必须有确定的归并规则，否则 `InvalidUpdateError: Can receive only one value per step`；③ 恢复友好——快照+部分更新天然支持重放。`add_messages` 是最常用的消息通道 reducer：新 id 追加（自动把 str/tuple 包装成对应 Message 类型）、同 id **原位替换**（消息级 upsert）。

**4. 深入解释**：字段级类比——覆盖通道是白板（谁最后写是谁的），reducer 通道是签到表（只会变长或按规则归并），同一状态里两类可并存（EX-44-01 的 text 覆盖、findings 追加）。状态设计六条军规（ch44.3）：每个字段先问谁写/谁读/生命周期，答不出就删；追加型字段（日志/证据/轨迹）一律显式 reducer，裸 list 迟早吃掉审计记录；"当前值"字段（category/route）保持覆盖；可序列化优先——对象引用放闭包（工厂注入）不放状态；大对象不进状态（快照体积）；结论与过程分字段。工程坑：`from __future__ import annotations` + reducer 定义在函数内 → NameError（注解变字符串后按模块全局名解析），reducer 必须放模块顶层。

**5. 工程案例**：见 part08 ch44——EX-44-01（最小两节点）、EX-44-02（覆盖/追加/upsert/自定义去重四组实验）、EX-44-03（没有 checkpointer 时第二次 invoke 不记得第一次——"记忆"是 ch47 给的，不是 MessagesState 给的）；P2 的 TriageState 全部追加型字段用 `Annotated[list, merge_lists]`（README 第 4 节第 1 条），天然支持并行写入与恢复重放的幂等合并。

**6. 追问与回答边界**：
- 追问 1：为什么模型重答后消息列表不翻倍？——要点：add_messages 按 id 判重 upsert；适配层复用原消息的 id 就能原位替换。
- 追问 2：两个图报 `Channel 'xxx' already exists with a different type`？——要点：同名字段不同 reducer 在编译期注册冲突；复用同一个 reducer 对象（tests/test_ch47.py 的做法）。
- 边界：Pydantic/dataclass 状态 schema 的序列化细节、RemoveMessage 删除语义，以所用版本官方文档为准。

### 题 6-2 [模拟题] 条件路由和循环怎么写？recursion_limit 应该调多大？

**1. 问题与考查点**：控制流工程化——"判断放节点、分流放边"的职责划分与终止条件设计；recursion_limit 的语义定位是高频陷阱。

**2. 常见错误回答**："把 recursion_limit 调到 1000 就不会报错了。"——把保险丝当设计；或路由函数里直接查库做 IO（决策不可测、边不可审）。

**3. 简洁合格回答**：`add_conditional_edges(节点, 路由函数, path_map)`——路由函数**只读已归并进状态的字段、零副作用零 IO**（"判断"放节点里可测，"分流"放边上可改）；返回值必须在 path_map 全覆盖，缺失值直接 KeyError（fail-fast，配 pytest 锁住）。循环靠回边+终止条件：终止条件是独立可测的纯函数（如"评审通过→END，否则→draft"）。recursion_limit 默认 25，是**保险丝不是设计**——正经循环必须有业务终止条件（轮次/分数上限+达到上限的显式行为：返回部分结果并打标，而不是抛异常），调大它来容纳失控循环=把 bug 配置化。

**4. 深入解释**：四种常见路由模式（ch45.5）：分类路由（一进多出）、闸门路由（不通过出图或去人工）、升级路由（按严重程度分流）、Send 扇出（份数由数据决定）——识别口诀：需求里"根据 X 走不同流程"是①，"不满足不准往下"是②，"越严重越要贵通道"是③，"每个元素都要处理一遍"是④。循环图上线清单：业务上限+达限行为显式定义、每轮朝终止条件前进（零进展轮提前退出）、"0 次循环"与"打满上限"都有测试、**循环体内动作必须幂等**（循环×重试×恢复重跑是副作用重复的三重放大器）。模型分类的路由兜底三段式：schema 枚举约束→校验失败重试一次→回退默认通道并打标。

**5. 工程案例**：见 part08 ch45——EX-45-01（分类路由，Mock/Real 双模式）、EX-45-02（循环与 GraphRecursionError 熔断）、EX-45-03（Send 扇出）；P2 只有一条条件边（assess 后是否进人工审批）——刻意为之："每条条件边都该有测试，边越少越稳"；P2 扩展方向的"多轮取证循环"（缺口→回 extract_evidence）也明确要求 recursion_limit 保险丝（README 第 12 节）。

**6. 追问与回答边界**：
- 追问 1：GraphRecursionError 在"看起来没循环"的图里出现？——要点：两节点互相指或条件边震荡；修法是加尝试次数字段设上限，不是调大 recursion_limit。
- 追问 2：模型输出了 path_map 之外的分类值，生产怎么办？——要点：不能靠崩——schema 兜底+重试一次+回退通道打标（错分的代价是"走了通用通道"，可控可统计）。
- 边界：recursion_limit 的精确计数口径（按超步，每超步 1~2 次节点）以官方文档为准，本书未逐版本核对。

### 题 6-3 [模拟题] 讲清 interrupt 的恢复语义。为什么说"节点会从头重跑"？

**1. 问题与考查点**：本书重点的验收题——恢复语义的**精确**表述；"节点重跑"这个细节直接决定副作用设计，答错它等于没做过生产图。

**2. 常见错误回答**："interrupt 就是断点，恢复后从断点下一行继续。"——错。恢复后**节点从头重跑**，interrupt() 那一行"返回" resume 的值；"下一行继续"的想象会让 interrupt 之前的副作用执行两次。或者把 interrupt 说成异常处理机制（实现上像，语义是流程级暂停）。

**3. 简洁合格回答**：完整序列五步：① 节点执行到 `interrupt(payload)` → 本次 invoke 立即返回，结果带 `__interrupt__`，图**停在检查点上**（payload 成为检查点的一部分——人两天后才批，上下文还在）；② 外部做决定，`invoke(Command(resume=value), config)` 恢复；③ 该节点**从头重跑**，interrupt 之前的代码**再执行一遍**；④ 跑到 interrupt() 时直接"返回" resume 的值，代码继续；⑤ 图继续到下一节点。两条铁律：**interrupt 之前只能放只读操作**；副作用放 interrupt 之后（最好再下一个节点）+ 幂等账本。resume 的值是**一次性的**：被消费后对已完成 thread 重复 resume 不会重放节点。拒绝是一等结果：resume=False 时结论照常产出并留痕（P2 测试锁定）。

**4. 深入解释**：为什么"重跑"是语义内核不是实现瑕疵——它保证恢复路径与正常路径**共享同一段代码**（没有两套逻辑要维护）。三个区分：interrupt 与 sleep 等审批（sleep 占着线程、进程死了全丢；interrupt 把控制权交还，状态在检查点上，进程可释放重启换机器）；interrupt 与"向模型追问"（流程控制 vs 对话——判据：没人回应流程是否永远走不下去）；interrupt 与异常（返回值带 `__interrupt__` 结构，不是抛给调用方）。四种审批形态同一个原语：单票单审/会签（单节点顺序多次 interrupt，各自独立检查点）/或签（interrupt 前查已有批复——只读段，重跑安全）/升级审批（条件边分级）。超时升级 LangGraph 不管——外部定时任务查 `get_state().interrupts` 催办或自动拒绝。

**5. 工程案例**：见 part08 ch48——EX-48-01（人工审批）、EX-48-02（副作用幂等：实验 A 的"执行两次"翻车现场）；P2 的 approval 节点（只读段→interrupt→恢复后执行+账本）与 resume_demo 三段演示（进程内拒绝/跨进程批准/幂等重放）；审批平台字段映射表（thread_id=业务键、payload=申请单、resume 值=审批结果+操作者——resume 必须带操作者身份，审计才能回答"谁批的"）。

**6. 追问与回答边界**：
- 追问 1：恢复时报"没有匹配的 interrupt"？——要点：thread 已消费过该中断或 thread_id 写错；先 `get_state` 看 `next` 与 `interrupts` 再谈恢复。
- 追问 2：节点里有 HTTP 调用怎么办？——要点：读写拆开——重跑段只读（拼上下文），写动作放 interrupt 后过幂等键；不可幂等的（发短信）账本先行（先占 action_key 再发送）。
- 边界：`__interrupt__` 返回结构、多中断并存等细节以所用版本官方文档为准；本书实测基于 langgraph 1.2.16。

### 题 6-4 [模拟题] 恢复后副作用会不会执行两次？怎么保证"恰好一次"？

**1. 问题与考查点**：幂等设计的层次（纪律/账本/审计）——把分布式系统的老问题接到新框架上，考的是迁移能力而不是框架知识。

**2. 常见错误回答**："LangGraph 有事务保证。"——没有；或"我把执行放在 interrupt 后面就安全了"——只挡住了"重跑"，挡不住"执行成功但检查点未落"的崩溃窗口（进程在两者之间挂掉，恢复重放照样再执行一次）。

**3. 简洁合格回答**：三层防线：① **纪律层**——副作用只放在 interrupt 之后（重跑不触碰）；② **账本层**——副作用带唯一 action_key，执行前先查账本（命中即 `already_done` 跳过），执行后记账——进程崩溃在"已执行未提交检查点"窗口时，重放命中账本不重复执行；③ **审计层**——每次副作用对应一条人工决策（审计 `approval.*` 事件）+ 一条账本记录，可对账。语义上的诚实表述：这是 **at-most-once 生效**（at-least-once 执行+幂等去重），不是分布式意义的"恰好一次"。Java 对照：这就是幂等消费的唯一业务键+Saga 参与者去重表——经验直接平移。

**4. 深入解释**：账本的键设计：action_key 要含业务维度与轮次（P2 的 `restart_service:payment-service:incident-payment-outage`——动作:目标:事件单），唯一索引兜底并发。RetryPolicy 重试期间节点整体重入——重试也放大副作用，所以**重试原则上只给只读节点**（P2 的只读取证查询是天然候选）。恢复调用的输入语义：恢复 invoke 只传增量或 None——传"完整历史"会把旧消息再追加一遍（消息翻倍，ch47.9 的调试题）。

**5. 工程案例**：P2 的 actions_ledger.jsonl 与 `already_done` 状态；测试 `test_replayed_resume_does_not_repeat_side_effect`（重放命中账本不重复执行）与 `test_resume_state_consistent_with_prior_snapshot`（恢复不破坏事实）；ch48.7③ 的修复顺序（先把副作用挪到 interrupt 之后，再加账本——无法挪动的遗留副作用至少要有 action_key 去重）。

**6. 追问与回答边界**：
- 追问 1：不可幂等的副作用（发短信）怎么办？——要点：账本先行——先占 action_key 再发送；发送失败标记待补偿而不是盲目重发。
- 追问 2：账本和检查点要同一个存储吗？——要点：不必——账本是业务留痕（JSONL/表），检查点是执行机制；但对账要用同一个 action_key 字符串。
- 边界：多副本下账本去重键要进唯一索引；本书教学实现为单文件，未做并发压测（如实声明）。

### 题 6-5 [模拟题] checkpointer 和"把对话历史存数据库"有什么区别？thread_id 怎么设计？

**1. 问题与考查点**：持久化模型的本质（完整执行状态 vs 消息列表）+ thread_id 命名纪律——后者是生产事故高发区。

**2. 常见错误回答**："就是把 messages 存起来，下次拼上。"——那是历史管理的退化用法；checkpointer 存的是**图的完整执行状态**（中间字段、下一步是谁、待决中断信息），因此能精确恢复到任意超步——历史存库只是它的一种退化形态。thread_id 用随机 UUID 也是常见错误——出事时对不上业务。

**3. 简洁合格回答**：checkpointer 在**每个超步之后**自动快照整图状态，thread_id 是会话主键；查询接口 `get_state` 看四个字段——`next`（停在谁/完没完：`()`=完成、`('approval',)`=停在审批）、`values`（状态事实）、`interrupts`（待决事项）、`metadata`（步数与时间戳）；`get_state_history` 翻完整轨迹；历史快照支持重放（时间旅行）。thread_id 命名三选一并写进团队约定：业务单据号（对得上账，P2 的 incident-XXX）、`user_id:session_id`（客服隔离）、UUID（仅当流程与业务实体无对应）；反模式：用户级 ID 让多轮业务共享一个 thread——历史串台。存储选型：InMemorySaver（进程内）→ SqliteSaver（单机/演示，**单写者模型**不是多副本方案）→ PostgresSaver（多副本共享检查点库，任何副本可接手任意 thread）。

**4. 深入解释**：恢复前的健康检查"三看"（get_state 看 next/values/metadata 再动手——P2 resume_demo 进程 2 的标准动作）。检查点**不是审计日志**——它是执行机制不是合规记录，审计另建（P2 的 JSONL 审计）。快照含敏感业务状态→存储权限按敏感数据管理（Postgres 账号/SQLite 文件权限与业务主库同级）。schema 演进纪律：加字段可以、删字段慎（老 thread 恢复时报键缺失）、语义只追加式变更、schema_version 打标。性能账：成本大头是状态体积——先瘦身状态再谈优化（控制字段比关快照有效）。

**5. 工程案例**：见 part08 ch47——EX-47-01（InMemory+thread 隔离，两轮 6 个检查点）、EX-47-02（SqliteSaver 两个独立 with 块模拟两进程接力）、EX-47-03（时间旅行重放/分叉）；P2 用 incident_id 作 thread_id（README 第 4 节第 5 条）；SqliteSaver 依赖 langgraph-checkpoint-sqlite（本书实测 3.1.2）。

**6. 追问与回答边界**：
- 追问 1：每步都写快照，慢吗？——要点：内存微秒级/本地一次写；状态瘦身优先于关快照；序列化可自定义。
- 追问 2：时间旅行在生产有什么正经用途？——要点：修复类（答错那轮换输入重跑）、排障类（事故现场检查点重放定位）、测试类（从 interrupt 检查点重放验证账本幂等——P2 就这么测）。
- 边界：PostgresSaver 的部署形态、官方 saver 的 TTL/清理接口以官方文档为准；本书只实测了 InMemory 与 Sqlite。

### 题 6-6 [模拟题] LangGraph 里的工具调用循环怎么搭？模型"刷工具"怎么防？

**1. 问题与考查点**：双节点结构与三层防护——同时考"模型决定/程序执行"的分离意识与测试方法。

**2. 常见错误回答**："写个 while True 调模型直到它说完成。"——终止依赖模型**自我声明**，模型抽风就是死循环+账单失控（ch42 开头的真实事故叙事：同参数重复调用 20+ 次）；或者不给 ToolMessage 带 tool_call_id（模型读到错位上下文）。

**3. 简洁合格回答**：标准双节点：agent 节点（调模型，AIMessage 可能带 tool_calls）→ 条件边（有 tool_calls 去 tools、没有去 END）→ tools 节点（ToolNode 或白名单手工执行，ToolMessage 按 tool_call_id 配对）→ 回边到 agent。防刷三层：① **recursion_limit 硬保险丝**（默认 25）；② **业务层轮次计数**——tool_rounds 自增 reducer，达到上限提前收尾并返回"已查到的部分结果"+打标；③ **工具侧限流**（幂等键与退避同样适用于工具执行）。工具失败处理与题 5-4 同源：预期内失败转模型可读文案，或"错误即数据"（捕获写状态+条件边降级——异常也是证据）。

**4. 深入解释**：模型节点与工具节点分离的测试红利——脚本化 MockLLM（工厂闭包注入）驱动循环，`llm.calls` 断言"模型收到了什么"（调用次数与消息快照）；配合 `stream_mode="updates"` 看"图执行到哪"——**模型视角+图视角**双时间线，能回答工具循环排障三大问题：模型没调对工具？工具没返回对结果？循环没按预期收敛？ToolNode 的 `handle_tool_errors` 参数可把异常转文本回传，但生产更推荐错误即数据（P2 的 `tool_error` 证据项直接参与"证据不足"结论）。

**5. 工程案例**：见 part08 ch46——EX-46-01（两轮工具循环：消息序列 6 条、call_001/call_002 配对，Mock 脚本驱动）；ch42 的 create_agent 是同一循环的框架版；P2 **故意不用 ToolNode**——取证计划要"先落 plan、审查后执行"（README 第 4 节第 4 条），这是"控制流定制"的对照样本（与题 5-5 呼应）。

**6. 追问与回答边界**：
- 追问 1：ToolMessage 丢了 tool_call_id 会怎样？——要点：一轮可以并行多个工具调用，id 是模型把结果对回请求的唯一依据；错配让模型读到错位上下文——agent 输出错乱的经典来源。
- 追问 2：达到轮次上限时怎么向用户表达？——要点："已查到 X，Y 因轮次上限未完成"——把上限写进结论而不是静默截断；打满上限的 thread 进告警名单。
- 边界：并行工具调用的开关参数名随 SDK 版本与厂商而异，以所用 SDK 文档为准。

### 题 6-7 [模拟题] LangGraph 的并行是真并行吗？并行分支写同一字段会怎样？

**1. 问题与考查点**：超步（Pregel）模型与 reducer 的配合——区分"并发调度"与"并行执行"，以及归并冲突的机制与修法。

**2. 常见错误回答**："当然是多线程并行。"——图默认在同一事件循环里按超步调度；或"并行分支各自覆盖，最后写的赢"——这正是 `InvalidUpdateError` 的来源（无 reducer 字段一超步只能收一份更新）。

**3. 简洁合格回答**：图按 **Pregel 超步**推进：同一超步的分支**并发调度**（IO 密集型节点天然并发；CPU 密集的真并行要在节点内部用线程/进程做——题 1-1/2-1 的选型结论在这里继续生效），图的职责是编排与归并。并行分支写同一个**无 reducer** 字段 → `InvalidUpdateError: Can receive only one value per step`；解决：给字段声明追加/求和类 reducer（归并规则由你定义），或把写入错开超步。静态并行（多边同发）适合份数编译期已知；份数运行时才定用 **Send** 扇出（Map 节点收到的是单份 arg 而非整图状态；combine 必须只从 Map 有入边，靠超步屏障等到所有份到齐）。

**4. 深入解释**：一路失败怎么办——默认异常冒泡终止整图；要"部分成功"语义就在分支节点捕获**预期内**异常写错误标记（错误即数据），汇总节点按标记区分处理——P2 的 `tool_error` 证据即此模式。子图封装的判据：被多张图复用且有自己的内部状态才值得子图化（子图可独立测试/编译/加检查点）；"把节点函数抽成模块"只是代码组织不是子图。归并的确定性：超步内写入顺序无关紧要——带 reducer 的字段归并结果确定（求和/追加满足结合律）。

**5. 工程案例**：见 part08 ch49——EX-49-01（并行归并与 InvalidUpdateError 的修复现场）、EX-49-02（子图）；P2 扩展方向的三路并行取证（error_events/service_status/dependency_map 三路 Send + reducer 归并，README 第 12 节）。

**6. 追问与回答边界**：
- 追问 1：并行节点的写入顺序确定吗？——要点：对带 reducer 的字段，归并结果与到达顺序无关（结合律保证）；对覆盖字段才有"谁后谁赢"。
- 追问 2：怎么压测并行图的吞吐？——要点：瓶颈通常在模型 API（并发限制见题 2-4），图本身开销在快照与调度；先测下游再谈图。
- 边界：超步调度的线程模型细节以官方文档为准；本书未做并发基准测试（如实声明）。

### 题 6-8 [模拟题] LangGraph 应用怎么测试？"图没法测"你怎么反驳？

**1. 问题与考查点**：测试策略分层——"写过生产图"的照妖镜；能否给出四层地图与恢复语义的可信测法。

**2. 常见错误回答**："图是框架跑的，测不了。"——图的每层都可测；或只写一个"跑通就行"的冒烟——没有分层，失败定位靠猜；或测试间共享 InMemorySaver/审计文件（互相污染，时绿时红）。

**3. 简洁合格回答**：四层测试地图：① **节点直调**——节点是 `(state) -> dict` 纯函数，绕过图直接调，最快、覆盖业务分支；② **Mock 注入整图**——模型节点用工厂闭包创建（`make_agent_node(llm)`），测试注入脚本化 MockLLM：脚本逐条返回预置回答，**游标耗尽抛错绝不编造**（模型行为超出剧本会暴露而不是被洗白）；③ **快照断言**——`get_state` 断言 next/values/metadata/interrupts；含 interrupt 的图两段式：先断言 `__interrupt__` 暂停点，再 `Command(resume=...)` 断言终点；④ **失败路径**——`pytest.raises(GraphRecursionError/KeyError/RuntimeError 脚本耗尽)`。外加**框架契约测试**（锁 RetryPolicy 默认值、关键报错文案——升级版本先红）。恢复语义测试三步：断言暂停点（next+interrupts 载荷）→ 恢复后**逐字段对比**中断前后快照的事实字段（假设/告警不变）→ 时间旅行回到中断检查点重放，验证账本命中不重复执行。

**4. 深入解释**：Mock 脚本即"模型行为剧本"——测试读起来像剧本（第 1 轮要查订单→第 2 轮要查政策→第 3 轮总结），非模型同事也能 review；一个测试只回答一个问题（"正常路径+审批+幂等"分三个测试）；fixture 隔离（tmp_path+每测试新建 saver+审计目录）。"怎么测模型乱来"两问两答：控制流层用 Mock 模拟乱来剧本，验证防线真实生效（白名单拒绝/证据不足拒答）；模型层用评估集量化发生率——两层合起来回答"乱来了会怎样 + 多常发生"。CI 策略：节点+整图全量秒级；Prompt 回归与控制流回归分 job；真模型评估夜间跑（有成本）。

**5. 工程案例**：见 part08 ch51 EX-51-01（四种姿势全 PASS）与 tests/test_ch51.py；P2 的 14 个测试是四层地图的工程化样本（单节点白名单×2+只读+工具幂等 / 整图正常与三类失败 / 快照恢复一致与 thread 隔离 / recursion_limit+人工拒绝+重放幂等+审计完备）；`test_resume_state_consistent_with_prior_snapshot` 的逐字段对比是"恢复不破坏事实"的标准测法。

**6. 追问与回答边界**：
- 追问 1：快照断言锁多细？——要点：锁 next/values 关键字段与 metadata["step"] 量级，别锁完整轨迹的每一步（step 数随实现浮动）。
- 追问 2：真模型要不要进 CI？——要点：PR 只跑 Mock（秒级、零成本）；夜间跑评估集（golden set 断言规则化、不断言全文）。
- 边界：get_state_history 的轨迹断言粒度、契约测试覆盖哪些报错文案，按团队需要裁剪；本书给的是 1.2.16 实测样本。

### 专题六 · 30 分钟自测（模拟口试）

> 用法：同前。本专题评分重点：恢复语义与幂等的题（3/4/5）必须出现"节点从头重跑"与"崩溃窗口"这两个关键词——缺失直接不合格。

## 12.7 专题七：Agent 与 MCP

> 对应正文：第九部分大纲（ch52~ch56，正文交付前以本节与 examples/ch52、ch53、ch55 示例及项目二为准）。这个专题考察"判断力"：Workflow 还是 Agent、单 Agent 还是多 Agent、工具怎么治理、MCP 到底解决什么——全部是取舍题，没有背诵题。

### 题 7-1 [模拟题] 什么任务该用 Agent，什么该用固定 Workflow？

**1. 问题与考查点**：三条硬问题（ch52）——这是"能不能上生产"的判断题；能否把"自主性"当成要花钱买的能力来评估。

**2. 常见错误回答**："复杂的用 Agent，简单的用工作流。"——"复杂"不是判据；或"Agent 更智能所以优先 Agent"——把概率决策当免费午餐，忽略成本不可控与不可测试的代价。

**3. 简洁合格回答**：三问（EX-52-01 的决策表）：**Q1 路径能不能提前画出来？**（能→Workflow：控制流写死反而可测试、可审计）；**Q2 失败了要不要"换一条路再试"？**（要→Agent 的自主改道有价值）；**Q3 出错时业务能接受多大代价？**（代价高→收敛控制流、加人工审批）。组合判断：路径可画=Workflow；路径不可画但代价高=Agent+审批+预算护栏；代价低且探索性强=裸 Agent。一句话定性：Agent 的"自主"是在**有限循环内**按概率选下一步，不是真有意图——护栏（步数上限/审批）是默认配置，不是可选优化。

**4. 深入解释**：决策表要做成**代码**（EX-52-01：需求特征打分→结论+理由），评审时跑给架构师看——比"业界都在用"可辩护。治理抓手是 Agent loop 的**外部可观察行为**（EX-52-02）：步数、工具调用轨迹、终态——这些都可记录、可回归。plan-verify 循环（EX-52-03：先规划后验证）是给 Agent 加刹车的中间形态：模型仍自主，但每步产物过验证节点。需求漂移预案：Workflow 半年后加需求可能变成 Agent 形态——重新跑决策表，别沿用口头结论（与 ch37 的决策表同构）。

**5. 工程案例**：P2 是"Workflow 为主+一个审批闸门"：主干线性（解析→预筛→取证→假设→评估→结论），因为路径可画（Q1=能）；"要不要重启"用 interrupt 人工决策而不是让模型决定（Q3=代价高）。对照 ch42 的天气 Agent（代价低、探索性）——同一本书里两个形态各有其位。

**6. 追问与回答边界**：
- 追问 1：Agent 一定比 Workflow 贵吗？——要点：轮数不可控=成本不可控；预算护栏（步数上限/并发限制）把成本上限变成配置项，这是 Agent 方案的必备件。
- 追问 2：怎么向老板解释"看起来简单"的需求不该用 Agent？——要点：用 Q1——路径能画出来时，Workflow 每一步可测试可审计，Agent 每一步都是概率；"可控性是需求，不是偏好"。
- 边界：ch52~ch56 章节号按 syllabus 引用（正文交付前以本节与示例代码为准）；示例在 examples/ch52_workflow_agent、ch53_single_vs_multi。

### 题 7-2 [模拟题] 什么时候需要多 Agent？单 Agent 不够用的信号是什么？

**1. 问题与考查点**：架构拆分判断——考"不堆概念，给判断标准"（ch53 的教学目标）；能否说出多 Agent 的真实成本而不是画组织架构图。

**2. 常见错误回答**："多个 Agent 协作更智能，铁定要上多 Agent。"——多 Agent 的通信协议、状态一致性、失败传播、排障复杂度都是真实成本；或把"多工具"误当"多 Agent"（一个 Agent 挂 20 个工具仍是单 Agent）。

**3. 简洁合格回答**：单 Agent 优先。拆多 Agent 的三个信号：① **上下文超载**——提示词+工具清单+历史互相稀释，模型开始忘事、选错工具；② **权限要隔离**——不同环节权限边界不同（查询 Agent 只读、执行 Agent 受审批），拆开后各 Agent 护栏独立；③ **并行分工**——多路独立任务要并行推进。多 Agent 的三个成本：通信消息协议（谁说什么、什么格式）、共享状态归并（谁的事实为准）、失败传播与级联重试（一个 Agent 挂了下游怎么办）。先单 Agent+好工具，撑不住了再拆。

**4. 深入解释**：多 Agent 的常见形态（主管-执行者/流水线/对等协作）各有失败模式（主管成瓶颈、流水线误差传播、对等协作死锁）——**形态不重要，"状态怎么归并、失败怎么传播"才重要**，回答时主动把话题拉到这两点。LangGraph 的落地手段就是子图+共享状态 schema（ch49）：子图有自己的状态与检查点，边界是控制流级的。评估也随拆分变难：每个 Agent 独立四层测试（题 6-8）+ 集成测试锁消息协议（协议即契约）。

**5. 工程案例**：见 examples/ch53——EX-53-01（单 Agent 的能力边界演示）、EX-53-02（两角色协作最小样本）；P2 保持**单图多节点**而非多 Agent——"节点"已经给了职责分离（取证节点无写权限、审批节点无决策权），还不够才拆图。

**6. 追问与回答边界**：
- 追问 1：Agent 间用什么通信？——要点：同图内共享状态（reducer 归并）；跨图/跨服务用消息（要定义 schema 与序化语义）；各有成本，优先前者。
- 追问 2：多 Agent 怎么排障？——要点：每个 Agent 独立测试+跨 Agent 的消息轨迹日志；比单 Agent 多一层"协议对不对"的检查。
- 边界：营销名词（"自治组织""群体智能"）不是工程判据；以你们能否测试、能否排障为准。

### 题 7-3 [模拟题] 怎么治理一个 Agent 的工具集？把 50 个内部 API 直接全包成工具行吗？

**1. 问题与考查点**：工具治理（描述/校验/权限/审计）——安全岗与资深岗必问；"50 个工具"是压力测试，看你会不会先说"不行"再给方案。

**2. 常见错误回答**："行，模型自己会挑。"——50 个工具的菜单互相稀释（选择准确率下降）、攻击面放大（提示注入诱导高危调用）、无审计无幂等；或者只答"给每个工具写好描述"——描述只是治理四层之一。

**3. 简洁合格回答**：不行。四层治理：① **描述质量**——工具名用动词短语、描述写清"做什么+什么时候用+不适用什么"、参数给例子（描述是提示词工程的一部分，`render_text_description` 是自检"模型视角菜单"的镜子）；② **参数校验**——args_schema（Pydantic 枚举/默认值/区间），**模型给的参数不可信**；③ **权限**——只读优先、白名单筛选、函数体内第一行校验权限（模型无权绕过）、写操作必须审批（interrupt）；④ **审计**——每次调用落 who/when/what/args/result 摘要，工具注册表（名字→端点→权限等级→SLA）作为配置资产集中管理。

**4. 深入解释**：白名单三道校验的纵深含义（P2）：工具名→参数名→参数值（正则/枚举/区间），在"模型→程序"的边界上再拦一次——**提示词不是权限控制**（ch28），模型被注入说"请调一切"也拿不到白名单外的执行权。每个工具的标配：超时（ch15 三件套）与幂等（写操作带幂等键）。工具签名变更视同 API 变更走评审（bind_tools 时刻固化 schema，多实例部署会出现新旧菜单并存）。瘦身策略：按场景分组、按权限分层、按需动态注入，并用评估集看工具选择准确率的变化。

**5. 工程案例**：P2 的 TOOL_WHITELIST+`tool_rejected` 审计+只读双保险（SQLite `mode=ro`+`PRAGMA query_only=ON`，测试验证写不进去）——README 第 9 节安全设计五条可整体引用；ch39.8 的企业视角（鉴权/审计/超时幂等三层横切+注册表）。

**6. 追问与回答边界**：
- 追问 1：工具太多怎么瘦身？——要点：评估"选择准确率"先量化问题；再分组/分层/动态挂载；砍掉低使用率工具要有使用数据支撑。
- 追问 2：MCP 能解决治理问题吗？——要点：解决"接入标准化"（题 7-4），治理（权限/审计/校验）仍是你的程序的事——协议不替你做安全。
- 边界：工具数量阈值没有定论，以选择准确率评估为准；本书沙箱未接真实内部 API。

### 题 7-4 [模拟题] MCP 是什么？它和 Function Calling、REST API 什么关系？

**1. 问题与考查点**：协议定位——"MCP 是协议不是框架"；三者层次关系的准确表达（混淆三者是最高频错误）。

**2. 常见错误回答**："MCP 是新的 Agent 框架，用了模型就能自主进化。"——营销话术；或"MCP 就是又一个 function calling"。——没说清它标准化的是"工具从哪来、怎么发现、怎么调"这一层，也没说清执行权在哪。

**3. 简洁合格回答**：MCP（Model Context Protocol）是连接模型应用与外部能力的**开放协议**：角色三件——host（模型应用）、client（host 内的协议客户端）、server（能力提供方）；server 暴露 tools（可被调用的函数）、resources（可读取的数据）等能力（细节以当前官方规范为准）。与 Function Calling 的关系：**互补不在一个层**——FC 是"模型点名工具"的模型侧机制（ch24 的闭环），MCP 标准化的是工具的**发现、描述与接入**；MCP server 的工具最终仍经 tool_calls 协议被模型点名。与 REST 的关系：REST 是通用接口风格，MCP 在其上加了"能力发现+统一工具描述+会话语义"，让同一个 host 接不同 server 不用各写适配。**执行权依旧在 host 程序**——MCP 不改变"模型点名、程序执行"的安全模型。

**4. 深入解释**：落地形态（ch55 示例）：stdio 传输——host 把 server 作为子进程拉起，stdin/stdout 承载 JSON-RPC 消息（**stdout 只能是协议帧**：print/logging 走 stderr，否则协议帧被污染、client 解析直接失败——ex_55_02 文件头明确写了这条纪律）；另有 HTTP 类传输用于远程常驻服务（细节以官方规范为准）。价值判断：能力多、来源杂、要跨团队复用时，MCP 的标准化划算；两三个内部工具直接写 @tool 更简单——**协议也有接入成本**。Java 侧对接思路：把已有 Java 服务包成 MCP server（或经网关暴露），Python host 经 client 接入——ch56 的方向。

**5. 工程案例**：examples/ch55_mcp——ex_55_02 最小 stdio server（2 工具+1 资源+1 提示模板，FastMCP 风格）、ex_55_03 client、ex_55_04 langchain-mcp-adapters 适配示例；server 端把 ValueError 转成协议级错误响应的做法（工具异常→协议错误帧）。

**6. 追问与回答边界**：
- 追问 1：MCP server 崩了 Agent 会怎样？——要点：工具不可用是预期内失败——转成模型可读反馈或错误即数据；host 要做连接管理与超时。
- 追问 2：MCP 的安全边界？——要点：server 是信任边界外的能力提供方——白名单、参数校验、审计在 host 侧照做不误。
- 边界：MCP 规范演进快（传输与能力集都在加版本），本书只对示例演示的 stdio 形态负责，其余以官方文档为准。

### 题 7-5 [模拟题] stdio 模式下为什么一句 print 就会把 MCP 弄挂？生产用哪种传输？

**1. 问题与考查点**：传输机制的工程细节——区分"读过文档"与"踩过坑"；能否给出传输选型与调试方法。

**2. 常见错误回答**："print 只是打个日志，没影响。"——stdio 下 stdout 就是协议通道，print 进去等于往 JSON-RPC 流里塞脏数据，client 解析直接失败（这是"协议通道被业务输出污染"的经典事故）。

**3. 简洁合格回答**：stdio 传输里，host 把 server 作为子进程拉起，双方用 stdin/stdout 交换 JSON-RPC 消息——**stdout 被协议独占**，任何 print/logging 必须走 stderr（本书 ex_55_02 文件头即此纪律；验证方法是"单独启动 server，stdout 必须沉默"）。生产选型：本地同机、开发/个人场景用 stdio（免端口免鉴权，进程父子关系即信任）；远程/共享服务用 HTTP 类传输（server 常驻、可鉴权可扩缩）——具体传输类型与握手细节以所用版本官方规范为准。两条通用纪律：连接生命周期管理（server 崩溃重启、健康检查）、协议版本协商失败 fail-fast 并留日志。

**4. 深入解释**：为什么 stdio 适合本地——零网络配置、随 host 生命周期启停；代价是单机、单连接、调试要"两看"（client 日志看协议帧、server stderr 看业务日志）。HTTP 类传输引入的是网络世界的问题——超时/重试/鉴权/TLS，ch15 的稳定性清单照用；这正好呼应 Java 工程师的老经验："协议换成网络协议后，稳定性课单一个不少。"

**5. 工程案例**：ex_55_02/ex_55_03 的 server/client 对（含 stdout 沉默验证）；server 端 `raise ValueError(f"计划 {plan_id} 不存在")` 被协议层转成错误响应——业务异常与协议错误的分界示范。

**6. 追问与回答边界**：
- 追问 1：怎么调试 stdio server？——要点：先单独验证"启动不打印"；client 侧开协议日志；业务日志全部引到 stderr/文件。
- 追问 2：多工具 server 要不要拆？——要点：按权限与变更频率拆（高危独立部署），与题 7-3 的治理一致。
- 边界：各传输的正式名称与参数以官方规范为准；本书沙箱只演示了 stdio，HTTP 传输未实测——如实声明。

### 题 7-6 [模拟题] 一个要跑 10 分钟的 Agent 任务，HTTP 接口怎么设计？

**1. 问题与考查点**：长任务模式——请求内循环/异步任务化/分步推进的三形态选型（ch46.8）；考"HTTP 语义与长任务天然冲突"的意识。

**2. 常见错误回答**："把网关超时调大。"——占住连接 10 分钟：超时重试、负载均衡、用户体验全坏；进程一重启任务全丢；或者"让前端一直转圈等"——同样的问题，只是把锅甩给了浏览器。

**3. 简洁合格回答**：三形态：① **请求内循环**——一次 HTTP 里跑完整图，适合轮数可控、总时长 <10s（简单，但循环期间占着连接）；② **异步任务化**（本题答案）——请求只做"受理"，立即返回 thread_id+任务号；图在后台 worker 推进，checkpointer 持久化保证进程重启可续；前端轮询 `get_state` 或订阅 SSE（stream_mode=updates 给"取证中…评估中…"的节点级进度）；工具循环长、涉及慢工具、要人工审批时的标配；③ **分步推进**——每次请求推进一步（利用检查点续跑语义），仅强交互向导用。配套设计：任务状态机（受理/运行中/等审批/完成/失败）、审批走 interrupt+回调、受理接口幂等（同业务单号返回同任务）。

**4. 深入解释**：为什么形态 2 与 LangGraph 天然适配——状态在检查点上，worker 可无状态化、换机器接手（凭 thread_id 寻址）；超时语义分层（受理响应秒级、任务本身无 HTTP 超时、审批有 SLA+外部超时升级——题 6-3）；取消语义：取消=写状态标记+节点在安全点检查标记，不是 kill 进程。与 Java 集成的分工：Java 网关只转发受理与查询接口，长连接 SSE 可透传（ch57 的模式）。

**5. 工程案例**：ch46.8 的三形态与选型判断（"循环轮数 ≤3 且总时长 <10s 用形态 1；轮数不可控或慢工具用形态 2"）；P2 的 CLI 是形态 1 的教学版，服务化路线即形态 2（README 第 12 节扩展方向）；审批对接 IM（interrupt 载荷推审批卡，`Command(resume)` 由回调驱动）。

**6. 追问与回答边界**：
- 追问 1：受理后重复提交怎么防？——要点：幂等键（业务单号）+thread_id 复用：同键返回同任务，不重复起跑。
- 追问 2：worker 挂了任务怎么续？——要点：新 worker 凭 thread_id get_state"三看"（next/values/metadata）后继续推进——检查点是续跑的依据。
- 边界：任务队列选型（Celery 类/云服务/自研）不在本书展开，按团队现状；形态 3 的适用面很窄，别当默认答案。

### 题 7-7 [模拟题] 你怎么评估一个 Agent 系统的好坏？

**1. 问题与考查点**：评估意识从 RAG 延伸到 Agent——结果质量+过程约束双维度；能否给出可落地口径而不是"看效果"。

**2. 常见错误回答**："看它能不能完成任务。"——没有可计算定义；或只看答案质量不看步数/工具调用/成本——一个"答对了但刷了 30 次工具"的 Agent 是事故不是功能。

**3. 简洁合格回答**：两个维度：① **结果质量**——任务成功率（场景评估集：给定输入+期望终态）、拒答/升级正确率（该交人工的交了吗——P2 的 UNKNOWN+缺口清单）、结论可追溯性（每个结论能对应到证据与审计记录）；② **过程指标**——步数分布、工具调用次数与选择正确率、成本（token/调用数）、时长分布。护栏触发本身是信号：recursion_limit 或步数上限**打满的 thread 就是问题名单**（提示词或工具有毛病）。全部进回归：场景评估集+Mock 剧本控制流回归（题 6-8）+真模型夜间评估。

**4. 深入解释**：Agent 评估与 RAG 评估的增量——路径不唯一使"对齐标准答案"不适用，改评"**终态等价类+过程约束**"（没越权、没超预算、证据留痕）；消融实验定位组件价值（去掉某个工具/提示词段落后成功率变化多少）；线上反馈闭环（用户采纳/撤销动作落库回填评估集）。成功率门槛的回答姿势：没有普适数——低风险场景可灰度试、高风险动作必须人工闸门；指标是持续运营对象，不是一次性门槛。

**5. 工程案例**：P2 的评估口径三条（拒答正确率/结论可追溯性/副作用安全，README 第 8 节）；14 个测试是"过程约束"的离线版（白名单拒绝、递归熔断、重放幂等都是过程指标的可测形态）。

**6. 追问与回答边界**：
- 追问 1：模型升级后 Agent 行为漂移怎么办？——要点：契约测试+场景回归集双保险；版本三元组（模型/Prompt/工具清单）记录，变更可解释。
- 追问 2：怎么区分"模型变笨"和"提示词变坏"？——要点：固定模型跑 Prompt 回归、固定 Prompt 跑模型评估——一次只动一个变量。
- 边界：Agent 评估的学界标准不在本书范围；本书给的是工程可落地的口径（终态+过程+回归）。

### 专题七 · 30 分钟自测（模拟口试）

> 用法：同前。本专题评分重点：每题都要"先给判断、再给判据"——只报概念不给取舍的，按不合格处理。

1. **[模拟题] 用三问法现场判断"发票审核助手"该 Workflow 还是 Agent。** 评分要点——Q1 发票类型与审核规则能否画全（大多能→Workflow 为主）；Q2 证据缺失要不要改道（可加有限 Agent 环节）；Q3 误判代价（高→人工闸门）；能说出"混合形态：Workflow 主干+受限 Agent 环节"加分。

5. **[模拟题] 给"跑 10 分钟的 Agent"画受理-轮询-审批时序图。** 评分要点——受理（幂等键→thread_id+任务号）→后台推进（checkpointer）→轮询 get_state 或 SSE→审批 interrupt/回调 resume→终态；说出"进程重启可续"的依据。

## 12.8 专题八：系统设计与项目深挖

> 对应正文：全书综合 + 两个项目（projects/p1、p2）的"面试讲法"小节 + 第十部分大纲（ch57~ch61，正文交付前引用其编号）。设计题与项目深挖题考的不是知识量而是**决策质量与真实性**——评分者暗中打分的三件事：约束先行（先问需求再画图）、权衡显式（每个选择说得出"放弃了什么"）、诚实边界（不知道就说不确定）。

### 题 8-1 [模拟题] 现场设计：给一家 500 人的公司做一个内部制度知识库

**1. 问题与考查点**：RAG 全链路的工程决策与约束访谈能力——白板题的开场 30 秒（问不问需求）就分出了档次。

**2. 常见错误回答**：上来就画"向量库+LLM"两框图——没有需求访谈（权限模型？更新频率？拒答口径？）、没有评估方案、没有失败路径；或者堆名词（"用向量数据库+Agent+微调"）——每个名词都是风险。

**3. 简洁合格回答**（按白板顺序展开）：
- **先问四个约束**：知识规模与更新频率（几百篇、月更）、权限模型（部门隔离？租户？）、实时性（无）、拒答口径（宁可拒答不编造）。
- **入库管线**：文档源（Markdown/网盘同步）→加载清洗（front-matter 带权限元数据，必需字段缺失拒绝入库）→两级切分（标题分节+节内递归，200/30 量级起步，评估定参）→嵌入入库（记录模型版本，换模型全量重建）。
- **检索**：权限过滤先行（元数据 filter 下推）→向量+BM25 两路（BM25 用现成 ES）→RRF 融合→top-k+阈值（评估集校准）。
- **生成**：编号证据+token 预算装箱（整块丢弃）→结构化输出（answer/citations 分字段）→程序校验引用（失败回退抽取式）→拒答双保险。
- **服务与集成**：FastAPI 暴露 /ask 与 /ask/stream（SSE：meta 引用先行→delta→done）；Spring 侧经网关转发，身份从 JWT 注入，Python 侧不解析消息文本做授权。
- **质量与运维**：评估集（应答+应拒两类）接 CI、结构化日志+trace_id、usage 成本记录、文档同步 webhook、审计留存。

**4. 深入解释**：这张图的每一层都对应 P1 的一个选型决定（README 第 2 节的表格）——面试时可以直接说"这个设计我在一个可复现的项目里完整实现过"，然后引用 25 chunk/16 条评估集/四指标/17 个测试这些锚点。规模演进点主动给：千级 chunk numpy 全量扫描仍可行，十万级换 ANN+过滤下推。成本杠杆：top_k 与 chunk_size 直接乘在输入 token 上、高频 FAQ 可走便宜模型或纯检索直答、拒答与限流拦截无效流量。"先写评估口径再写代码"作为立项纪律收尾——RAG 是概率系统，没有评估口径的项目无法验收。

**5. 工程案例**：P1 全流程（12 篇合成文档→25 chunk→四指标评估→SSE 协议→pytest）就是这道题的可运行参考答案；引用数字时声明"合成语料校准"（题 8-9 的口径纪律）。

**6. 追问与回答边界**：
- 追问 1：为什么不用现成知识库产品？——要点：按需求答——要权限下推+拒答口径+引用协议的定制控制；采购与自建的边界按团队能力与数据敏感级。
- 追问 2：怎么灰度上线？——要点：影子索引+评估对比→按部门灰度→全量；指标回退即回滚（切分参数属索引 schema 级变更）。
- 边界：多模态（图表）解析、OCR 本书只给流程未实测（ch31 待核实项），引用时声明。

### 题 8-2 [模拟题] 现场设计：一个"日志排障 Agent"——能查证据、下结论，高风险动作要人批

**1. 问题与考查点**：Agent+安全+持久化的综合设计——P2 的完整复刻能力；考你把"自主性"关进笼子的设计功力。

**2. 常见错误回答**：设计成"给模型一个能执行任意命令的工具"——权限灾难；或者没有"证据不足怎么办"的设计（模型编个根因就是事故）；或者忘了"人批完进程重启了怎么办"。

**3. 简洁合格回答**：
- **主干 Workflow 化**（路径可画，Q1=能）：解析日志→规则预筛→取证计划→受限只读查询→模型假设（结构化 schema）→证据评估→（有高风险动作时）人工审批→分级结论（P1/P2/UNKNOWN）。
- **工具侧**：白名单三道校验（工具名→参数名→参数值）、SQLite 只读双保险（`mode=ro`+`PRAGMA query_only=ON`）、SQL 全参数化、每次调用写 JSONL 审计（who/when/what/args/result）。
- **模型边界**：只做结构化假设与置信度表达；不给执行权；日志文本截断并包在"证据摘要"数据段（注入边界）——模型可以错、可以被注入，但权限边界在白名单+只读连接+审批门上。
- **拒答**：证据不足→UNKNOWN+指名道姓的缺口清单（缺状态/缺事件/缺依赖记录），不编结论。
- **审批与幂等**：interrupt+Command(resume)，副作用走幂等账本（action_key 唯一），拒绝也是一等结果。
- **持久化**：checkpointer+thread_id=事件单号，跨进程可恢复；结论、证据、审计全部留痕可回放。

**4. 深入解释**：为什么主干不用自由 Agent——可测试性（每节点纯函数）、审计（节点是天然切面）、成本可控（模型只看压缩后的证据摘要而不是全量日志）；这是三问法 Q1/Q3 的直接应用。面试时最有力的收尾："这个系统的 14 个测试里有 10 个在测失败路径——排障工具自己必须先可信。"扩展路径（接 ES/Loki、多轮取证循环、并行取证）说明设计留了口。

**5. 工程案例**：P2 的架构图（README 第 2 节）、失败路径表（第 7 节，每条都有测试锁定）、resume_demo 三段演示（进程内拒绝/跨进程批准/幂等重放）——后者是"恢复语义"的现场讲材，面试官若追问"重启了怎么办"，直接演示。

**6. 追问与回答边界**：
- 追问 1：日志里有敏感信息怎么办？——要点：入库前脱敏、审计分级、检查点按敏感数据管权限（ch47.8）。
- 追问 2：误报率高怎么办？——要点：预筛规则进回归集、置信度校准、把"证据缺口"反馈给日志采集侧——排障工具的错误也是数据。
- 边界：真实日志源（ES/Loki）接入本书未实现，属扩展方向；合成日志数据要声明（题 8-6）。

### 题 8-3 [模拟题] 成本估算题：这个 RAG 问答功能每月花多少钱？

**1. 问题与考查点**：估算框架与杠杆意识——数字可以不知道，**算式与假设必须当场搭**；考你能不能把成本拆到"可操作的杠杆"上。

**2. 常见错误回答**："没数据算不了。"——放弃；或拍一个"大概几千块"——没有算式没有假设，追问一句就塌。

**3. 简洁合格回答**（给算式）：**月成本 = 日请求量 × 每请求成本 × 30**。每请求成本 = embedding 1 次（问题文本，几十 token）+ LLM 1 次（system+top_k 个 chunk+问题 ≈ 输入 token；输出上限受 max_tokens 控制）。P1 的结构给参考量级：编号证据 prompt 约 1~2k token 输入（README 第 7 节）。然后给杠杆与敏感性：① top_k 与 chunk_size 直接乘在输入 token 上（最大的两个杠杆）；② 历史管理——多轮滚雪球，20 轮会话的平均费用可达 5 轮的数倍量级（ch27 口径）；③ 缓存——高频 FAQ 命中缓存跳过生成；④ 模型分级——高频/简单走小模型；⑤ 拒答与限流拦截无效流量。最后声明纪律：**单价以厂商文档当期价为准，本书不背具体价格；给的是量级+敏感性+杠杆**。

**4. 深入解释**：固定成本别漏：入库 embedding（一次性）、评估集夜间回归（持续、有成本）、坏例人工复核（人力成本）。成本要可观测才有估算闭环：每请求 usage 落结构化日志、按租户/功能分桶（ch60 方向）。把成本估算接到"预算护栏"：并发限制（题 2-4）+步数上限（题 6-6）让**成本上限变成配置项**——这句是把成本题升级成架构题的钩子。

**5. 工程案例**：P1 README 第 7 节的单请求成本结构；EX-30-02 的 token 算术（277 vs 187 的对照算法）；EX-34-01 的预算装箱（预算不足时按分数整块丢弃——预算本身就是设计输入）。

**6. 追问与回答边界**：
- 追问 1：请求量翻 10 倍怎么办？——要点：先看缓存命中率、再压 top_k/换小模型、最后扩并发配额——按"边际成本从低到高"排。
- 追问 2：怎么向财务证明成本合理？——要点："每次回答成本 vs 人工答疑成本"折算，附假设清单；不承诺节省比例，给可复核的算式。
- 边界：任何价格类数字现场声明"以厂商当期文档为准"——不背价格是纪律不是心虚。

### 题 8-4 [模拟题] 安全评审题：这个"能查库、能发工单"的 AI 助手，上线前你要拦下什么？

**1. 问题与考查点**：安全清单化能力与纵深防御——考"清单思维"（评审要可执行）与"提示词不是权限控制"这条红线的肌肉记忆。

**2. 常见错误回答**："加个提示词，让它别乱来。"——ch28 红线；或只答某一层（"要做好鉴权"）——没有纵深，单层失守即失守。

**3. 简洁合格回答**（按清单走）：
- **身份与权限**：用户身份只来自请求上下文（JWT/Session），绝不来自问题文本或模型输出；每个工具函数体内第一行校验权限；多租户过滤在检索层。
- **注入防线**：指令数据分离（数据段标记）、输出白名单、**间接注入**意识（库里的工单/网页内容也是不可信输入）；真正的闸门在程序侧。
- **工具面**：只读优先、白名单三道校验、写操作（发工单）必须 interrupt 审批+幂等键、每个工具独立超时。
- **数据面**：脱敏入库、密钥走环境变量/密管（零硬编码）、检查点与审计按敏感数据管权限、只读 DB 账户+参数化 SQL。
- **失效语义**：判定器/权限组件故障 **fail-closed**（拒绝服务优于越权放行）；审计完整可回放（who/when/what/args/result）。
- **红线测试**：越权参数被拒、注入诱导被白名单拦、人工拒绝后不执行——三条都必须有自动化测试锁定（P2 的 test_whitelist_* 与 test_human_rejection_blocks_side_effect）。

**4. 深入解释**：纵深防御的层次感：模型层不可信（可以错、可以被注入）→程序层全闸门（白名单/只读/审批/幂等）→审计兜底回溯（事后可查"谁批的、执行了什么"）。整个方案的题眼一句话："**模型可以错，但拿不到执行权。**"与 Java 团队的分工：权限源与审计流水在 Java 侧 RBAC，Python 侧消费——你是消费者不是权威源，这个边界要主动说。

**5. 工程案例**：P2 README 第 9 节安全设计五条可整体引用；ch28 的注入三层缓解与边界（SQL 有词法边界、Prompt 没有——所以程序侧防线不可省）；P1 的"身份绝不来自问题文本"（README 第 7 节）。

**6. 追问与回答边界**：
- 追问 1：审批人被骗批了怎么办？——要点：审批单载荷带"模型依据的证据摘要"+动作影响说明，人审的是证据不是措辞；高危动作灰度放量。
- 追问 2：审计日志会被注入污染吗？——要点：审计是程序写不是模型写，字段白名单+只追加存储。
- 边界：沙箱内未做渗透测试；清单是评审框架，具体阈值按公司安全规范——把"这份清单要过贵司安全团队"说出口是加分项。

### 题 8-5 [模拟题] 讲一个你做过的 AI 项目（背景与决策）

**1. 问题与考查点**：STAR 变体——本书改成五段：**背景→决策→替代方案→验证→复盘**（普通 STAR 的 R 拆成三段，因为面试官真正要追问的是决策与验证）；考表达的层次感与可验证锚点密度。

**2. 常见错误回答**：按时间流水账讲（"首先我做 A 然后做 B"）——没有决策点；或全是大词（"架构设计""赋能""闭环"）没有一处可验证细节；或者把教学项目包装成生产项目——被追问细节时崩塌。

**3. 简洁合格回答**（以 P1 为例的 90 秒五段讲法）：
- **背景**：内部制度散落、人工答疑耗时；要求答案可溯源、证据不足宁可拒答、按部门隔离。
- **决策**：选 RAG 而非微调/长上下文（四连问：会改/要权限/量大/不实时——三条命中）；检索自实现余弦+词面补偿（当时 embedding 为 mock 的边界决定的补偿设计）；拒答双闸（阈值拦"不自信"、判定拦"自信跑题"）。
- **替代方案**：直接上向量库产品——25 块规模不需要，运维面反而大；只做阈值单闸——实测有"自信跑题"漏网（跨租户案例），所以加了 gate2。
- **验证**：自建 16 条评估集（14 应答+2 应拒）、四指标回归接 pytest（17 个测试）、11 组 curl 实测含权限拒绝与跨租户案例（run log 留痕）。
- **复盘**：阈值与权重只对本语料有效；真实模型路径未实调（沙箱无 Key）——下一步是 CI 夜间真模型回归。
- （然后主动声明：这是教学工程、语料为合成数据。如果面试官问的是商业项目，这个结构原样适用，数据换成真实的。）

**4. 深入解释**：五段里"替代方案"与"复盘"最值钱——它们证明你做过权衡、能自我批评；每段都要有**可验证锚点**（文件名/测试名/数字/运行记录），锚点密度决定可信度。时长控制：先给 90 秒版，面试官要哪个细节再展开哪段——把六段式（题前训练）与五段式（项目叙事）分开用。

**5. 工程案例**：P1 README 第 10 节的 90 秒讲法（可直接背的结构）；P2 README 第 11 节的三问三答（为什么 LangGraph/恢复不重复/模型边界）——两份现成讲材。

**6. 追问与回答边界**：
- 面试官任意细节追问的应对 → 题 8-6。
- 边界：模板不编造经历——你跑过哪个项目就讲哪个；讲不出的细节不要现编（题 8-6 的纪律）。

### 题 8-6 [模拟题] "这个模块具体是你写的吗？为什么这么设计？"——真实性追问怎么接？

**1. 问题与考查点**：12.0.3 说的"第三类最容易被编造的经历击穿"——考真实性与深入度的一致性；这是全卷对"诚信"权重最高的一题。

**2. 常见错误回答**：细节含糊（"大概是用了个框架"）、数字越问越大、被质疑时慌忙改口——**一致性崩塌比"不知道"致命得多**；或者反向过度防御（每个问题都觉得被冒犯）。

**3. 简洁合格回答**：三条纪律：① **具体到可指认**——"拒答双闸在 kb.py 的 answer 函数里，gate1 阈值 0.16 是评估集上应答最低分 0.194 与应拒最高分 0.129 之间取的"；② **知道边界**——"P1 的 LLM 生成路径按 openai 3.35.1 签名实现，但沙箱没有 Key 没有实调过，这一点 README 的未验证项写了"；③ **一致地"不知道"**——没做过的环节直说没做过，然后讲你会怎么做。被质疑时的四步公式：复述对方的质疑点 → 给出当时的约束 → 给出现有证据 → 承认局限。绝不现场改故事。

**4. 深入解释**：为什么诚实边界反而加分——面试官对 AI 项目经历的真伪高度敏感（编造重灾区），"知道自己的项目哪里没验证过"恰恰是**做过的人的标志**——没做过的人没有"未验证项"可讲。替代方案问答模板："当时还考虑过 X，没选它是因为 Y（约束/成本/评估数据），如果 Z 变了我会重评。"把教学项目讲出价值的方法：强调可复现性（同输入同输出、全测试覆盖、运行记录）与迁移点（哪些简化在生产要换）——"每个简化都是显式记录的迁移点，面试时主动说出来比被问出来好"（ch36.5 原话）。

**5. 工程案例**：P1 README 第 12 节"未验证项（诚实清单）"就是面试里"承认边界"的现成话术库（4 条，条条具体）；P2 README 第 11 节对三连问的标准答案。

**6. 追问与回答边界**：
- 追问 1：面试官说"这数字不对吧"？——要点：回到口径（题 8-9 的三句话公式），不慌不改。
- 追问 2：完全没做过的追问（如"你们怎么做 A/B"）？——要点："这个我没做过。我的理解是……但我不装懂。"——理解可以给，经历不能编。
- 边界：本题全部技巧以"你真的做过"为前提——技巧不能替代经历，这是本部分的底线。

### 题 8-7 [模拟题] "这个项目你踩过最大的坑是什么？"——复盘怎么讲？

**1. 问题与考查点**：失败叙事的结构与自我认知——"没坑"是零分答案，甩锅是负分答案。

**2. 常见错误回答**："没什么坑，挺顺利的。"——要么没做、要么没反思；或甩锅式复盘（"测试同学没测出来"）——暴露的是流程与格局问题。

**3. 简洁合格回答**：四段式：**现象**（可复现的表象）→**根因**（一句话说透机制）→**修复**（改动点）→**沉淀**（变成什么纪律/测试/监控）。本书提供三个"标准坑"模板（都是书中的真实实验案例——前提是你亲手复现过它们，才能讲成自己的实验）：
- **限流翻倍坑**：多实例部署后"60 次/分钟"变 120 次/分钟（计数器在进程内存）→根因：进程内状态在水平扩展后失真→修复：Redis INCR 外置→沉淀：状态外置清单进上线检查。
- **重试风暴坑**：下游抖动时退避无抖动，同毫秒集体重试把刚恢复的下游再打挂→根因：同步重试无随机化→修复：指数退避+抖动+预算上限→沉淀：重试参数模板化。
- **幻觉引用坑**：回答引用不存在的 [5]→根因：Prompt 约束是软的→修复：程序校验+回退抽取式→沉淀：引用有效性不变式测试。

**4. 深入解释**：好复盘的三个信号——根因到**机制层**（不说"配置错了"，要说"为什么这个配置会这样"）；沉淀**可复用**（变成测试/检查单/监控项，而不是"下次注意"）；诚实**分层**（我的失误/团队流程的洞/工具的坑，各归各位，不混着说）。复盘与题 4-8 的排障流程呼应：坑的"现象→根因"段就是一次排障。

**5. 工程案例**：三个坑分别对应 part03 ch19.1（多实例限流翻倍）、ch15.1（重试风暴）、part06 EX-34-02（幻觉引用）——全部有代码与测试可复现；面试前把自己项目里对应的真实坑也各写一个四段式。

**6. 追问与回答边界**：
- 追问 1："怎么保证不会再犯？"——要点：指认沉淀物（测试名/检查单项/监控项），不复述"我会更小心"。
- 追问 2："如果重来一次？"——要点：按**当时的信息面**重推决策，展示"决策-信息"关系而不是上帝视角。
- 边界：坑必须真实——教材的坑要先亲手复现再讲成自己的实验；绝不能讲成"公司生产事故"（那是编造经历）。

### 题 8-8 [模拟题] "你做了这么多年 Java，为什么转 AI 应用？用 Python 会不会可惜？"

**1. 问题与考查点**：动机真实性与身份稳定性——面试官在评估"拿了 offer 会不会走"与"是不是跟风"；同时暗中考你对两个生态的真实理解。

**2. 常见错误回答**："Java 太卷了/Python 火。"——动机外部化、随波逐流；或贬低 Java 抬高 Python——对面可能就是 Java 背景的面试官，还暴露你不懂"工程经验是资产"。

**3. 简洁合格回答**（三段式，按自己真实情况填空）：① **变化的事实**：我所在的业务开始长 AI 功能（举例：客服问答/日志排障），这类功能的主生态在 Python（模型 SDK、LangChain/LangGraph、评估工具链），我顺着手头需求系统学了一套面向 Java 开发者的课程并跑通了两个完整项目（指向具体项目）；② **经验的平移**：AI 应用的大头是普通工程——并发控制、超时重试、幂等、权限、评估回归，这些是我 Java 年限的直接资产，Python 只是把工具换了（Semaphore≈Bulkhead、评估集≈契约测试、checkpointer≈流程实例存储）；③ **职业判断**：我要做的是"AI 应用工程师"——应用工程向，不碰训练；Java 经验不是沉没成本，是这个方向上的差异化（不少 Python 出身的人反而缺服务工程深度）。

**4. 深入解释**：表达纪律：用**不承诺式**表述（"我的判断是应用层机会在增长"而不是"这行必然大火"）；被问"会不会回去写 Java"——答"集成场景里我本来就要写"（Python AI 服务 ↔ Spring Boot 的双向集成是常态），两栈是组合不是二选一。动机答案没有标准，只有**真实与具体**之分：能举出自己手头需求的动机 > 任何宏观叙事。

**5. 工程案例**：本书 ch01 的定位声明本身就是答案的理论版——"AI 应用工程师=把输出不可控的模型能力，用工程手段包装成行为可预期的服务；模型那部分你只能'选与防'，其余全部是普通工程活，而普通工程活正是 Java 老手的主场"。

**6. 追问与回答边界**：
- 追问 1："Python 哪里让你不爽？"——要点：给真实的具体点（GIL/打包/类型检查弱）+缓解手段（进程池/mypy/锁定依赖）——抱怨+方案=深度；只抱怨=浅。
- 追问 2："算法要不要补？"——要点：按第十一部分的边界答——会判断适用场景（RAG/Prompt/微调选择树），不装会训练；"应用工程师的算法知识边界"本身就是一个好答案。
- 边界：不贬低任一语言、不承诺行业判断；一切以你真实的经历与判断填空。

### 题 8-9 [模拟题] "你这个 100% 的评估指标是真的吗？"——数字被质疑怎么回应？

**1. 问题与考查点**：数字的**口径意识**——每个数字必须能说出"怎么来的、适用范围、谁可以复现"；同时考压力下的诚实（这是价值观题）。

**2. 常见错误回答**："测试都过了，就是真的。"——说不出口径；或慌忙把数字改小——一致性崩塌（题 8-6 的反面教材）；或反过来硬顶（"我的数字不会有错"）——暴露没有口径意识。

**3. 简洁合格回答**（三句话公式：**口径→条件→复现**）："这个 100% 是 16 条评估集上的四指标（hit@2/关键词覆盖/引用有效/拒答正确），评估集和语料是配套的合成资产；它的适用条件是 Mock 模式、这套语料、这套切分参数；复现命令是 `python3 eval/run_eval.py`，任何人跑一遍都能验证。它的含义是'结构回归守门'，不是语义质量证明——README 里明确写了'答案是否真对要人工抽检'。"三原则：不引用没跑过的数字；数字与版本绑定（切分/模型/Prompt 三元组）；口径升级主动声明（"换真实 embedding 这些数字全部要重校"）。

**4. 深入解释**：面试官质疑数字多半在测"你知不知道它的脆弱性"——**主动说出局限（样本量小、合成语料、Mock 模型）比被戳穿体面得多**；这也是本书写作红线的面试版：不把没实测的东西说成实测（FACTS 红线 4）。压力测试的终极题："那你给个真实准确率？"——标准答案："在没有可靠口径之前我不给数字；方法上是评估集+人工抽检双门槛，建起来之前我不承诺。"——拒给数字但给路径，是这一题的满分形态。

**5. 工程案例**：P1 README 第 6 节的指标口径段落（"词面级/结构级指标只能做回归守门"）与第 12 节未验证项清单——两处都是"数字带边界"的书面示范。

**6. 追问与回答边界**：
- 追问 1："怎么把指标做得更可信？"——要点：扩样本、真实模型夜间评估、badcase 回填、人工对齐 LLM 判官（算一致率）。
- 追问 2："你们公司（项目）的线上指标呢？"——要点：没有就说没有，说清"我讲的都是可复现的离线口径"。
- 边界：**永不为压力当场造数**——这是职业底线题，答案没有灰色地带。

### 题 8-10 [模拟题] 面试最后"你有什么想问的？"——反问什么既加分又拿信息？

**1. 问题与考查点**：判断力与职业成熟度——反问是双向面试的评分点，也是你唯一的信息采集窗口。

**2. 常见错误回答**："没有问题了。"——放弃窗口、显得没兴趣；或只问薪资加班（那是 HR 环节的题）；或问出"贵司用什么大模型"这类一查官网就知道的问题。

**3. 简洁合格回答**（按目的分组，选 2~3 个）：

- **收尾式表态**："如果我入职，前 30 天您期望我交付什么？"——把面试变成试用期预演。

**4. 深入解释**：反问的隐藏功能——**你提的问题就是你的能力画像**：问评估体系的人被默认懂评估，问复盘文化的人被默认经历过生产。听到答案后的追问（"评估集谁维护？""指标掉了我有权限回滚吗？"）进一步展示工程素养。反问答案本身也是决策输入：三个问题都答不上来的团队，你的 offer 决策要重新掂量。

**5. 工程案例**：本书 ch60（成本与可观测）与 ch61（上线清单）的问题化版本——把书里的清单变成反问，既自然又专业（"上线前你们过什么检查单？"）。

**6. 追问与回答边界**：
- 本题无追问，但注意：offer 判断与薪资谈判不在本书范围，**本书不承诺任何求职结果**——反问策略只提高信息质量，不保证结果。

### 12.9.1 经验迁移话术：三个自我介绍段落模板

自我介绍只有 60~90 秒，结构比文采重要：**现状一句话 → 迁移路径一句话 → 证据两到三句 → 定位一句话**。以下三个模板对应三种常见处境，选贴近的一个填空。

**模板 A：在职 Java 工程师，完成本书并跑通项目**

纪律：项目数字必须是你跑出来的真实数字（16 条/14 个测试/25 chunk 这些是本书项目的值，你复现后如实引用）；说了 LangGraph 就要接得住题 6-3。

**模板 B：完成学习但暂无生产 AI 经历（转型求职）**

> "我是 Java 后端出身，正在转向 AI 应用开发。过去 X 个月我用一套系统教材补齐了 Python 工程栈（asyncio/Pydantic/FastAPI/pytest）和 LLM 应用栈（模型 API、RAG、LangChain/LangGraph），全部代码有运行记录与测试。两个自建项目：……（同模板 A 的证据段）。我清楚自己还没有生产 AI 项目的经验，所以我把'可验证'做到了我能控的范围：Mock 模式下同输入同输出全流程可复现、测试全绿、诚实的未验证清单。我的判断是：服务工程的底子——并发、幂等、权限、排障——是 AI 应用的主要成本所在，这正是我已有经验最密的地方。"

纪律：主动说"没有生产 AI 经历"是给追问降温——对方从"查证你是否吹牛"切换到"验证你学得扎不扎实"，题目对你反而有利。

**模板 C：在 Java 岗位上做过 AI 集成**

> "我在 X 公司负责 Y 系统，去年起负责其中的 AI 功能集成：Java 侧持有用户身份与权限，Python 侧提供问答服务——SSE 转发、网关透传、超时与降级配置、审计对账是我做的……（只讲真做过的部分）。检索与评估那部分是 Python 同学负责，我理解原理（切分/检索前过滤/评估指标）但没有亲手做过，正在通过课程项目补这一段。"

纪律：C 模板的最大风险是"顺手把别人的活讲成自己的"——没做过的模块明确说"理解原理但没亲手做过"，这句在题 8-6 的纪律里是加分句。

**三个模板共同的"三不"**：不写没用过的框架；不给未实测的数字；不说"精通"——说"能独立完成 X 并有测试证明"。
