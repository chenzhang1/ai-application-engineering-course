# 第 62 章 微调解决什么：预训练、SFT、LoRA 与偏好优化

> **本章目标**：分清四个训练阶段各自改变模型的什么；掌握 RAG/Prompt/微调的选择树并会走树；建立成本与资源量级的判断框架（诚实版：只给判断依据，不给训练实操）。
> **前置知识**：ch22（Transformer 直觉与训练阶段一句话）、ch30（什么时候不用 RAG）。
> **学完你能做什么**：在需求评审会上判断"这个诉求该不该微调"并给出依据；跑通确定性选择树（EX-62-01）；估算一个微调提案的成本构成，判断它是否值得立项。

## 62.1 真实问题引入：三个"微调"，三件完全不同的事

某零售公司（合成案例）的季度会上，三个部门提了三个需求，都说要"微调大模型"：

- **市场部**："我们品牌的语气很独特，希望客服回复都是那个味儿。"——**风格问题**。
- **客服部**："我们的售后制度三天两头改，模型答的全是过时口径。"——**知识时效问题**。
- **数据部**："工单要按内部规范转成结构化 JSON，通用模型格式老出错。"——**格式遵循问题**。

负责人拿着三个需求找算法团队，得到三句不同的答案："第一个不用微调，先调 Prompt；第二个微调解决不了，要上 RAG；第三个可以考虑微调，但先把评估集建了。"三句话背后是一套完整的技术路线判断体系——**先分清问题属于哪一类，再谈用什么工具**。本章就是把这套体系交给应用工程师。

## 62.2 一句话解释 + 生活类比 + 类比边界

**一句话解释**：微调（fine-tuning）改变的是模型的**参数倾向**——它擅长让模型"学会做事方式"（格式、风格、任务套路），不擅长让模型"记住可更新的事实"或"获得运行时判断力"（权限、实时性）。

**生活类比**：微调像**送一位老员工去岗前培训班**：培训班能改变他的做事风格（报告按公司模板写）、话术（对客户用规范用语）、技能熟练度（表格处理又快又稳）；但培训班**塞不进**下周才发布的红头文件（知识时效），**保证不了**他永远不说错话（幻觉），更**替代不了**门禁系统（权限）。培训改变的是"这个人"，权限是"公司制度"——两者属于不同层面。

> 💡 类比边界：
> 1. 培训有"过拟合"风险：只教过一类业务的员工，换个业务反而不适应——微调样本分布太窄会损伤通用能力（灾难性遗忘的一种通俗形态），所以"教什么"要与"考什么"（评估集）配套设计；
> 2. 培训效果因人而异：同样的课，有人学得快有人学不会——微调效果**依赖底模**（基座模型版本），换底模要重新训练重新评估；
> 3. 最关键的边界：培训班教的**技能**与图书馆**查资料**是两种能力——前者进参数（微调），后者靠检索（RAG），62.4 的选择树就是分派这两件事的规则。

## 62.3 正式原理与准确术语：四个阶段各自解决什么

**一张表先立框架**（每行的"不解决什么"与"解决什么"同样重要）：

| 阶段 | 输入 | 改变什么 | 解决什么 | 不解决什么 |
|---|---|---|---|---|
| 预训练（pre-training） | 海量通用语料 | 语言能力与世界知识 | "会说人话、知道常识" | 你的私有知识、你的任务格式 |
| SFT（supervised fine-tuning，监督微调） | 指令-回答样本对 | 指令遵循与任务格式 | "按你的要求做事"（格式/流程/风格） | 事实知识的更新（会背错新的） |
| LoRA（low-rank adaptation，低秩适配） | 同 SFT 的数据 | 只训练注入的小矩阵，底模冻结 | 同 SFT 的效果，成本/显存低一个量级 | 底模本身的根本能力边界 |
| 偏好优化（preference tuning，RLHF/DPO） | 偏好对比数据（哪个回答更好） | 回答的整体倾向 | "更符合人的偏好"（有用/安全/语气） | 具体任务的格式（那是 SFT 的事） |

**预训练**（2 段通俗解释）：①从零把"语言能力 + 世界常识"压进参数——读完互联网规模的文本，学会预测下一个词；你的公司制度不在它的语料里，这就是"私有知识缺口"的来源。②Java 类比：预训练像**安装 JDK 和标准库**——它决定了"这门语言能写什么"，但不含你的业务代码。类比边界：JDK 装完是确定的，预训练模型是概率性的；且"升级 JDK"（换底模）对应用是大事，对预训练模型同理——**版本升级要全量回归**。

**SFT**（2 段通俗解释）：①给模型看几万条"指令→理想回答"的样本对，让它学会"收到这类请求该产出什么样的回答"——格式、口径、拒绝方式都在这批样本里定义。它教的是**行为模式**，不是**事实本身**：样本里写"7 天可退"，模型学到的是"售后问题要按公司口径、结构化地回答"，而不是把"7 天"可靠地存进记忆。②Java 类比：SFT 像**按公司规范培训 + code review 文化**——产出风格被校准，但没人靠培训记住产品手册（那要靠能更新的文档系统，即 RAG）。类比边界：培训可能有遗漏与偏差（数据质量决定上限，ch63 的垃圾进垃圾出）；code review 修正的是倾向不是每次输出，SFT 亦然——**微调后仍有错误率，评估集量化它**。

**LoRA**（2 段通俗解释）：①全量微调要更新模型的全部参数（数十亿级），LoRA 冻结原模型，只在旁边注入两个小矩阵（低秩分解）参与训练——训练参数量降一到两个数量级，效果接近全量微调（以各任务实测为准）。②Java 类比：LoRA 像**插件/AOP 拦截器**——不改核心 jar，运行时织入一段"适配逻辑"；原版本随时可回退。类比边界：AOP 织入是确定性的，LoRA 是训练出来的概率性适配；插件可以卸载，LoRA 的"适配器"同样可插拔可多开（一个底模挂多个任务适配器），这是它在生产里的最大优点，也是"底模升级要重训所有适配器"的代价来源。

**偏好优化**（2 段通俗解释）：①SFT 教"应该怎么答"，偏好优化教"两种回答哪种更好"——用人类/模型的偏好对比数据调整整体倾向，让回答更有用、更安全、语气更对。RLHF（基于人类反馈的强化学习）与 DPO（直接偏好优化）是两条主要实现路线（数学不展开）。②Java 类比：像**建立"优秀 PR"的评审标准**——不是教你怎么写代码（SFT），而是让全团队对"什么是好代码"的判断趋同。类比边界：偏好是**整体倾向**的校准，解决不了"某个具体格式总错"（那是 SFT/样本的事）；且偏好数据的标注一致性本身就是工程难点（标注员之间都会打架）。

## 62.5 逐段解释：成本与资源量级判断（诚实版）

**先立边界：本书不提供训练实操**——不写训练脚本、不调训练框架、不报训练指标。原因在 ch63.5.2 的边界声明：训练是算法团队的深水区，应用工程师需要的是**判断量级、看懂报价单、问对问题**。以下是量级判断的四个依据。

**依据一：成本构成有五块，算力往往不是最大头。**数据标注（最容易被低估：清洗、统一口径、质量抽检的人力）、训练算力（GPU 时长 × 单价，随模型尺寸与样本量增长）、评估（每次迭代都要跑评估集，真实模型评估本身是 API 成本）、迭代人力（失败的重训是常态，第一次就成的微调项目是少数——这句是工程经验判断，不是统计结论）、长期运维（底模升级 → 全部适配器重训重评）。**用这五块向提案方要报价单，缺哪块哪块就是坑。**

**依据二：样本量的路线分界（与选择树一致）。**百级样本 → Prompt 优化与 few-shot 的领域；千级以上的一致样本 → LoRA 候选；万级以上才进入"值得讨论全量微调"的范围。**"一致"比"多"重要**：一千条互相矛盾的样本不如三百条口径统一的（ch63.1 的模拟演示了方向）。

**依据三：tokens 与 GPU 时长的估算框架（不给单价）。**训练 token 量 ≈ 样本数 × 平均样本 token 数（输入+输出）。GPU 时长 ≈ 训练 token 量 ÷ 实测吞吐——**吞吐必须实测**（取决于硬件型号、框架、序列长度、并行策略，跨环境差数倍是常态），任何"每个样本 X 秒"的经验值都不可跨环境复用。单价以厂商报价为准。**这个框架的价值是让你能问出正确的问题**："你们这次训练估了多少 token、用什么卡、吞吐实测过吗、预算含几次重训？"

**依据四：先算"不微调的替代方案"的账。**RAG 的成本是检索工程与维护（一次性+低额持续）；长 Prompt 的成本是每次请求多付输入 token（ch21/ch27 的账）——很多"要微调"的诉求，把这三条账摆出来后结论会反转。**微调是持续投入换边际能力，不是一次性买断**。

## 62.7 常见错误与排查

**错误一：拿微调解决知识更新（62.1 客服部的需求）。**
现象：花两周微调，上线第三天制度改版，模型又全错了。修复：知识类诉求转 RAG（选择树第一跳）；微调产出的"口径遵循能力"可以保留，但**事实内容必须走检索**。

**错误二：以为微调 = RAG 的替代。**
现象：评审会上"我们微调了就不需要检索了吧"。纠正：两者解决不同问题（62.3 表的知识缺口 vs 行为校准），混合路线（RAG+LoRA）才是知识+格式双要求的正解；"替代"叙事通常来自对训练周期与成本的低估。

**错误三：没有评估集就开始标注。**
现象：标了两万条才发现没有验收标准——好多少算好？修复：**评估集先行**（ch63.5.1 的铁律）：先花小成本定"什么算对"，再花大成本生产数据。

**错误四：数据脏了直接训。**
现象：爬来的历史工单直接当 SFT 数据，模型学会口语化、矛盾口径与错别字（ch63.1 模拟演示的三宗罪）。修复：数据质量检查清单（ch63.5.1）过滤后再进训练。

## 62.8 企业场景中的使用方式

- **应用工程师的角色定位**：不亲手训练，但要做三件事——**需求翻译**（把业务诉求拆成知识/风格/格式三类特征，喂给选择树）、**数据供给**（业务侧的数据清洗与脱敏管线，ch58 的位置纪律）、**验收把关**（评估集定义与验收标准由应用侧与算法侧共同签署）。
- **与算法团队的协作接口**：带着选择树的特征清单去开会（62.4 的 NeedFeatures 六个字段就是需求单模板），而不是带着"领导说要微调"去。会议产出应该是：路线共识、评估集范围、数据计划、成本报价单。
- **Java 团队的对接点**：微调产物（适配器/新模型版本）最终也是一个"服务端点"——ch57 的四模式集成、ch59 的稳定性、ch60 的成本归因**原样适用**；模型版本要进调用日志（ch60.3 字段表的 model/prompt_version 字段），灰度与回滚同 Prompt 版本一个待遇。

> **本章目标**：对"微调做不了什么"的三类问题（知识时效/幻觉/权限）逐个给出机制级说理；建立"没有评估集就别谈微调"的数据质量铁律；替应用工程师写下知识边界声明——该懂什么，不必深入什么。
> **前置知识**：ch22（训练阶段一句话）、ch35（评估）、ch58.3（权限三落点）、ch62（四阶段表）。
> **学完你能做什么**：在评审会上用机制论证否掉"微调解决知识更新/幻觉/权限"的提案；跑通两个边界演示（EX-63-01/02）；给团队写一页"应用工程师的微调知识边界"。

## 63.1 真实问题引入：一个提案，三个奢望

某保险公司（合成案例）的项目立项书写道："**微调一个专属大模型，要求：①掌握本公司最新理赔政策；②回答准确、不胡编；③能区分内部员工与客户的权限，敏感内容只答给内部。**"预算一次到位，排期三个月。

算法负责人的回复只有三行："第①条应该走检索——政策每周都改，微调追不上；第②条微调帮不了多少——胡编是生成机制的属性，不是知识多少的问题；第③条微调**永远**不该做——权限是运行时决策，权重是训练时固化的。"三行回复对应本章三节：逐条说理，把"为什么"讲到机制层。

## 63.2 一句话解释 + 生活类比 + 类比边界

**一句话解释**：微调改变的是**训练时固化的参数倾向**；而知识时效需要**运行时可更新的外部事实**，幻觉治理需要**可验证的生成依据**，权限需要**请求级的动态判定**——三者都不在参数里，所以都不该指望微调。

**生活类比**（沿用 ch62 的员工培训，边界收得更紧）：培训能让员工**行为更规范**（微调真正擅长的事），但：①他不会因此知道**下周才印发的文件**（时效）；②培训提高的是"说话更有条理"，不是"说的每句话都为真"（幻觉）；③你更不能靠培训决定他**能进哪间机房**（权限）。

> 💡 类比边界：
> 1. "培训提高可靠性"是真的——微调**可以**降低某些任务、某些形态的错误率（这是研究方向，效果因任务而异，需自测）；本章反对的不是"微调与幻觉毫无关系"，而是"**指望**微调消灭幻觉"——可靠性工程要的是可验证的机制（引用/拒答/评估），不是概率的改善；
> 2. 员工培训有结业考试，微调有评估集——两者都是"先定标准再投入"的逻辑（63.5.1）；
> 3. 三个"做不了"的共同深层原因：**参数是训练时刻的快照**——任何"之后才存在"（新知识）、"逐次而异"（权限）、"无法从数据推出保证"（真值）的东西，都不在那张快照里。

## 63.3 正式原理与准确术语：三类问题逐条说理

### 63.3.1 知识时效：参数是训练时刻的快照

**机制**：模型的事实知识来自预训练语料与（若有）SFT 语料，全部**固化在权重里**——训练完成的那一刻，模型的知识就被冻结了（knowledge cutoff，知识截止时间，ch21 讲过它的产品含义）。之后世界继续变化，权重不会。更新知识的唯一微调路径是"重新标注 + 重新训练 + 重新评估"，周期以周/月计、成本按 62.5 的五块构成全算一遍；而业务知识的更新节奏（政策、价格、库存）是日/周级。**更新速度的量级差是数十倍，这个差距不随工程努力消失**——它来自机制。

**正确工具**：RAG（知识在外部库，更新分钟级生效、可引用、可按权限过滤）与工具查询（实时数据直连源头）。EX-63-02 实验 A 演示了对照：同一个"2026 新版年假政策"问题，微调模型答 2025 旧口径（它只认识训练时的世界），RAG 流程检索到新文件答新口径。

> ⚠️ 常见坑："我们微调的时候把最新文档都放进去了"——放进去的只是**训练时刻**的最新。上线第二天起，这条知识就开始过时，而你没有机制知道它何时过时（检索系统至少能看到文档的最后修改时间）。**知识放权重里，等于把"可更新"的属性删掉了。**

### 63.3.2 幻觉：生成机制的属性，不是知识量的问题

**机制**：语言模型逐 token 生成**概率上合理**的序列——"合理"是流畅与连贯，不是"为真"。幻觉（hallucination，ch21 定义）源于这个机制本身：模型没有"我不知道"的可靠内省信号，上下文缺依据时它照样生成流畅文本。微调能改变的是**倾向**（比如用"拒答样本"教它证据不足时说不知道——这是有效且有价值的做法），但它不能给模型装上"真值校验器"：训练数据本身就无法保证全真，机制上也没有"生成后与事实比对"的步骤。

**正确工具**：幻觉治理的可靠性来自**可验证的机制链**（ch34/ch35 的组合）——只依据检索证据生成（有依据才开口）、引用溯源（答案可对回原文）、拒答策略（证据不足明确说不知道）、评估集量化幻觉率（含对抗样本）。EX-63-01 的模拟演示从反面支持这一点：干净数据教会模型"没依据就拒答"，脏数据反而放大编造倾向——**数据质量影响倾向，机制才提供保证**。

**边界（诚实声明）**："用微调降低幻觉"是活跃的研究方向（如用拒答样本、真实性导向的偏好数据），某些任务上有效果——**效果是否存在、多大，必须用你自己的评估集实测，本书不报任何量化结论**。生产防线的主承重结构永远是机制链，微调至多是辅助。

### 63.3.3 权限：权重是全局的，权限是请求级的

**机制**：一份权重服务所有用户——模型在推理时**不知道也不被允许知道**"这次调用来自谁"（调用者身份是运行时上下文，不是输入的一部分——就算把用户名拼进 Prompt，那也是可被注入伪造的文本，ch28 反例 A）。把权限规则"训进"权重有三重不可行：**不可验证**（无法对任意请求证明"这个回答没越权"——概率生成没有可审计的决策依据）；**不可分租户**（一份权重无法给 A 公司与 B 公司不同的权限边界）；**不可审计**（合规问"为什么这条数据给了这个用户"，"模型自己判断的"不是答案）。

**正确工具**：ch58.3 的三落点——检索前过滤（无权数据根本不进上下文）、工具权限校验（执行前按会话身份判定）、审计留痕（拒绝也记录）。EX-63-02 实验 B 演示：权限判定发生在代码层（`check_salary_permission` 只认会话身份），模型只负责在**被允许的数据**上生成。

> 📌 生产提示：把这三条说理压成一句评审会通用反问：**"这个问题需要的属性——可更新、可验证、可按请求区分——参数快照里有哪一个？"** 三个都没有，路线就该换。

**为什么评估集必须先行**：①它是**验收标准**——没有"什么算对"的定义，训练方与需求方对"效果不错"的理解可以差十万八千里；②它是**止损机制**——微调迭代要花钱，每一轮都要对照评估分数决定继续/回退；③它是**回归防线**——底模升级、数据更新后，同一套评估集保证没有退步（ch60 三层体系在微调场景的复用）。

**数据质量检查清单**（清洗 SFT 数据的最低工序，全部可用脚本半自动执行）：

| 检查项 | 做什么 | 对应的坏结果（EX-63-01 已演示） |
|---|---|---|
| 口径一致性 | 同一事实在全库只有一种说法（7 天 vs 15 天） | 矛盾口径被学走，答错数字 |
| 格式一致性 | 输出模板统一（政策：…结构） | 格式漂移，下游解析失败 |
| 文本规范化 | 错别字/全半角/标点清理（含脱敏——ch58 位置纪律） | 模型学会错别字，敏感数据进权重 |
| 去重与平衡 | 重复样本去除，类别分布检查 | 过拟合重复样本，长尾任务退化 |
| 拒答范式覆盖 | 收录"证据不足→明确拒答"的样本 | 训练外问题编造（幻觉放大） |

### 63.5.2 应用工程师的知识边界声明

**该懂的（本书教到这里为止）**：四阶段各解决什么（62.3 表）；选择树与三案例走树（62.4）；成本构成与量级判断框架（62.5）；"微调做不了什么"的三条机制论证（63.3）；数据质量与评估先行（63.5.1）；微调产物作为服务端点的工程化（62.8）。

**不必深入的（写出来是保护团队，不是设限）**：Transformer 训练数学（损失函数/优化器/学习率调度）；分布式训练与并行策略；训练框架的 API 细节与超参调优；RLHF/DPO 的算法推导。这些是算法工程师的专业纵深——**应用工程师越过这条线的正确方式是转岗或系统进修，而不是在项目里边干边猜**。

**协作时的"正确问题清单"**（你不必会答，但必须会问）：这次训练的 token 量与吞吐实测值？评估集怎么构成、基线分多少（Prompt+few-shot 的对照）？数据清洗工序与质量抽检比例？重训与底模升级的运维计划？训练数据里有没有做过脱敏与口径统一（ch58/ch63.5.1 清单）？——**这五个问题能把一个含糊的微调提案变成可评审的工程方案。**

## 63.7 常见错误与排查

**错误一："微调一下让模型知道最新政策"（63.1 第①条）。**
修复路线：政策类知识转 RAG（可更新/可引用/可过滤）；若输出格式也需要规范，走 RAG+LoRA 混合；微调样本里不放会过时的事实，只放"如何依据检索内容作答"的行为范式。

**错误二："微调完就不幻觉了"。**
修复路线：防线重构为机制链（依据生成/引用/拒答/评估），微调定位为辅助（拒答范式训练）；上线标准写进评估门槛（幻觉率阈值由业务签署）。

**错误三："把权限规则写进训练数据"。**
修复路线：权限回到代码层三落点（ch58.3）；训练数据本身要做**权限审计**——历史工单/文档里混入的越权内容既是数据污染也是合规风险。

**错误四：先标两万条数据再说。**
修复路线：评估集先行（63.5.1 的三条理由）；先标 300 条做基线实验，验证"数据→效果"的因果在生产环境成立，再放量标注。

## 63.8 企业场景中的使用方式

- **立项评审的否决模板**：遇到"微调解决知识/幻觉/权限"类提案，用 63.3 的三条机制论证+63.5.2 的问题清单逐条对答——否决不是终点，给出替代路线（RAG/机制链/代码层权限）才是。
- **与算法团队的分工协议**：应用侧交需求特征（62.4 的六字段）、评估集定义、数据管线（清洗/脱敏）；算法侧交训练方案、基线对照、评估报告——**双方共享同一套评估集与门槛**，避免"各自说各自的好"。
- **给管理层的一页纸**：微调不是买软件，是**养能力**——初始投入 + 数据维护 + 底模升级重训 + 持续评估，四项支出对应"行为校准"这一个收益；知识、真值、权限由别的机制承担（成本更低且必须更低，因为它们本来就该在架构层解决）。

## 63.11 面试追问[模拟题]

1. **[模拟题]** "业务方坚持'我们就想微调一个自己的模型'，预算也有，你怎么办？"——合格回答：不硬顶，先拆诉求（62.4 特征清单）→ 用选择树给每类诉求找最短路径 → 对确属微调区间（格式/风格+足量样本）的部分给立项方案（评估集先行+成本五块），对知识/权限部分给替代路线——**把"要不要微调"变成"哪部分值得微调"**。
2. **[模拟题]** "有人说'RAG 也有检索失败的时候，微调至少稳定'，怎么回应？"——合格回答：两者失败形态不同且可治理——RAG 失败是"检索层可观测、可评估（hit@k）、可优化（切分/混合检索）"的失败；微调的"稳定"是把知识冻结后的表面稳定，代价是过时不可见（63.3.1 的坑）。生产系统两者常并存：RAG 管事实、微调管行为——**不是二选一**。
3. **[模拟题]** "应用工程师需要懂训练吗？懂到什么程度？"——合格回答：懂"训练在解决什么问题、成本在哪、怎么验收"，不需要会训练（63.5.2 边界声明）；判断标准是能否完成三件事——需求翻译、数据供给、验收把关；做到这三件，微调项目对你就是"提供数据与标准的甲方工程"，深水区交给算法团队。
