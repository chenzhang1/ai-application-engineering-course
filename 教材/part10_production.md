# 第 57 章 架构边界：AI 服务与业务服务怎么切

> **本章目标**：给"要不要把 AI 能力拆成独立服务"建立可复用的判断框架；掌握 Python AI 服务与 Spring Boot 的四种集成模式及各自的坑；把序列化契约与超时预算这两个跨语言集成的高频事故源写成规矩。
> **前置知识**：ch17（FastAPI 服务）、ch24.8（AI 网关雏形）、ch16（Pydantic 契约）。
> **学完你能做什么**：用一张对照表和三个判断案例决定"切不切"；为每种集成模式列出适用场景与三个具体的坑；跑通契约演进与超时预算两个可运行演示，并把它们固化成测试。

## 57.1 真实问题引入：同一个功能，两种死法

某电商平台（合成案例）的 Java 团队接了两个 AI 需求，走了两条路线，也死了两次。

**第一种死法：不切，全塞进业务服务。**"订单异常备注自动摘要"被直接写进订单服务的 Controller：Java 里加一个 openai 官方 SDK 的 HTTP 客户端调用。上线第三天出事——模型 API 某次抖动把响应时间从 2 秒拖到 40 秒，Tomcat 线程池被同步等待占满，**连正常的订单查询一起挂**。复盘时发现三个无解的问题：AI 依赖的 Python 生态（tiktoken 计数、文档解析、向量检索）在 Java 里要么没有要么重写；模型相关的 Prompt 迭代每天发生，却要跟着订单服务走两周一次的发版节奏；成本没法归因——订单服务的日志里分不清哪些 CPU 和带宽花在 AI 上。

**第二种死法：切了，却没定规矩。**团队痛定思痛，把知识库问答拆成了独立 Python 服务。两周后出事——Python 侧为了"多返回一个置信度字段"，直接删掉了响应里的 `refs` 字段；Java 侧的反序列化当场炸掉。修复后又过了几天，运维发现 Python 服务偶尔"白算"：Java 网关 30 秒超时断开了，Python 里的 LLM 调用还在跑，token 照扣。

两种死法指向同一个问题：**边界不是"拆不拆"一个动作，而是一组契约**——数据契约（字段怎么演进）、时间契约（超时怎么传播）、故障契约（谁挂了会传染谁）。本章就是把这组契约讲清楚。

## 57.2 一句话解释 + 生活类比 + 类比边界

**一句话解释**：AI 服务与业务服务的边界，本质是把"变更频率、依赖生态、故障特征、成本结构"不同的两类代码用**显式契约**隔开——切不切、怎么连，都由这些差异决定，而不是由"微服务好不好"的口号决定。

**生活类比**：业务服务像**医院门诊**（流程稳定、按部就班），AI 能力像**外请的会诊专家**（意见有价值、但时间不归你管、收费方式不同）。门诊可以把常见问题自己答了（模块内调用），疑难的请专家会诊（同步 HTTP）；等不起专家的，留下资料等回复（异步任务）；一天要会诊几千次的，直接让专家团队进驻但走独立的排班与收费系统（独立服务+事件驱动）。

> 💡 类比边界：
> 1. 会诊专家"经验丰富但不了解你的病人病史"——AI 服务不持有业务状态，业务上下文必须随请求传递，这不是实现细节而是边界定义；
> 2. "独立排班"意味着两套系统会各自停机维护——**AI 服务挂了业务服务必须还能活**（降级路径在业务侧，57.5），如果做不到这一点，说明切分方案有问题；
> 3. 类比止于"边界"：真实系统的难点在契约细节（序列化、超时、幂等），这正是 57.4~57.5 的全部内容——类比给不了你这些。

## 57.3 正式原理与准确术语

- **服务边界（service boundary）**：两段代码之间唯一的合法交互通道。边界两侧各自独立部署、独立变更，一切交互走显式契约（HTTP/消息/事件）。
- **防腐层（anti-corruption layer，ACL）**：边界一侧的翻译层，把外部模型转成本域模型。AI 服务对 Spring 暴露的 DTO、Spring 调 AI 的客户端封装都是 ACL——**外部变更被隔离在 ACL 里，不渗进业务代码**。
- **序列化契约（serialization contract）**：跨服务传递的数据的字段名、类型、语义与兼容性承诺。Python 侧由 Pydantic 模型承载（ch16），Java 侧由 DTO/Jackson 承载，两侧靠 JSON 对齐。
- **超时预算（deadline budget）**：一次请求从入口到最深依赖的总时限，逐级分配、逐级递减。上游超时必须大于下游超时之和加余量，否则下游成功的结果送不回上游。
- **变更频率差异**：AI 功能（Prompt、模型版本、检索策略）以天为单位迭代；业务核心（订单、支付）以周/月为单位发版。**这是切分的头号依据**——变更节奏不同的代码放在同一个发布单元里，快的那部分会被慢的那部分拖住。

### 57.3.1 切分判断对照表

| 维度 | 倾向"不切"（业务模块内） | 倾向"切"（独立 AI 服务） |
|---|---|---|
| 变更频率 | AI 逻辑随业务版本走，月级变更 | Prompt/模型/检索日级迭代 |
| 依赖形态 | 只调模型 API（SDK 一行搞定） | 需要 Python 生态（文档解析/向量/embedding/编排框架） |
| 故障要求 | AI 失败可容忍，随业务一起降级 | AI 的高延迟/故障不能拖垮业务主链路 |
| 扩缩容 | 与业务同生命周期，量小 | 算力/配额独立核算，需要独立扩缩 |
| 团队技能 | Java 团队独立维护 | 有 Python 工程师长期投入 |

### 57.3.2 三个判断案例（合成案例，走表推理）

**案例 1：客服工单自动打标签。**特征：调用量中等；实现上只需要一次 chat 调用 + 结构化输出（ch24）；模型换了三次但 Prompt 变化月级；失败可容忍（标签错了人工改）。走表：依赖形态"只调模型 API"、变更月级 → **不切**。做法：Java 服务内 HTTP 调模型 API，或者由统一的"AI 网关"代理（ch24.8），不新建 Python 服务。**依据**：切分收益（独立迭代）小于切分成本（多一套部署/监控/契约维护）。**边界**：如果打标签准确率成为核心 KPI、需要自建评估流水线与 Prompt 回归（ch28/ch60），变更频率会升级到周级，此时重判。

**案例 2：企业文档知识库问答。**特征：需要文档解析、切分、向量检索、引用溯源（P1 项目全链路）；检索策略与切分参数在持续调优；问答延迟 2~10 秒，不能阻塞业务主链路；GPU/embedding 配额独立核算。走表：依赖形态"重 Python 生态"、变更日级、故障隔离要求高 → **切**。做法：Python FastAPI 服务（P1 的架构），Spring 通过 SSE 透传对接。**依据**：这张表五行里它占了四行"切"。**边界**：若只是内部 20 人试用，先用单体模块跑三个月再切也成立——**切分可以事后做，前提是模块边界一开始就清晰**。

**案例 3：支付风控里的"AI 辅助判定"。**特征：决策链路里 LLM 只出"建议分"，最终规则引擎在 Java 侧；强一致与审计要求（每一笔决策可回放）；失败必须立即降级为纯规则。走表：**规则与数据留在业务服务，AI 只作为"建议提供者"被调用**——可以不切（Java 直调），也可以切（独立推理服务），但**无论切不切，权限与审计都在业务侧**（ch58 的原则）。**依据**：AI 输出不进入资金决策的"事实层"，只进入"参考层"，边界天然清晰。**边界**：如果监管要求"AI 参与了哪些决策"可审计，那么调用 AI 的每一次记录（trace_id、输入摘要、输出）必须在业务侧落库，这一点倒逼接口设计：AI 服务的响应要带可记录的结构化字段，而不是一段自由文本。

> 📌 生产提示：三个案例的共同点是**先写"AI 失败了怎么办"，再写"AI 成功了怎么办"**。凡是"AI 挂了业务跟着挂"的设计，无论切不切都是错的。

## 57.4 最小完整示例：序列化契约的安全演进（EX-57-01）

跨语言集成的第一事故源是契约。EX-57-01 用 Pydantic 模拟"服务端演进、旧客户端解析"的三种场景，把演进规则变成可执行的知识。

EX-57-01 | 示例代码/ch57_arch_boundary/ex_57_01_contract_evolution.py（完整可运行）

```python
# ── AI 服务侧的响应契约 ────────────────────────────────────────────────
# V1：上线时的版本（Spring 客户端按它写的 DTO）。注意 refs 是必填——
# 这是"引用溯源"产品的硬承诺，所以进了契约的必填区。
class AIReplyV1(BaseModel):
    answer: str
    refs: list[str]               # 必填：无引用的回答不符合产品承诺

# V2：第一次演进——"新增"一个字段，带默认值（规则 R1）
class AIReplyV2(AIReplyV1):
    confidence: float = 0.0       # 新增：模型置信度。旧客户端不认识它，但没关系

def main() -> None:
    # 场景 1：V2 服务返回新响应，V1 时代的 Spring 客户端（用 V1 模型模拟）解析
    v2_payload = {"answer": "年假不清零，可结转。", "refs": ["HR-007"], "confidence": 0.87}
    old_client_view = AIReplyV1.model_validate(v2_payload)     # 成功：多余字段被忽略
    # 场景 2：服务端"顺手"删掉必填的 refs 字段（规则 R2 的代价）
    try:
        AIReplyV1.model_validate({"answer": "年假不清零，可结转。"})
    except ValidationError as exc:
        ...  # missing loc=('refs',) —— Spring 侧反序列化同样会抛异常
    # 场景 3：refs 类型悄悄从 list[str] 变成 list[dict]（规则 R3 的隐蔽性）
    try:
        AIReplyV1.model_validate({"answer": "…", "refs": [{"doc_id": "HR-007", "quote": "…"}]})
    except ValidationError as exc:
        ...  # string_type（期望 str 得到 dict）
```

真实运行输出（本沙箱实测）：

```text
[场景1] V2 响应 → V1 客户端（新增字段带默认值）
        解析成功：answer='年假不清零，可结转。'，refs=['HR-007']（confidence 被安全忽略）→ 兼容 ✓
[场景2] 删除必填字段 refs → V1 客户端
        解析失败：missing loc=('refs',) → 破坏契约 ✗（Spring 侧反序列化同样会抛异常）
        边界：若字段本来就是可选带默认值，删除不会让解析报错，但读到默认值的
        客户端行为仍可能改变——删字段永远要走评审，'解析不炸'不等于'语义无害'。
[场景3] refs 改类型 list[str]→list[dict] → V1 客户端
        解析失败：string_type（期望 str 得到 dict）→ 破坏契约 ✗

[契约演进军规]
  R1 新增字段必须带默认值（旧端忽略未知字段）
  R2 永不删除/改名已有字段；要下线就先停止写入、观察一个版本周期再删
  R3 类型与语义冻结；确需变更 → 换新字段 + 新版本路径（/v2/ask）双跑过渡
  R4 契约测试进 CI：把本示例的三个场景写成 pytest（测试/test_ch57.py 即做了）
```

四条军规逐条解释：**R1** 是 Pydantic 的默认行为红利——`model_validate` 忽略未知字段，Java 的 Jackson 配 `@JsonIgnoreProperties(ignoreUnknown = true)` 后行为一致，两侧都要确认这个配置存在；**R2** 的"观察一个版本周期"是指客户端不一定跟着你发版，删字段的破坏要等所有在途客户端换代后才真正解除；**R3** 最隐蔽——类型改了但字段名没变，单元测试全绿（新模型自己解析自己当然没问题），炸的是**没升级的对面**，所以契约测试必须"拿旧模型解析新输出"（测试/test_ch57.py 就是这个写法）；**R4** 把知识固化成 CI 门槛，人忘机器不忘。

## 57.5 逐段解释：四种集成模式的适用与坑

**EX-57-02 | 示例代码/ch57_arch_boundary/ex_57_02_timeout_budget.py（完整可运行）**演示超时预算的正确分配，真实运行输出：

```text
── 正确配置：预算逐级递减 ──
网关总预算: 30.0s
  Spring 业务服务: 26.0s
    Python AI 服务调用: 22.0s
      LLM API（首字节 8s / 整体 18s）: 18.0s

── 错误配置：每层都抄 30s ──
  网关 30s / 业务 30s / AI 服务 30s / LLM 30s
  后果：LLM 第 29s 才吐完 → 业务层 30s 已超时返回 504 →
        Python 进程里这次调用若未被取消，token 已计费、结果无人接收。
  修复：① 预算逐级递减（本示例的正确配置）；② Python 侧监听客户端断连，
        断连即取消上游 LLM 请求（FastAPI 里 request.is_disconnected()，ch17 的 SSE 同款手法）。

── 校验器演示：子步骤之和 >= 总预算时直接报错（把事故拦在配置期）──
  ValueError: 业务服务：子步骤预算之和 10.0s 必须 < 总预算 10.0s（要给序列化/排队/重试留余量，精确用满是事故配置）
```

> ⚠️ 常见坑：超时配置最常见的来源是"抄"——网关 30s 就给业务 30s、AI 服务 30s、LLM 30s。正确姿势是**倒推分配**：LLM 最深最慢，先给它留足（如 18s），再逐级向上预留传输与排队余量。Budget.allocate 的校验器让"精确用满"在配置期就报错，而不是在事故现场暴露。

### 57.5.1 模式一：同步 HTTP（请求-响应）

**适用**：单轮、低延迟（亚秒~数秒）、调用方需要"立即拿结果再做下一步"的场景——分类、实体抽取、embedding、单次摘要。Java 侧 `WebClient/RestClient` 调 Python 的 REST 端点，Python 内部调 LLM 后整包返回。

**三个坑**：①**线程占用**——Java 同步客户端等 AI 响应时占着线程池线程，AI 延迟的尾部（P99 数十秒）会放大成线程池耗尽，务必配 `Resilience4j TimeLimiter` 或异步客户端，超时预算见 EX-57-02；②**重试叠加**——Java 侧重试 + Python SDK 内建重试（ch24：openai 默认 2 次）= 请求数翻倍，57 章的规则是**全局只留一层重试**（ch59.4 展开）；③**大 payload**——把整篇文档塞进请求体再让 Python 现场解析，不如 Java 先传引用（文档 ID），Python 从共享存储取——传输的是指针不是数据。

### 57.5.2 模式二：SSE 透传（流式问答）

**适用**：生成式回答逐字上屏。Spring 侧用 `WebClient` 拿到 `text/event-stream` 流，再透传给前端（或直接让前端 EventSource 打到 Python 服务，Spring 只做鉴权）。

**三个坑**：①**代理缓冲**——Nginx/网关默认缓冲响应体，SSE 会被攒成一坨最后发出（ch17.5.3 的 `X-Accel-Buffering: no`），每一层代理都要确认禁缓冲；②**断连不传播**——前端关了页面，Spring 的流断了，但 Python 与 LLM 之间的调用还在跑（token 白烧）。契约：**每一跳都要把"下游断开"传播成"取消上游"**，Python 侧靠 `request.is_disconnected()` 或 uvicorn 的生成器取消（ch17.5.3 两条路径）；③**事件契约无版本**——SSE 的 `event:`/`data:` 结构也要按 57.4 的军规演进（新增事件类型 ≠ 可以改已有事件的 schema），前端按事件名分发，未识别事件**忽略但不报错**（前向兼容）。

### 57.5.3 模式三：异步任务（提交-轮询/回调）

**适用**：长任务（批量文档入库、批量摘要、Agent 长跑）。Spring `POST /jobs` 拿 `job_id`，轮询 `GET /jobs/{id}` 或接收回调。

**EX-57-03 | 示例代码/ch57_arch_boundary/ex_57_03_async_task_contract.py（完整可运行）**演示任务契约三要点，真实运行输出：

```text
── 1) 正常生命周期：提交 → 推进 → 完成 ──
    提交：job_id=c7fa5bbaf6a5 status=queued created=True
    轮询 1：status=running
    轮询 2：status=succeeded result=done: batch_summary

── 2) 幂等提交：Spring 超时重发同一个请求（同一个幂等键）──
    二次提交：created=False，返回的是同一个 job？True
    （若不做幂等：同一批文档会被摘要两遍——token 双倍计费 + 结果互相覆盖）

── 3) 取消语义：RUNNING 可请求取消，终态拒绝 ──
    RUNNING 中请求取消 → 成功？True
    再推进（worker 迟到的消息到达）→ ValueError: 任务 cca0ae1083c6 已处于终态 cancelled，worker 拒绝推进
    对已完成任务请求取消 → 成功？False（终态不可取消，返回 false 即可，不要报错）
```

**三个坑**：①**无幂等键的提交**——Spring 侧超时重发是新任务不是重试，批处理跑两遍（输出里第 2 幕的对比），提交接口必须收 `Idempotency-Key` 头；②**轮询无退避**——固定 1 秒轮询 1 万个任务 = 自己打自己，按 1s→2s→4s（上限 10s）退避；③**结果无 TTL**——任务结果堆在存储里永不清理，成本曲线缓慢上扬，契约里写明"结果保留 24 小时，过期需重新提交"。

### 57.5.4 模式四：事件驱动（消息队列）

**适用**：解耦与削峰——入库流水线上游不关心下游处理进度；一个事件多个消费者（入库后同时更新索引、刷新缓存、记审计）。Spring 发消息（RocketMQ/Kafka），Python 消费。

**三个坑**：①**至少一次投递**——消息队列的默认承诺是"至少一次"，重复投递是常态，消费端必须幂等（按消息业务键去重，同 EX-57-03 的账本思想）；②**消息 schema 演进**——消息体也要按 57.4 军规走，理想状态是"只加不改"，激进方案（Schema Registry + 兼容性检查）超出本书范围，但军规 R4 的"契约测试进 CI"现在就能做；③**毒消息**——某条消息让消费者反复崩溃，重试队列会被它堵死，配死信队列（DLQ）+ 告警，把毒消息捞出来人工处理。

> 📌 生产提示：四种模式可以组合——同一服务常是"同步 HTTP 为主 + 异步任务兜底长任务 + 事件驱动做数据管道"。选型判断句：**要答案多快？** 立即→同步；能等→异步；不关心→事件；要逐字看→SSE。

## 57.7 常见错误与排查（真实踩坑形态）

**错误一：Java 侧反序列化突然报 `Unrecognized field "confidence"`。**
原因：Python 侧新增了响应字段，Java 的 Jackson 默认遇到未知字段抛异常。修复：两侧对齐"忽略未知字段"（Jackson `@JsonIgnoreProperties(ignoreUnknown=true)` / Pydantic 天然忽略），并把"新增字段"写进契约评审清单——R1 军规只是必要条件，接收端的宽容配置才是完整防线。

**错误二：接口偶发 504，但 AI 服务日志显示"调用成功"。**
现象：响应没送到客户端，Python 日志里却是 200。排查顺序：对比网关超时（30s）与 AI 服务内 LLM 调用耗时（28~30s）——预算相撞，网关先放弃。修复：按 EX-57-02 重排预算（逐级递减），同时 Python 侧监听断连取消上游调用。

**错误三：SSE 在测试环境流畅，生产"卡住几十秒后一次性吐完"。**
原因：生产链路里多了一层反向代理/网关在缓冲响应体。排查：`curl -N` 直连 Python 服务（流畅）→ 逐跳加代理复测，找到缓冲层。修复：该层禁缓冲（Nginx `proxy_buffering off` 或 `X-Accel-Buffering: no`），并确认 HTTP/1.1 分块传输未被改写。

**错误四：同一个批处理任务执行了两遍。**
原因：Spring 侧调用超时后重发 POST，Python 侧没有幂等键，两次提交是两个任务。修复：提交接口收 `Idempotency-Key`，服务端按键去重（EX-57-03 第 2 幕）；重试方负责"同一操作同一键"。

## 57.8 企业场景中的使用方式

- **Spring Cloud Gateway 侧的配套**：AI 路由单独配置超时与重试（不要复用普通路由的默认值）；响应缓冲对 SSE 路由关闭；`X-Trace-Id` 由网关注入并透传（ch17 的约定直接沿用）。
- **Resilience4j 参数对照**：调 Python AI 服务用 `TimeLimiter`（对应超时预算的业务层份额）+ `RateLimiter`（保护自己不被 AI 流量反噬）+ `CircuitBreaker`（AI 服务整体不可用时快速失败走降级，参数表见 ch59.5.1 的 Java 对照列）。

- **本教材 P3 项目**（Java 模拟生产 API + Python Agent 对接）是四模式的完整练习场：HTTP 工具封装、异步任务状态查询、超时重试都在那里落地。

## 58.2 一句话解释 + 生活类比 + 类比边界

**一句话解释**：AI 链路安全的总原则是**权限决策发生在代码层、发生在请求时、基于会话身份**——模型权重是静态的、全局的、概率性的，永远不能承载"谁是调用者、这次允不允许"这类动态、分租户、需要审计的决策。

**生活类比**：模型像一个**口才极好的新来的实习生**：他读过互联网上的所有公开资料（预训练），你们还给他做了岗前培训（微调/系统提示词）。但给不给门禁卡、能看哪些档案、能不能代表公司签字——这些是**行政制度**（代码与权限系统）管的事，与实习生本人多聪明无关。你不会因为实习生"看起来很可靠"就把门禁系统交给他管。

> 💡 类比边界：
> 1. 实习生"培训后会更可靠"，但**可靠性提升不等于授权依据**——微调能降低某些错误率，但"降低"是概率改善，权限需要的是确定性保证（可验证、可审计），两者不可互换；
> 2. 门禁卡 analogy 的止步处：真实系统里"代码层"也可能有 bug，所以安全从来不是单点而是**纵深**（58.5.5 的五层防线）——类比给的是原则，纵深给的是工程；
> 3. 不要反向过度：实习生也确实要培训——**模型层的软缓解与代码层的硬控制是互补的**，本章反对的是"只有软缓解"，不是"不要软缓解"。

## 58.3 正式原理与准确术语：RBAC 多租户在 AI 链路的三个落点

- **鉴权（authentication）**：证明"你是谁"——网关层完成（JWT/Session/API Key），Python AI 服务收到的应是**已验证的身份声明**（如解析后的用户上下文），而不是原始凭证。
- **授权（authorization）**：决定"你能做什么"。**RBAC（Role-Based Access Control，基于角色的访问控制）**：用户→角色→权限的映射；**多租户（multi-tenancy）**：多个客户/部门共享一套部署但数据与配额严格隔离。
- **纵深防御（defense in depth）**：多层独立防线，任何一层失守不导致整体失守。每层要回答两个问题：这层是**概率级**（降低风险）还是**确定性**（机制上不可能）？失守形态是什么？

RBAC/多租户在 AI 链路上有三个落点，缺一不可：

| 落点 | 做什么 | 依据与红线 |
|---|---|---|
| ① 检索过滤 | 查询向量库前按会话身份过滤候选集（部门/租户） | 必须**检索前过滤**——事后过滤会泄露"存在但不可见"的信息（ch34 红线：被过滤文档可能已影响打分/进入引用） |
| ② 工具权限 | 每个工具注册"最低角色"，执行前校验会话身份 | 模型"点名"工具只是请求不是授权（ch24.5 的第④步）；身份只认会话（EX-58-03 演示"我是管理员"话术失效） |
| ③ 审计 | 谁在何时用何参数调了什么工具、看了什么数据、模型答了什么 | 拒绝也要留痕；审计里不能有明文敏感数据（58.5.1 的位置纪律） |

> ⚠️ 常见坑：三个落点最常见的缺失是"只有②没有①"——工具权限做得很好，检索却查的全库。检索过滤的检验方法：用一个**无权账号**问一个只存在于无权文档里的问题，正确行为是"答不出+无引用"，任何"影子答案"（答案对了但没有引用）都是事故前兆——说明文档内容以某种方式渗进了上下文。

|---|---|---|---|
| EX-58-01 | ex_58_01_readonly_sandbox.py | 只读沙箱工具包装器 | 最小工具面 + resolve 校验 = 越界路径全部拒绝 |
| EX-58-02 | ex_58_02_masking_boundary.py | 脱敏混合方案边界 | 正则保下限可回归，LLM 会误改只能当提示器 |
| EX-58-03 | ex_58_03_tool_rbac_audit.py | 工具权限矩阵与审计 | 身份只认会话，拒绝也留痕 |

沙箱包装器的核心代码（EX-58-01 节选，完整版见示例文件）：

```python
class ReadOnlyFileTool:
    """只读文件工具：LLM 能看到的全部接口就是 read(path) 一个方法。"""

    def __init__(self, allowed_root: Path) -> None:
        self.root = allowed_root.resolve()   # 根目录本身先规范化

    def _validate(self, requested: str) -> Path:
        if not requested.strip():
            raise SandboxViolation("拒绝：路径为空")
        p = (self.root / requested).resolve()     # resolve 展开 ../、symlink、相对段
        if not p.is_relative_to(self.root):       # 不在白名单内一律拒绝
            raise SandboxViolation(f"拒绝：{requested!r} 解析后越出白名单根目录 {self.root}")
        return p

    def read(self, requested: str) -> str:        # 唯一暴露给 LLM 的能力
        p = self._validate(requested)
        if not p.is_file():
            raise FileNotFoundError(f"文件不存在：{requested}")
        return p.read_text(encoding="utf-8")
```

注意它**没有** write/execute 方法——写与执行的能力在接口上不存在（58.5.4 展开为什么这比"运行时拦截"可靠）。

## 58.5 逐段解释：五道防线逐层拆解

### 58.5.1 数据脱敏：正则 + LLM 混合方案的边界（EX-58-02）

**EX-58-02 | 示例代码/ch58_security/ex_58_02_masking_boundary.py（完整可运行）**用三幕演示混合方案的能与不能，真实运行输出：

```text
── 第一幕：正则脱敏的标准命中 ──
    原文：客户张三，手机 13812345678，邮箱 zs@example.com，已实名。
    脱敏：客户张三，手机 [手机号]，邮箱 [邮箱]，已实名。  命中：['手机号', '邮箱']

── 第二幕：正则的漏报边界（两个真实世界的变体）──
    变体A 原文：备用联系方式：１３８１２３４５６７８（全角数字）
    变体A 脱敏：备用联系方式：１３８１２３４５６７８（全角数字）  命中：[] ← 漏报！\d 只匹配半角数字
    变体B 原文：填表写的号码是 138-1234-5678，分段格式
    变体B 脱敏：填表写的号码是 138-1234-5678，分段格式  命中：[] ← 漏报！分隔符破坏了连续 11 位假设
    教训：正则的漏报可枚举、可逐个修复（把变体加进模式库再回归），
          但'修复到什么程度算够'是业务决定——这正是不该指望单一防线的原因。

── 第三幕：LLM 脱敏的误改风险（Mock 脚本模拟，脚本模拟真实模型常见失守形态）──
    原文：        客户张三，手机 13812345678，邮箱 zs@example.com，工号 A1024 的员工负责跟进，已实名。
    LLM 脱敏后：  客户张三（[手机号]，[邮箱]），工号 9 开头的员工负责跟进，已实名。
    对比：工号 A1024 被改成了'工号 9 开头'——业务字段被误改，且这种错
          无法用回归测试锁定（同输入两次输出可能不同），只能人工抽检。
```

**混合方案边界表**（本节核心交付）：

| 方案 | 强项 | 失守形态 | 生产定位 |
|---|---|---|---|
| 正则脱敏 | 确定性、可回归、可审计、零成本 | 漏报变体（全角/分段/字形变体），且新变体要人工补 | **主力**：覆盖所有可枚举形态 |
| LLM 脱敏 | 覆盖面广（能理解"像手机号的东西"） | 误改业务内容、不可回归、自身要联网调模型（脱敏数据出边界？） | **只做"疑似敏感"标记器**，输出候选交人工确认，不直接改写 |
| 人工抽检 | 发现前两者都漏的 | 抽样偏差 | **兜底**：按比例抽检 + badcase 回填模式库 |

**位置纪律（三条铁律）**：①脱敏必须发生在**进 Prompt 之前、进日志之前、进评估集之前**——三处任何一处后置都是泄露；②脱敏映射表（占位符↔原文）单独加密保管且**永不进日志**——否则日志成了新的泄露源；③模式库（正则集）进版本管理，变更走回归——正则是代码，不是配置碎片。

> 📌 生产提示：判断脱敏方案是否合格的最快方法：拿最终日志与发给模型 API 的请求体，反查原始明文能不能被拼出来。任何一条能拼出来，方案不合格——因为"发给第三方模型 API"与"写进日志"在合规意义上都是**数据出域**。

### 58.5.2 密钥管理：从环境变量到密钥管理服务

**等级一：环境变量（教学的起点，小团队的及格线）。**密钥不进代码、不进镜像，部署时注入进程环境（ch16 的 pydantic-settings 读取，ch02 的 `.env` 只用于本地开发且进 `.gitignore`）。**它的天花板**：`env` 对同进程内所有代码可见（依赖库都能读到）、随日志 dump 环境的框架特性存在误打印风险、轮换要重启。

**等级二：密钥管理服务（KMS/Secret Manager 的思想）。**无论用云厂商的 Secret Manager、Vault 还是公司的凭据平台，思想四条：①**集中存储与托管**——应用启动时向 KMS 认证后取密钥，密钥不落盘不进镜像层；②**最小暴露面**——每个服务只能取自己的密钥（服务身份认证），生产进程里的代码读不到其他团队的凭据；③**轮换**——密钥有版本，轮换时新旧并存一段窗口，应用无感切换；④**审计**——谁在何时取了哪个密钥有记录（这一点对齐 ch58.3 的审计落点）。

**不进代码库的三道机械防线**：①`.gitignore` 覆盖 `.env`/密钥文件；②pre-commit/CI 阶段跑密钥扫描（正则匹配 `sk-` 开头、高熵字符串、私钥头）；③**事故预案**：发现密钥已提交——第一步是**吊销**（在厂商控制台作废），第二步才是清理历史提交。顺序反了等于没修：git 历史里的密钥永远能被翻出来，只有吊销让它失效。

```python
# 语法示意（非落盘示例）：CI 里的密钥扫描最小正则（生产建议用现成扫描器，覆盖更多模式）
import re
SECRET_PATTERNS = [
    re.compile(r"sk-[A-Za-z0-9]{20,}"),          # OpenAI 风格 Key
    re.compile(r"-----BEGIN (RSA )?PRIVATE KEY-----"),
]
def scan(text: str) -> list[str]:
    return [p.pattern for p in SECRET_PATTERNS if p.search(text)]
```

### 58.5.3 只读数据库 + 查询白名单 + 参数化 SQL（ch19 的深化）

ch19 已验证了三件事：参数化查询让注入在机制上失效、SQLite `PRAGMA query_only` 模拟只读账户、固定窗口限流。AI 场景把这些深化为**"LLM 生成的 SQL 也按不可信输入处理"**的完整管线（text-to-SQL/Agent 查库场景）：

| 层 | 控制 | 失守形态（为什么不能少） |
|---|---|---|
| 生成层 | 模型只生成 SQL 文本，等同用户输入 | —— |
| 静态校验 | 只允许单条 SELECT；表白名单；强制 LIMIT 上限；禁多语句 | 只靠正则匹配会有解析歧义——用 SQL 解析器（如 sqlglot 类工具，采用前自行核实）或至少"分号截断+关键字黑名单+表名白名单"三件套 |
| 执行层 | 只读账户执行（PostgreSQL `GRANT SELECT`，等价 ch19 的 query_only）；语句超时；返回行数上限 | 应用层校验有 bug 时，数据库权限是最后防线——**"改不了"由数据库保证**（ch19.5.2 原话） |
| 审计层 | 完整 SQL + 参数 + trace_id 落审计 | 事后无法回答"模型当时生成了什么、查到了什么" |

**边界声明**：本表的"静态校验"层在本书是设计规范与代码示意，未在沙箱接入真实 PostgreSQL 验证生产语法；白名单的完备性（嵌套子查询、CTE、函数调用）需要按所用数据库实测，采用前先写对抗测试。

### 58.5.4 工具审批与沙箱边界：subprocess 的风险与只读沙箱（EX-58-01 / EX-58-03）

**subprocess 的四类风险**（为什么"让 AI 跑命令"必须过沙箱）：①**shell 注入**——`subprocess.run(f"cat {path}", shell=True)` 的 `path` 来自模型参数或用户输入，`; rm -rf /` 直接拼接执行；②**能力过大**——`ls` 与 `rm`、`curl` 在同一把锤子里，进程继承了服务全部权限（环境变量里有密钥！`env` 泄漏是真实攻击面）；③**无边界副作用**——读写任意路径、访问网络、fork 轰炸；④**不可审计**——黑盒命令让事后无法回答"当时到底执行了什么"。

**沙箱等级表**（教学只做第一级，生产按风险升级）：

| 等级 | 机制 | 防什么 | 不防什么 |
|---|---|---|---|
| L1 进程内校验 | 最小工具面 + 路径白名单校验（本节示例） | 越界路径/越权操作（代码正确前提下） | 代码本身有 bug、依赖库被投毒 |
| L2 受限子进程 | subprocess 无 shell + 参数列表传参 + 清空环境变量 + 超时 | shell 注入、环境泄漏 | 进程级逃逸、资源滥用 |
| L3 容器/微 VM | 独立用户/网络禁用/文件系统只读/资源限额 | 进程级逃逸 | 内核级漏洞（需专业沙箱） |
| L4 人工审批 | 高危动作过 interrupt 审批（ch48） | 一切自动化误判 | ——（最后一道闸，成本最高） |

**EX-58-01 | 示例代码/ch58_security/ex_58_01_readonly_sandbox.py（完整可运行）**——只读沙箱工具包装器，真实运行输出：

```text
[沙箱] 白名单根目录：/tmp/tmpxohn5b9g/workspace

── 合法请求：读白名单内文件 ──
    read('docs/policy.md') → 年假政策：入职满一年 5 天。

── 攻击 1：../ 穿越（经典路径遍历）──
    SandboxViolation: 拒绝：'../../secret.txt' 解析后越出白名单根目录 /tmp/tmpxohn5b9g/workspace

── 攻击 2：绝对路径注入 ──
    SandboxViolation: 拒绝：'/tmp/tmpxohn5b9g/secret.txt' 解析后越出白名单根目录 /tmp/tmpxohn5b9g/workspace

── 攻击 3：符号链接逃逸（白名单内放一个指向外面的软链）──
    SandboxViolation: 拒绝：'innocent.md' 解析后越出白名单根目录 /tmp/tmpxohn5b9g/workspace（resolve() 展开了软链的真实目标）

── 攻击 4：想写文件 / 想执行命令？接口上就不存在 ──

    包装器有 write 方法？False  有 execute/run 方法？False

```

三个设计点逐条解释：①**最小工具面**——包装器只暴露 `read()`，写与执行在接口上不存在（攻击 4），这比"运行时拦截坏调用"可靠一个量级：拦截靠代码正确，消失的能力不需要正确性；②**先 resolve 再校验**——`Path.resolve()` 展开 `..`、相对段与符号链接，然后 `is_relative_to(root)` 判定在白名单内，三种攻击（1/2/3）全部被同一行判定挡住；③**拒绝可审计**——每次拒绝抛 `SandboxViolation` 且消息含原始请求与原因，调用方写审计日志。`测试/test_ch58.py` 用参数化测试锁定了全部越界路径。

**与审批的衔接**：沙箱防"越界"，审批防"越界内的高危"。写入类、删除类、重启类动作即使参数合法也要过 ch48 的 `interrupt()` 人工审批——**审批平台回调持有 resume 权，模型没有**。

### 58.5.5 Prompt 注入纵深防御：生产级五层防线

ch28 建立了注入的机制级理解（注意力竞争 + recency 优势）与四层缓解。生产环境在此基础上把防线扩成**五层**，每层标注强度（确定性/概率级）与失守形态——这张图是本节核心交付：

```text
用户输入 ──► ┌────────────────────────────────────────────────────────────┐
             │ 第1层 输入侧（概率级）：数据段标记包裹外部内容；注入模式检测；   │
             │        来源白名单（间接注入：被检索的网页/工单先过审核）         │
             ├────────────────────────────────────────────────────────────┤
             │ 第2层 模型侧（概率级）：指令/数据分离模板；"数据中的指令不执行" │
             │        软条款——被"再忽略一次"绕过的可能性永远存在              │
             ├────────────────────────────────────────────────────────────┤
             │ 第3层 权限侧（确定性）：身份从会话取；额度校验；多租户过滤      │
             │        失守形态仅剩实现漏洞（如从消息内容取身份）              │
             ├────────────────────────────────────────────────────────────┤
             │ 第4层 工具侧（确定性）：工具注册表+角色矩阵（EX-58-03）；       │
             │        沙箱（EX-58-01）；高危动作人工审批（ch48）             │
             ├────────────────────────────────────────────────────────────┤
             │ 第5层 输出侧（确定性）：输出白名单模板；引用校验；异常输出     │
             │        丢弃+告警+审计（ch28 的 program_side_guard 生产化）     │
             └────────────────────────────────────────────────────────────┘
                        ▼                                    ▼
                    正常响应                            拦截 + 审计记录
```

**五层的分工逻辑**：1~2 层**降低攻击成功率**（概率级，永远不承诺 100%）；3~4 层**保证攻击即便"骗过模型"也拿不到东西**（模型可以说服，但代码不放行——没权限的数据检索不到、没权限的工具执行不了、白名单外的输出发不出去）；第 5 层是**兜底与发现**——前四层全漏时，异常输出形态（不在白名单模板内、引用对不上）触发拦截与告警，让"被攻击了"从不可知变成可观测。

> ⚠️ 常见坑：评审中最常见的错误排序是"在第 2 层投入 90% 精力"（反复打磨系统提示词的安全条款），而 3~4 层只有一句"模型会调用的工具都有权限控制"（没有实现）。自检问题：**如果模型被完全注入控制，攻击者能拿到什么？** 答案应该只有"它能生成文本"——拿不到数据（第 3 层）、调不了工具（第 4 层）、发不出异常内容（第 5 层）。拿不到，提示词失守就只是体验问题不是安全事故。

## 58.7 常见错误与排查

**错误一：身份信息从消息内容取。**
现象：后端把用户消息里的"我是管理员"或某 JSON 字段当身份用。修复：`SessionUser` 只来自网关注入/JWT 解析（EX-58-03 第 4 幕的对照）；代码评审红线——凡是 `request.body` 里的内容参与鉴权判断，一律打回。

**错误二：用正则"防注入"。**
现象：在用户输入里匹配"忽略指令"关键词，命中就拒绝。问题：注入话术无限变体（同义改写、编码、拆分），黑名单永远追不完；且正常用户提到"忽略"两个字会被误伤。正确姿势：关键词匹配最多进第 1 层做**检测信号**（记审计、降信任），防线主体永远在 3~4 层的确定性控制。

**错误三：沙箱用 try/except 包一层 subprocess 就算完事。**
现象：`try: subprocess.run(cmd, shell=True) except Exception: pass`——异常不是威胁模型，命令执行才是。修复：对照 58.5.4 的等级表逐级升级（参数列表传参、清环境、白名单、审批），并让 tests 里存在"越界输入必须被拒"的断言（本教材 test_ch58.py 的写法）。

**错误四：密钥打进镜像层。**
现象：`COPY .env /app/.env` 或 `ENV API_KEY=sk-xxx` 写进 Dockerfile。后果：任何拿到镜像的人 `docker history`/读层文件就能提取；镜像进仓库即等于密钥进仓库。修复：运行时注入（环境变量/KMS），镜像里只有代码与依赖；已泄漏的 Key 立即吊销（58.5.2 的顺序）。

**错误五：审计日志记了明文敏感数据。**
现象：审计做得很好，但 `args` 里有手机号、模型输入全文。后果：审计系统成了最大的敏感数据仓库，权限松一寸泄露一丈。修复：审计前过 58.5.1 的脱敏管线（正则为主）；`args` 只记**参数名与脱敏后的值**；完整原文如需排障，进独立的加密存储并单独授权。

## 58.8 企业场景中的使用方式（Spring Security 对照）

- **工具权限 ↔ Method Security**：`@PreAuthorize("hasRole('ADMIN')")` 与 EX-58-03 的角色矩阵同构——把工具名映射到权限点，校验代码集中在执行入口一处，不在业务代码里散落 if。
- **检索过滤 ↔ 数据权限**：Spring 侧常见的"部门数据权限拦截器"（SQL where 注入部门条件）与 ch34 的检索前过滤是同一思想的两个战场；AI 场景多一步：过滤要发生在**向量召回之前**（候选集层面），不是结果层面。
- **审计 ↔ AOP 切面**：Java 侧用切面统一记审计，Python 侧集中在 `invoke_tool` 这类唯一入口（EX-58-03）——**入口唯一，审计才无死角**。
- **密钥 ↔ Spring Cloud Config/Vault 集成**：Java 团队已有 Vault 的话，Python 服务直接对接同一套（HTTP API 或 Agent sidecar），不要为 Python 另起炉灶。

## 59.1 真实问题引入：一天内的两次告警

某内容平台（合成案例）的 AI 摘要服务上线首日收到两次告警，风格完全相反。

**上午：429 风暴。**模型厂商配额临时下调，摘要服务开始收到 429。服务的响应是"重试"——SDK 内建重试 2 次（ch24），框架层又包了一层重试，再加上消费消息的重投递：**每一笔被限流的请求瞬间变成 4 笔**。配额雪上加霜，429 率从 5% 飙到 40%，直到有人手动把服务重启才停下来。

**下午：答非所问。**客服侧反馈摘要内容张冠李戴：把 A 商品的活动规则写进了 B 商品的摘要。排查发现团队为了省钱上了"语义缓存"——相似问题直接返回缓存的摘要。阈值设了 0.85，而两条不同商品的标题 embedding 相似度恰好 0.87。

两次事故各对应本章一半内容：上午是**流量整形**（重试/限流/熔断/背压）没做对，下午是**缓存边界**没想清。先讲机制，再给参数，最后划边界。

## 59.2 一句话解释 + 生活类比 + 类比边界

**一句话解释**：稳定性设计的对象是**故障的传播方式**——超时管"多久放弃"，重试管"放弃前再试几次"，限流管"进多少"，背压管"同时压多少"，熔断管"还试不试"，降级管"试不了时给什么"，缓存管"能不能不试"。

**生活类比**：这一套机制像**水坝的溢洪道系统**：限流是进水闸（控制进量），背压是水库容量（超了就泄洪而不是漫坝），重试是抽水机（低水位时再抽一次），熔断是泄洪道（水位危险时直接放水不走机组），降级是备用柴油机（电网挂了也能供水），缓存是高位水箱（同样是供水，不用每次都开泵）。大坝工程师不会说"这些机制让洪水不发生"——它们让**洪水不冲垮大坝**。

> 💡 类比边界：
> 1. 溢洪道是按"历史最大洪水"设计的，但没人能保证未来不超——**参数是起点不是结论**，本部分所有数字都标注了这一点；
> 2. 抽水机（重试）在洪峰期（限流期）恰恰是要停的——重试在故障时**放大**流量，这是 LLM 场景重试要特殊小心的根源（59.3）；
> 3. 水箱的水可能不新鲜（陈旧缓存），还可能"拿错瓶子"（语义缓存误命中）——缓存在稳定性与正确性之间做交换，59.5.3 专门讲这个交换。

## 59.3 正式原理与准确术语

- **超时（timeout/deadline）**：等待上限。三个不同的超时要分开配置：连接超时（建立 TCP/TLS）、首字节超时（TTFB，发出请求到第一个 token）、整体超时（完整响应）。流式场景整体超时常被"空闲超时"（token 间隔）替代。
- **重试（retry）**：失败后再试。三要素：**重试哪些错误**（429/5xx/连接错误可试；401/403/400 不可试）、**退避（backoff）**（指数退避 base×2ⁿ + 全抖动 jitter，防止同时重试）、**重试预算（retry budget）**（重试流量占比上限，如 10%——预算耗尽后本周期不再重试，这是对"重试风暴"的机制级封顶）。
- **限流（rate limit）**：控制请求**速率**（每分钟几个），ch19 的固定窗口/滑动窗口/令牌桶，按"租户×端点"两个维度配。
- **背压（backpressure）**：控制**在途量**（同时压在系统里几个），Semaphore+队列深度（59.5.2），uvicorn 的 `--limit-concurrency` 是进程级总闸（ch20）。
- **熔断（circuit breaker）**：错误率超阈值后**快速失败**一段时间（OPEN），期间不碰故障下游，冷却后半开探测（EX-59-04）。
- **降级（fallback/degradation）**：熔断/限流/超时后的替补方案，降级链：缓存 → 备用小模型 → 排队 → 拒绝（503+Retry-After）→ 静态话术。
- **幂等（idempotency）**：同一操作执行多次与一次效果相同。**幂等键（idempotency key）**：调用方为"同一个逻辑操作"生成的唯一标识，服务端据此去重。

**为什么 LLM 重试要特别小心"重复计费+幂等"**——这是 LLM 与普通 RPC 的第一个本质差异：

普通 RPC 的读超时通常意味着"服务端没处理完或没处理"，重试代价低。LLM 调用不同：**读超时时服务端往往已经完整生成并计费**——生成 30 秒完成，响应在网络里丢了或客户端只等了 20 秒。此时重试是"再买一次同样的东西"。第二个差异：LLM 应用常带工具调用与写操作（ch48 的副作用），重试可能重复执行副作用。

## 59.4 最小完整示例：LLM 重试的两笔账（EX-59-01）

**EX-59-01 | 示例代码/ch59_stability/ex_59_01_retry_double_billing.py（完整可运行）**把这两笔账算出来，真实运行输出：

```text
── 策略 A：朴素重试（读超时 → 原样重发，共试 3 次）──
    收到的请求：3 次；服务端真实生成并计费：3 次
    客户端拿到的答案：[None, None, '答案[3]：解释一下什么是缓存击穿']
    账单视角：3 × (500+300) tokens，其中只有 1 份结果被用到——其余是白烧的钱。

── 策略 B：幂等键重试（同一 Idempotency-Key 重发 3 次）──
    收到的请求：3 次（含重发）；服务端真实生成并计费：1 次
    客户端拿到的答案：[None, '答案[1]：解释一下什么是缓存击穿', '答案[1]：解释一下什么是缓存击穿']（重发命中账本，三次同一个结果）
    账单视角：只计费 1 次——同样的故障，代价差 3 倍。

── 处置决策表（读超时怎么办）──
  有幂等键且服务端支持   → 放心重试（策略 B）
  无幂等能力，请求只读   → 默认不自动重试：转降级（缓存/小模型/拒答）或人工重试
  无幂等能力，有副作用   → 绝不自动重试：先查副作用是否已发生（工具调用/写操作）
  429/连接失败（请求没到）→ 可以自动重试（还没花钱），退避+抖动，见 59.5.1 参数表
```

> ⚠️ 常见坑：OpenAI 官方接口**没有幂等键参数**（以厂商文档为准），策略 B 需要在网关层自己实现（按 key 记账）或选用支持幂等的服务。没有幂等能力时，"读超时默认不自动重试"看起来激进，实则是把"双倍账单"换成"一次降级"——成本与体验的交换通常划算。

## 59.5 逐段解释：参数表、背压与缓存边界

### 59.5.1 LLM 场景稳定性参数表（核心交付）

**诚实声明先行**：下表的数字是**工程惯例起点**（综合 ch15/ch19/ch24 的机制与业界常见配置归纳），不是本沙箱压测结论——沙箱没有真实模型流量，任何"生产最优值"都取决于你的流量形态、模型与预算。用法：拿它当评审底稿，逐行问"这个值在我的场景下该改吗"。

| 机制 | 参数 | 起点值 | 依据（为什么是这个量级） | 边界（什么时候要改） |
|---|---|---|---|---|
| 连接超时 | connect | 2~5s | TCP+TLS 建连秒级足够，慢说明网络问题 | 跨国/代理链路放宽到 10s 并告警 |
| 首 token 超时 | TTFB | 10~30s | 模型排队+预填常见秒级，30s 已能覆盖 P99 | 突发长上下文场景上调；持续超说明配额不足 |
| 整体/空闲超时 | read/idle | 非流式 60~120s；流式空闲 30s | 长生成需要大上限；流式用"空闲"判死 | 按模型实际 P99 输出时长定，参考 ch21 的 token 预算 |
| 重试：错误类型 | retryable | 429/408/5xx/连接错误；401/403/400 不试 | 确定性错误重试无意义（ch24） | 厂商错误语义要对照核实清单（ch24 表） |
| 重试：次数 | max_retries | ≤2（SDK 默认 2，够用） | 每加一次重试，尾延迟翻倍 | 全链路只留一层（ch57 的叠加坑） |
| 重试：退避 | backoff | base 0.5~1s，×2，全抖动 | 指数退避+抖动防同步重试（ch15.5.1） | 有 Retry-After 头必须遵从（429） |
| 重试预算 | budget | ≤10% 流量 | 重试流量占比封顶，防风暴 | 限流期内降到 0（熔断思维） |
| 读超时重试 | read-timeout retry | **默认关闭**（除非幂等键） | 重复计费+副作用（EX-59-01） | 网关实现幂等账本后放开 |
| 限流：维度 | scope | 租户×端点 双维 | 防一个租户吃光配额（ch19 隔离） | 单租户内部再按功能细分 |
| 限流：算法 | algo | 令牌桶/滑动窗口 | 固定窗口边界毛刺（ch19.9 题 2） | 内部调用固定窗口也够 |
| 背压：并发 | concurrency | 按下游配额定（如配额 QPS×平均延迟） | 在途量>配额必然 429，压进去也没用 | 每模型一个闸门，ch13 Semaphore+Redis |
| 背压：队列 | queue_depth | 0~2×并发数 | 队列是延迟的存放处，深队列=高延迟（EX-59-02） | 实时接口队列趋近 0：快速拒绝好过慢等待 |
| 熔断：窗口/阈值 | window/threshold | 最近 20~50 次，失败率 ≥50% | 小窗口灵敏、大窗口稳定，50% 是惯例 | 低流量场景按绝对失败数兜底（如连错 5 次） |
| 熔断：冷却/探测 | cooldown/probe | 30s / 1~3 个探测 | 给下游喘息，探测量要小 | 长恢复期服务（冷启动）加长冷却 |
| 降级：顺序 | chain | 缓存→小模型→排队→503 | 体验损失从低到高排列 | 高危意图（资金/权限）跳过缓存直接降级 |

**Java 对照（参数一一对应）**：Resilience4j `TimeLimiter`（timeoutDuration ↔ 超时）、`Retry`（maxAttempts/waitDuration/enableExponentialBackoff+jitter ↔ 重试三要素，**注意它没有 retry budget，需要自己包一层**）、`RateLimiter`（limitForPeriod/limitRefreshPeriod ↔ 限流）、`CircuitBreaker`（slidingWindowSize/failureRateThreshold/waitDurationInOpenState/permittedNumberOfCallsInHalfOpenState ↔ 熔断四参数）、`Bulkhead`（maxConcurrentCalls ↔ 背压并发闸门）。Sentinel 对应：流控规则（QPS/线程数 ↔ 限流/背压）、熔断降级规则（慢调用比例/异常比例 ↔ 熔断）、热点参数限流（按参数值限 ↔ 租户维度）。Spring Cloud Gateway 的 `RequestRateLimiter`（Redis 令牌桶）对应 ch19 的 Redis 方案——**算法同源，差别只在计数在 Java 网关还是 Python 应用**。

### 59.5.2 背压与并发控制：Semaphore + 队列深度

ch13 的 Semaphore 演示了"限并发"，但生产还差两件套：**排队上限**与**快速拒绝**。EX-59-02 补齐，真实运行输出：

```text
── 洪峰实验：并发上限 3 + 队列上限 2，10 个请求同时到达 ──
    成功完成：5 个（3 个在跑 + 2 个排队，跑完一个进一个）
    快速拒绝：5 个（排队位已满，立即 503 + Retry-After，而不是等 30s 再超时）
    闸门统计：accepted=5 rejected=5

── 为什么'无限排队'是事故配置 ──
    没有队列上限时，洪峰下第 200 个请求要等前 199 个跑完——
    客户端超时断开后服务端还在算（token 白烧），重试再来一波，系统进入雪崩。
    背压三板斧：并发上限（Semaphore）+ 队列上限（快速拒绝）+ 降级（拒绝时给缓存/兜底话术）。

[部署注意] asyncio.Semaphore 是进程内存——uvicorn --workers 2 时每个 worker
    各有一份，总在途量 = 2×N。跨进程的并发控制要用 Redis（ch19 限流同款思路）
    或 uvicorn --limit-concurrency（ch20，进程级总闸）。
```

三个层次的并发控制各管一段，不要混：**uvicorn `--limit-concurrency`** 是进程总闸（保护自己不被连接数打爆，ch20 实测存在）；**应用内 Semaphore** 是业务闸门（按"下游配额"精确定容，EX-59-02）；**Redis 限流** 是速率闸门（跨实例共享，ch19）。三者从外到内，越靠内越精确。

### 59.5.3 缓存与语义缓存的边界

精确缓存（ch19）：键=请求的确定性哈希，同请求必同键，**永不误命中**；代价是同义改写全 miss。语义缓存：键=embedding 相似度，相似问题共享答案，命中率高；代价是**误命中**——语义相近 ≠ 意图相同。

**EX-59-03 | 示例代码/ch59_stability/ex_59_03_semantic_cache_mishit.py（完整可运行，核心 10 行）**演示误命中如何发生，真实运行输出：

```text
── 先建立缓存：有人问过'病假有几天' ──
    写入缓存：'病假有几天' → 病假每年 10 天，需提供医院证明。

── 阈值 0.8：新查询 '年假有几天' ──
    缓存返回：病假每年 10 天，需提供医院证明。
    来源：cache:病假有几天(相似度0.866)  命中=True  正确=False  ← 误命中！语义相近（都有'X假有几天'），意图与答案完全不同

── 阈值 0.9：新查询 '年假有几天' ──
    缓存返回：miss
    来源：miss  命中=False  正确=False

── 对照：精确缓存（哈希键）在这个场景零风险 ──
    '年假有几天' 的哈希 ≠ '病假有几天' 的哈希 → 永不互串；代价是同义改写全 miss（命中率低）。
```

（示例里"模型"由确定性知识库扮演——错在缓存层不在模型层，这使演示与具体厂商无关。相似度 0.866 来自教材共享 MockEmbedder 的实测值。）注意 0.9 阈值那一幕：miss 之后如果回源，答案会正确——**阈值是"准确率损失"与"命中率收益"之间的旋钮**，没有免费的位置。

**语义缓存上线五条边界**（59.1 下午事故的预防清单）：①阈值保守起步（0.95 级别）按业务抽检收紧/放宽；②缓存键必须带**业务维度**（feature/租户/模型版本）——HR 助手与 IT 助手不共享答案空间；③**高危意图绕过**（退款/权限/金额类宁可多花钱不可答错话）；④记录"命中了哪条历史问题"（示例的 source 字段）——排障时它是唯一线索；⑤保留**总开关**，事故时一键回退精确缓存。

## 59.7 常见错误与排查

**错误一：三层重试叠加成风暴（59.1 上午事故）。**
现象：429 率上升时请求总量反而暴涨。排查：统计"出站请求量/入站请求量"比值，>1.5 即有重试叠加。修复：全链路只留一层重试（约定在调用方），SDK `max_retries=0` 关内建（ch24.5 第 4 点），加重试预算。

**错误二：熔断参数照抄文档。**
现象：低流量服务设"最近 50 次失败率 50%"——一天只 30 次调用，熔断永远不触发，形同虚设。修复：低流量按**绝对失败数**兜底（连错 5 次即开），高流量才用比例窗口；参数表每个值的"边界"列就是为此写的。

**错误三：缓存键不含租户维度。**
现象：A 公司用户偶尔看到 B 公司的制度摘要。排查：对比两条缓存记录的键与命中文本。修复：键里加 tenant_id（ch19 军规②"键里不放敏感信息"与"命名空间分层"的组合应用），同时检查语义缓存的相似度匹配是否也该**限定在租户内**进行。

**错误四：Semaphore 在多 worker 下"失效"。**
现象：设了并发 10，压测发现实际在途 20。原因：`--workers 2` 两个进程各一份 Semaphore（EX-59-02 的部署注意）。修复：跨进程计数用 Redis（INCR/DECR 或 ZSET），或把 uvicorn 收敛为单 worker + 更多副本（水平扩）。

**错误五：把 429 也重试到耗尽预算。**
现象：对 429 重试 3 次，每次都 429——这不是重试能解决的（配额没了）。修复：429 读 `Retry-After` 遵从等待；连续 429 直接触发熔断/降级，并把"触发限流"当作扩容信号（ch24.5 第 4 点原话："是要扩容配额或降请求率的信号，而不是'再多试几次'的信号"）。

## 59.8 企业场景中的使用方式

- **Resilience4j/Sentinel 双栈团队**：Java 网关做限流与熔断（保护自己），Python 应用做按下游配额的背压（保护厂商配额）——两层目标不同都要留（ch17.8 的结论在 59 章完整化）。
- **降级链的产品化**：降级不是纯技术动作——"从大模型降到小模型"要提前过评估（小模型在该任务上的质量分，ch60 的评估体系）、"拒绝服务"要配产品话术，**降级方案是要开发的功能，不是配置项**。
- **容量评估公式**：可用并发 ≈ 厂商配额 QPS × 目标 P99 延迟；背压并发上限 = 可用并发 × 安全系数（0.8）。公式里的每个数都来自实测（配额看厂商控制台，延迟看 ch60 的统计日志），**不要拍脑袋**。

<details>
<summary>点开查看参考答案</summary>

1. 限流管速率（每分钟进几个），背压管在途量（同时压着几个）。只有限流没有背压：每分钟放行 60 个但每个要 10 秒，在途稳态 10 个看似正常，突发下放行窗口内的请求同时涌入仍可能压垮下游连接池；只有背压没有限流：慢速调用方每秒 1 个永远不触发背压，但 1000 个调用方各 1 QPS = 1000 QPS 早已超配额（需要按调用方限流）。

## 59.11 面试追问[模拟题]

1. **[模拟题]** "你们的 AI 服务怎么防止上游限流把自己打挂？"——合格回答按防护链说：入口限流（按租户×端点，Redis 计数）→ 背压（并发+队列上限，快速拒绝）→ 出站重试预算（429 不硬试，Retry-After 遵从）→ 熔断（连续 429/5xx 打开，走降级链）→ 降级（缓存/小模型/503）。核心认知：**限流风暴是"重试+重投递放大"出来的，治的是放大系数不是入口流量本身**。
2. **[模拟题]** "语义缓存的阈值怎么定？"——合格回答：没有理论最优值，定法是"评估集上扫描阈值画 P-R 曲线"——把缓存命中当检索问题：每个阈值下统计"命中且正确/命中"（准确率）与"命中/应命中"（召回率），按业务对错答的容忍度选点，再配五条边界（59.5.3）。说不出评估方法的"拍脑袋 0.85"是不合格信号。
3. **[模拟题]** "熔断打开期间用户体验怎么保证？"——合格回答：降级链提前开发并演练（缓存兜底的陈旧度要产品确认；503 要带 Retry-After 让客户端退避；高危意图拒绝时给人工通道）。反问面试官一句也加分：**熔断保护的是系统，降级保护的才是用户**——两者必须配对设计。

# 第 60 章 成本与可观测：让每一分钱、每一毫秒可归因

> **本章目标**：建立"每次调用记什么"的字段规范并用 FastAPI 中间件真实实现；把 trace_id 从 ch17 的单服务实践扩展到跨服务贯穿；搭建离线评估/在线反馈/回归测试的三层评估闭环。
> **前置知识**：ch17（trace_id 中间件与 contextvars）、ch21（token 计数与 usage）、ch28（golden set 回归）、ch35（评估指标定义）、P1（评估集）。
> **学完你能做什么**：为一个 AI 功能算清"每次请求多少钱、钱花在哪个功能"；用结构化日志+trace_id 在几分钟内定位一笔可疑消费；回答"这个 Prompt 改动敢不敢上线"时拿出三层证据。

## 60.1 真实问题引入：月底的 3.7 万账单

某 SaaS 团队（合成案例）月底收到模型 API 账单，金额是上个月的 3 倍。复盘会上问了三个问题，全都答不上来：**哪个功能花的？**——账单只有月度总额，没有功能维度；**哪些调用是浪费的？**——日志是"2026-10-12 14:03:11 INFO 用户xxx提问成功"这种文本行，token 数没记，重试了几次没人知道；**质量有没有同步提升？**——没人说得清这个月改了哪些 Prompt、改完有没有跑评估。

账单不可怕，可怕的是**不可归因**。本章的目标是把"花出去的每一分钱"和"得到的质量"都变成可查询的数据：每次调用一行结构化记录（tokens/延迟/成本/trace_id/功能名），每个版本一套评估分数。有了这两样，账单翻倍时你在几分钟内能答出上面三个问题——而不是开一晚上复盘会。

## 60.2 一句话解释 + 生活类比 + 类比边界

**一句话解释**：可观测性（observability）= 结构化日志（每一次调用的事实）+ trace_id（把事实串成链路）+ 指标聚合（事实变成趋势）+ 评估体系（质量也是指标）；成本不是财务问题，是**带价签的可观测性**。

**生活类比**：可观测性像**商场的分户电表**：不是"这个月物业电费 3 万"，而是"三楼火锅店 1.2 万、一楼奶茶店 0.3 万、公共照明 0.5 万"。有了分户数据，"谁该省、怎么省"才有讨论基础。

> 💡 类比边界：
> 1. 电表只计量不判断——"三楼用电翻倍"可能是促销也可能是漏水，**归因判断仍要人做**（这正是 trace_id 与评估分数存在的意义：给判断供料）；
> 2. 分户电表装在自己家里，而模型 API 的"电表"在厂商那边（usage 由服务端返回）——**你至少要把厂商的读数抄回自己的账本**（中间件里记 usage），并知道两套口径的差异（tiktoken 本地估算 vs 服务端统计，ch21 的 count_method）；
> 3. 类比止于计量：质量维度（答得好不好）电表管不了，它是三层评估体系的事（60.5）。

## 60.3 正式原理与准确术语：每次调用记什么

**调用记录字段表**（本节核心交付——AI 调用日志的最小完备字段集）：

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| ts / trace_id | 时间戳 / 全链路追踪号 | 定位一笔消费对应的请求（ch17 已建立） |
| tenant / feature | 租户 / 功能名 | 成本归因的两个主维度（谁花的、花在哪个功能） |
| model / prompt_version | 模型名 / Prompt 版本 | 成本与质量都跟着这两个变量走 |
| prompt_tokens / completion_tokens | 输入/输出 token 数 | 成本的直接驱动；输入贵在累积（ch27 上下文膨胀） |
| count_method | token 计数方式 | 区分服务端统计与本地估算——两套口径不可混（ch21/ch24） |
| latency_ms / ttft_ms | 总延迟 / 首 token 延迟 | 用户体验由 TTFT 决定（流式场景），总延迟决定资源占用 |
| cost_est | 估算成本 | tokens × 单价；单价进配置不进代码 |
| finish_reason / status | 结束原因 / 状态码 | length 截断、tool_calls、异常各是一类成本与质量信号 |
| retry_count | 重试次数 | 重试是隐蔽的成本放大器（ch59），不记就看不见 |

**结构化日志（structured logging）**：日志行本身是 JSON 对象（JSONL），可被日志管道（ELK/Loki/云日志服务）直接解析聚合。文本日志（"用户提问成功"）无法按 feature 聚合 tokens——**不可聚合的日志等于没记**。

**指标（metrics）与日志的分工**：日志回答"这一笔发生了什么"（逐笔明细，贵，按需查），指标回答"趋势如何"（聚合数值，便宜，常驻面板）。从日志聚合出指标：每分钟成本、P99 延迟、429 率、各 feature token 均值——面板上至少这四张图。

## 60.4 最小完整示例：token/延迟/成本统计中间件（EX-60-01）

EX-60-01 | 示例代码/ch60_observability/ex_60_01_cost_middleware.py（完整可运行）

```python
@app.middleware("http")
async def cost_middleware(request: Request, call_next):
    trace_id = request.headers.get("X-Trace-Id") or uuid.uuid4().hex[:16]
    start = time.perf_counter()
    response = await call_next(request)            # 端点在 scope 里留下 usage
    latency_ms = (time.perf_counter() - start) * 1000

    usage: dict = getattr(request.state, "usage", {}) or {}
    price = PRICE_TABLE["demo-model"]
    prompt_t = usage.get("prompt_tokens", 0)
    comp_t = usage.get("completion_tokens", 0)
    cost = (prompt_t / 1000 * price["prompt_per_1k"]
            + comp_t / 1000 * price["completion_per_1k"])
    logger.info(json.dumps({
        "ts": round(time.time(), 3),
        "trace_id": trace_id,
        "path": request.url.path,
        "status": response.status_code,
        "latency_ms": round(latency_ms, 1),
        "prompt_tokens": prompt_t,
        "completion_tokens": comp_t,
        "count_method": usage.get("count_method", "unavailable"),
        "cost_est_yuan": round(cost, 6),
    }, ensure_ascii=False))
    response.headers["X-Trace-Id"] = trace_id
    return response

@app.post("/v1/ask")
def ask(body: AskIn, request: Request) -> dict:
    """业务端点：只管调模型，把 usage 交给请求作用域，记账是中间件的职责。"""
    result = get_llm().chat([...])
    request.state.usage = result.usage
    return {"answer": result.content}
```

真实运行输出（本沙箱实测；latency 每次不同）：

```text
{"ts": 1792387924.321, "trace_id": "t-demo-001", "path": "/v1/ask", "status": 200, "latency_ms": 142.8, "prompt_tokens": 31, "completion_tokens": 42, "count_method": "tiktoken:cl100k_base", "cost_est_yuan": 0.000131}
{"ts": 1792387924.326, "trace_id": "t-demo-002", "path": "/v1/ask", "status": 200, "latency_ms": 1.4, "prompt_tokens": 32, "completion_tokens": 43, "count_method": "tiktoken:cl100k_base", "cost_est_yuan": 0.000134}
```

三个设计决策逐条解释：①**业务代码零侵入**——端点只写一行 `request.state.usage = result.usage`（scope 在中间件与端点间共享），计时、算钱、打日志全在中间件；对比"每个端点自己打日志"的写法：漏记是必然的；②**价目表进配置且标注占位**——示例的 PRICE_TABLE 数字是演示占位（非任何厂商真实定价），生产从厂商定价页核对后放进配置中心：**价格会变，代码里的常量会腐烂**；③**usage 缺失按 0 记 + count_method=unavailable**——"没统计到"必须显式可见，被当成 0 成本与被当成没花钱是两种事故。

**成本估算的口径边界**：本示例的成本 = 本地 usage × 配置单价，属于**估算**；真实计费以厂商账单为准（折扣、批量价、缓存折扣都会让两边对不上）。工程姿势：每月对一次总账，偏差超阈值（如 5%）排查口径。

## 60.5 逐段解释：trace_id 贯穿与三层评估体系

### 60.5.1 trace_id 贯穿（ch17 的扩展）

ch17 在单服务内用 contextvars 建立了 trace_id（每请求唯一、日志全串、响应头回传）。生产链路上它要跨三道边界：**网关→Python**（Spring Cloud Gateway 注入 `X-Trace-Id`，Python 沿用不重新生成——EX-60-01 的第一行）；**Python→模型 API**（透传到厂商请求的 user/trace 字段或请求头，支持与否按厂商核实——至少本地日志已能串）；**同步→异步**（异步任务把 trace_id 存进任务记录，ch57 的 job_id 与 trace_id 配对——长任务跨小时，靠这对键才能从头查到尾）。

排障会话的最短路径：用户报障给出响应头里的 trace_id → 日志管道一查，该请求的完整时间线（检索了什么、Prompt 多长、调了什么工具、花了多少 token、为何失败）全部就位。**没有 trace_id 的排障是考古，有 trace_id 的排障是查账。**

### 60.5.2 三层评估体系（EX-60-02）

**EX-60-02 | 示例代码/ch60_observability/ex_60_02_eval_three_layers.py（完整可运行）**把三层闭环跑通，真实运行输出：

```text
── 第一层：离线评估（固定评估集，两条版本对比）──
    v1: hit_rate=0.50 refusal_ok=1.00 total=0.60
    v2: hit_rate=1.00 refusal_ok=1.00 total=1.00

── 第二层：在线反馈（模拟一周真实用户的点赞/点踩）──
    v1: 👍61 👎27 满意率=0.69
    v2: 👍74 👎12 满意率=0.86
    （线上满意率与离线分数方向一致 → 评估集代表性可接受；背离时优先怀疑评估集分布。）

── 第三层：回归门槛（发布 v2 前的 CI 断言）──
    断言1 total(v2) >= total(v1)：1.00 >= 0.60 → True
    断言2 对抗样本全守住（refusal_ok == 1.0）：True
    回归门槛：通过 ✓ 允许灰度

── 闭环：线上 badcase 回填评估集（评估网越织越密）──
    badcase 回填后评估集规模：6 条（badcase 必须先脱敏——ch58 的位置纪律）
    下一次改 Prompt，q6 就在回归网里——这正是三层体系的意义：让'敢改'有依据。
```

三层各自的定位与局限（对照表，指标定义沿 ch35/P1）：

| 层 | 回答什么 | 频率 | 成本 | 局限 |
|---|---|---|---|---|
| 离线评估 | "在**我准备的**样本上，新版本比旧版好吗" | 每次改动（分钟级，Mock/真实模型） | 低~中（真实模型按样本量计费） | 评估集分布 ≠ 线上分布，会老化 |
| 在线反馈 | "**真实用户**觉得好吗" | 常态（点赞点踩/人工纠正率） | 低（埋点） | 反馈有偏（不满意才点），慢，不能灰度前用 |
| 回归测试 | "这次改动有没有**破坏既有承诺**" | 每次发布前（CI 门槛） | 低（本地/CI 跑） | 只能守既有覆盖面，发现不了新问题 |

三层的协作关系是**闭环**：离线评估守发布、在线反馈验真实、badcase 回填评估集修"分布老化"（EX-60-02 的最后一幕）；回归门槛里**对抗样本单列**（只断言安全底线，ch28 的思想——质量分可以商量的，安全分不可以）。ch28.8 的"Prompt 资产仓库 + 评估流水线"是本节的企业级完整形态，本节给出的是它的最小可运行内核。

> 📌 生产提示：把三层评估和 ch59 的降级链连起来——"降到小模型"的决策依据不是拍脑袋，是小模型在**同一套评估集**上的分数。评估集是整个生产体系的质量度量衡：Prompt 版本、模型版本、降级方案，都用同一把尺子量。

## 60.7 常见错误与排查

**错误一：文本日志"看起来什么都有"，但无法回答任何聚合问题。**
现象：日志文件几 GB，问"上周知识库问答花了多少 token"答不出。修复：按 60.3 字段表重构为 JSONL（EX-60-01 直接可用）；过渡期用正则从旧日志回填关键字段，明确标注估算口径。

**错误二：成本只按月总算。**
现象：月底才知道超支，为时已晚。修复：维度下沉（租户/feature/模型），日级聚合+预算告警（单租户日预算超 80% 告警、100% 限流——ch59 限流的成本版）。

**错误三：TTFT 没测，流式体验优化无从下手。**
现象：用户抱怨"慢"，总延迟 P99 只有 3 秒（不慢）。真相：TTFT 8 秒——用户等首字等到关页面。修复：中间件记 ttft（流式响应在首 chunk 时刻打点）；优化方向是预填长度（缩短输入）、首包话术（先回一句"正在检索…"）、厂商侧的流式支持。

**错误四：评估集只测 happy path。**
现象：离线全绿，线上注入样本全军覆没。修复：评估集分层（常规/对抗/边界，ch28.7 错 5 的同款病），对抗样本单独门槛。

**错误五：把"没有反馈"当"满意"。**
现象：点赞率 95% 就宣布质量达标。真相：99% 的用户不点赞——分母错了。修复：看"反馈率"（反馈数/请求数）先确认信号是否有效；人工纠正率（客服改过多少 AI 答案）比点赞更硬。

## 60.8 企业场景中的使用方式

- **Micrometer/MDC 对照**：Java 侧 `MDC.put("trace_id", ...)` + Micrometer 指标注册 ↔ Python 侧 contextvars + JSONL 日志聚合——**字段规范（60.3 表）两边共用**，同一个 trace_id 在 Java 与 Python 的日志里同值可查（ch57 的跨语言链路在这里闭环）。
- **OpenTelemetry 的定位**：OTel 是"字段规范的行业标准实现"（trace/span 语义、跨语言 SDK），生产可评估引入；本书教的是规范本身（记什么、怎么串）——先有数据规范，再选实现，顺序不能反。
- **成本归因的产品化**："这个功能这个月花了多少"要有看板（日志聚合 → BI/自建面板），给产品经理看 feature 维度、给老板看总趋势、给运维看 429/延迟——**同一份日志，三种切面**。

## 61.1 真实问题引入：周五下午的一次"完美上线"

某团队（合成案例）周五 16:00 上线新的 AI 客服功能：测试全绿、镜像构建成功、`kubectl apply` 一气呵成。17:30 用户开始投诉"机器人答非所问"；18:20 模型 API 开始 429（流量估算错了 3 倍）；19:00 有人提议回滚，才发现**没有演练过回滚**——数据库迁移是新写的，旧版本代码对新表结构不兼容，回滚等于停服。最后通宵手工修复。

复盘的三条结论构成本章骨架：①**上线是流程不是事件**——测试绿只是"可以开始上线"，不是"上线完成"；②**容量与回滚是上线的一半工作量**，另一半才是部署；③**故障排查的能力在上线前就要准备**（日志字段、告警规则、案例演练）。先讲流水线，再讲探针与 K8s，最后是检查清单与三个案例。

## 61.2 一句话解释 + 生活类比 + 类比边界

**一句话解释**：上线 = 可重复的流水线（CI/CD）+ 机器可读的健康信号（探针）+ 可回退的发布（版本化+回滚演练）+ 可勾选的检查清单（把纪律外化）。

**生活类比**：上线像**航班的起飞流程**——机长不是"感觉能飞"就起飞，而是逐项念检查单（checklist）；起飞后塔台持续监控（探针/告警）；发现异常有既定复飞程序（回滚）。航空业用血泪教训证明：**聪明人靠记忆会漏项，纪律靠清单不漏**。

> 💡 类比边界：
> 1. 检查单不能替代演练——飞行员也进模拟器：回滚、降级、扩容都要**真演练**过（本部分反复强调）；
> 2. 航班的"复飞"是标准动作，软件的回滚常被政治化（"都上了为什么撤"）——**回滚的技术成本要压到接近零**（版本化+兼容迁移），让回滚不变成心理战；
> 3. 检查单是上线纪律的最小形态，更大的形态是 SRE 的变更管理与错误预算——超出本书范围，思想相通。

## 61.3 正式原理与准确术语

- **CI（持续集成）**：每次提交自动验证（lint+测试），绿是合并门槛。AI 服务的 CI 纪律：**测试一律 Mock 模式**（真实调用慢、贵、不确定——CI 要的是确定性），模型相关质量靠 ch60 的离线评估层（可以定时跑，不阻塞每次提交）。
- **CD（持续部署/交付）**：验证通过后自动发布。**灰度/金丝雀（canary）**：新版本先接 5% 流量，观察指标再放量；**回滚（rollback）**：切回上一版本——前提是版本化部署与兼容的数据迁移。
- **存活探针（liveness probe）**：失败=重启容器。只回答"进程自己还活着吗"。
- **就绪探针（readiness probe）**：失败=摘除流量（不重启）。回答"现在能接请求吗"（依赖可用性）。
- **HPA（Horizontal Pod Autoscaler）**：按指标（CPU/自定义指标如 QPS）自动增减副本数。

```yaml
name: ai-service-ci

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.12"]   # 与镜像基础版本对齐；多版本时在此追加
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip               # 依赖缓存：pip install 不变时秒级跳过

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt -r requirements-dev.txt 2>/dev/null \
            || pip install -r requirements.txt

      - name: Static checks (lint)
        run: |
          ruff check .
          python -m compileall -q examples   # 快速语法兜底

      - name: Run tests (mock mode, no network)
        env:
          LLM_MODE: mock           # CI 一律 Mock：真实调用又慢又花钱还不稳定
        run: python -m pytest 测试/ -q

  build:
    needs: test                    # 测试绿了才构建镜像
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - name: Build image (tag only, push is team-infra's job)
        run: docker build -t ai-service:${{ github.sha }} .
        # 沙箱教学仓库无 Dockerfile 构建环境；真实仓库按 ch20 的多阶段 Dockerfile 执行

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production       # 受保护环境：可配置人工批准（approvals）
    steps:
      - name: Deploy (placeholder)
        run: echo "真实部署命令由团队平台注入；必须支持一键回滚（见教材 61.5.3 检查清单第 14 项）"
        env:
          API_KEY_REF: ${{ secrets.OPENAI_API_KEY }}   # 密钥只走 secrets 注入，绝不写进代码
```

五个设计决策逐条说理：①**三段式 job 依赖**（test→build→deploy，`needs` 链）——任何一段红，后面不执行；②**Mock 纪律进 CI**——`LLM_MODE: mock` 写死在环境变量里，PR 级测试秒级完成且零成本（质量评估另设定时任务跑真实模型，不阻塞开发）；③**pip 缓存**——依赖不变时安装层秒跳（ch20 层缓存在 CI 的等价物）；④**deploy 用受保护 environment**——生产部署可配人工批准与密钥隔离（GitHub Environments 语义），密钥只走 `secrets.` 引用（58.5.2 的密钥纪律在 CI 的落点）；⑤**镜像 tag 用 commit SHA**——部署的版本可追溯到具体提交，回滚=切回旧 SHA。

## 61.5 逐段解释：健康检查、探针与 K8s 最小知识集

**存活与就绪分离（EX-61-02，完整可运行）**——这是从 Java 过来的工程师最容易配错的一处。真实运行输出：

```text
── 场景 1：依赖全部健康 → 就绪 ──
    GET /healthz → 200 {'status': 'alive'}
    GET /readyz  → 200 {'status': 'ready'}

── 场景 2：Redis 挂了 → 就绪失败（503），但存活仍是 200 ──
    GET /healthz → 200（进程本身没问题，不该重启）
    GET /readyz  → 503 {'status': 'not_ready', 'failed': ['redis: ConnectionError: connection refused']}（K8s 把 pod 从 Service 摘除，流量不再打进来）
    反面教材：如果把 redis 检查写进 /healthz，K8s 会重启 pod——
    Redis 抖 30s，你的服务被重启 N 次，恢复后还得重新预热缓存，抖动被放大。

── K8s 探针最小集（进阶选修）──
    readinessProbe: httpGet /readyz port=8917 initialDelaySeconds=5 periodSeconds=10
    livenessProbe:  httpGet /healthz port=8917 initialDelaySeconds=15 periodSeconds=20
    （探针失败会重启容器——所以 liveness 的检查逻辑必须'只管进程自己'。）
```

ch17 的 /healthz 是"存活"语义的雏形；本示例补上 /readyz 并把语义钉死：**依赖健康只影响 readyz**。一个便于记忆的判据：这个检查失败时，你希望 K8s **重启容器**还是**暂时别把流量打给它**？前者进 liveness，后者进 readiness。

**K8s 最小知识集（○进阶选修，未在本沙箱验证，以官方文档为准）**——Java 团队用 K8s 跑 Spring Boot 的经验大部分平移，需要重新建立的认知按优先级列四条：

| 概念 | 最小必懂 | AI 服务特有注意点 |
|---|---|---|
| Deployment | 副本数、镜像版本滚动更新、`revisionHistoryLimit` 支持回滚 | 镜像 tag 用 SHA（61.4）；滚动更新的 maxUnavailable 让灰度天然发生 |
| 探针 | readiness/liveness 分离（本节） | AI 服务的就绪检查含"模型配置就绪"（Key 可用、配额未耗尽的轻量探测，别真调模型） |
| HPA | 按 CPU 或自定义指标（QPS/在途请求数）扩缩 | 扩容缓解不了厂商配额瓶颈——HPA 上限要和 ch59 的背压参数对齐 |
| Secrets/ConfigMap | 密钥挂载不进镜像、配置与代码分离 | 对接 58.5.2 的密钥管理思想；Secret 的 base64 不是加密，RBAC 才是 |

**边界声明**：K8s 的 Service/Ingress/网络策略、多集群、服务网格等本书一律不展开——这些属于平台工程，AI 应用工程师"能看懂 YAML、能与运维对话"即可，深度以岗位需要为准。

### 61.5.4 三个故障排查案例（合成案例，演练用）

以下三个案例为**教学合成的演练案例**（现象与排查路径参照真实故障的典型形态构造，具体数字为虚构），建议当剧本演练：先只读"现象"，自己写排查路径，再对答案。

### 案例 A：突发 429 风暴

**现象**：上午 10:07 起，AI 客服的 429 率从 2% 飙到 45%，P99 延迟从 3s 涨到 28s；厂商配额未变；无新版本发布。

**排查过程**：①看 429 的租户/功能分布（ch60 结构化日志的价值时刻）——98% 集中在"新上线的批量工单摘要"功能；②看该功能的**出站/入站请求比**——比值 3.8（正常应 ≈1），说明重试在放大流量；③看重试日志——SDK 内建重试 2 次 + 业务层自己又包了一层"失败重试 3 次"，对 429 也在重试。

**根因**：新功能把"摘要失败"笼统地归为可重试，429 也进入重试；两层重试叠加，把"配额不足"放大成"配额挤兑"。**修复**：立即——下线业务层重试（只留 SDK 一层）；对 429 识别 `Retry-After` 并退避；把批量摘要改走异步任务削峰（EX-57-03）。**预防**：重试预算与"可重试错误清单"进代码评审 checklist（ch59.5.1 表第 4~7 行）；429 率告警阈值 5%（超过即人工介入而不是等系统自愈）；新功能上线前做 1.5 倍预估流量的容量评估。

### 案例 B：语义缓存误命中事故

**现象**：客服反馈"机器人把病假天数说成年假天数"，此类投诉 2 天内 11 起；版本无变更。

**排查过程**：①按投诉的 trace_id 查会话日志——回答内容与知识库比对，确认回答来自**缓存**（ch59.5.3 的 source 字段记录了命中的历史问题："病假有几天"）；②复现两条查询的 embedding 相似度——"年假有几天" vs "病假有几天" = 0.866（EX-59-03 的真实数值），高于缓存的 0.85 阈值；③问变更历史——阈值 0.85 是上线时"参照别家经验"拍的，**从未用评估集扫描过**。

**根因**：语义缓存的阈值未经评估校准；且缓存键没有 feature 维度（HR 问答与考勤问答共享缓存空间），放大了误命中面。**修复**：立即——关语义缓存总开关（回退精确缓存，五条边界里的第⑤条）；短期——阈值提到 0.95 并在评估集上扫描 P-R 曲线选点；中期——缓存键加 feature/租户维度，高危意图（政策数字类）绕过缓存。**预防**：语义缓存上线必过"误命中评估"（59.11 追问 2 的方法）；缓存命中日志常驻抽查（每周人工核对 50 条命中）；给"答错数字"单独建告警（数字类回答与知识库比对）。

### 案例 C：检索权限回归

**现象**：B 部门员工在问答助手里看到了 A 部门制度的**具体条款内容**（引用列表里没有该文档）；无版本发布记录（排查时发现实际上线了一个未走流程的"检索优化"）。

**排查过程**：①用 B 部门测试账号复现——确认能看到 A 部门文档内容；②查该账号会话的完整 Prompt 日志（ch60 结构化日志）——A 部门文档的片段**在上下文里**，说明检索层把它召回进了 Prompt；③diff 检索代码——两周前一次"检索优化"把 ch34 的**检索前过滤**改成了"检索后过滤"（先全库召回再按权限删引用列表，理由是"前置过滤让命中率指标变难看"）；④查那次变更的测试——只测了命中率，没有权限断言。

**根因**：权限过滤从候选集层被移到结果层（ch34 红线被违反），且该变更绕过了上线清单（61.5.3 第 9 项本可拦住：检索前过滤要有测试）。**修复**：立即——恢复检索前过滤；对受影响周期做影响面评估（哪些 B 部门会话看过 A 部门内容，按合规要求上报）；短期——权限回归测试进 CI（无权账号查询无权文档，断言"无内容渗漏"）。**预防**：**安全断言进评估集**（对抗样本思想：权限不是性能优化可以商量的）；变更清单强制过 61.5.3 的第 9~12 项；"绕流程上线"本身进事故复盘的组织项。

三个案例的共性值得指出：**根因都不是"技术做不到"，而是"防线被省略"**——省略评估（案例 B）、省略权限断言（案例 C）、省略重试纪律（案例 A）。这正是检查清单存在的意义。

## 61.7 常见错误与排查

**错误一：CI 里跑真实模型调用。**
现象：CI 从 3 分钟变成 20 分钟，偶发红（网络/限流），团队开始"重跑直到绿"。修复：CI 只跑 Mock（确定性），质量评估另设定时任务（ch60 的离线评估层），报告挂 PR 但不阻塞提交。

**错误二：探针全指向 /healthz 且带依赖检查。**
现象：Redis 抖动引发全局重启风暴（EX-61-02 的反面教材）。修复：liveness 只查进程（永远 200，除非进程真死了）；依赖进 readiness。

**错误三：回滚没演练。**
现象：61.1 的通宵。修复：每次发版前在预发环境做一次"部署→发现问题→回滚"全程演练，把回滚命令写进发布文档（不是写在某个人的脑子里）。

**错误四：上线无容量评估。**
现象：流量按预估 1/3 评估，上线即 429（案例 A 的远因）。修复：容量公式（ch59.8）+ 预估流量的 1.5 倍压测（背压参数在压测下校准）。

**错误五：告警全是"服务不可用"级别。**
现象：要么全绿要么全炸，中间状态（429 率 20%、缓存命中率腰斩、成本日环比 +80%）无人知晓。修复：按 60.3 字段聚合出四个趋势面板（ch60.3 指标），每个设阈值告警——**中间状态的告警才是预防性的**。

## 61.8 企业场景中的使用方式

- **与 Spring Boot 流水线的合流**：Jenkins/GitLab CI 团队把 61.4 的三段骨架翻译成 Jenkinsfile 即可；**AI 特有的三个新增点是 Mock 测试纪律、契约测试（ch57）、评估门槛（ch60）**——其余 stage 与后端服务完全一致，运维心智零迁移。
- **Actuator 对照**：Spring Boot 的 `/actuator/health/liveness`、`/actuator/health/readiness`（K8s Probes 支持）与本节 /healthz、/readyz 一一对应——**同一个 K8s 集群里两种语言的服务用同一套探针语义**，平台侧无需区分。
- **发布评审会节奏**：把 61.5.3 清单做成模板（每项挂证据链接），新功能上线前 30 分钟评审会逐项过；灰度期盯 ch60.3 的四个指标面板，24 小时无异常再放量——**清单+面板+灰度**是上线纪律的最小闭环。
- **多租户 SaaS 的额外两条**：配额与限流参数按租户灰度（新租户先小配额）；成本告警按租户独立（一个租户的异常用量不惊动全部）。

## 61.11 面试追问[模拟题]

1. **[模拟题]** "AI 服务的 CI/CD 和普通后端有什么不同？"——合格回答：三点——测试纪律（CI 一律 Mock，质量评估独立定时跑，成本与稳定性原因）；契约测试（跨语言序列化契约进 CI，ch57）；评估门槛（发布前要过评估集+对抗样本，ch60——这是普通后端没有的"质量回归"）。其余（流水线骨架、探针、回滚）与后端同构。
2. **[模拟题]** "上线后用户说'AI 回答变慢了'，你的排查顺序？"——合格回答：先定位到会话（trace_id）看该请求的 TTFT/总延迟/token 数；对比时段基线（ch60 的指标面板）区分"个别慢"与"整体慢"；整体慢看三维——上游（厂商延迟/429）、自身（并发/队列/缓存命中率）、输入（上下文膨胀，ch27）——按数据收敛，不按感觉猜。
3. **[模拟题]** "为什么说'回滚是上线的一半'？"——合格回答：回滚能力决定"出事后的爆炸半径与恢复时长"；它要求版本化部署（SHA tag）、数据迁移双向兼容、回滚命令演练过——这些约束反过来塑造部署设计（滚动更新、迁移脚本规范）。没有回滚的上线等于把恢复寄托在"现场修好"上（61.1 的通宵）。
